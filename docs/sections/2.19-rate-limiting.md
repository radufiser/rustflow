# 2.19 - Rate Limiting with Tower

## Overview

RustFlow's API is open for reads and protected by API keys for writes. But there's nothing stopping a client — malicious or misconfigured — from sending 10,000 requests per second. A single aggressive client can:

- **Exhaust server resources** — CPU time spent processing requests, memory for connection handling
- **Starve other clients** — legitimate requests queue behind the flood
- **Amplify external costs** — enrichment endpoints proxy to JSONPlaceholder; a flood of requests becomes a flood to their API too
- **Create denial-of-service conditions** — the server can't keep up, response times spike, health checks fail

Rate limiting is the first line of defense. It caps how many requests the server processes per time window, returning `429 Too Many Requests` for anything over the limit. Combined with authentication (who is this?) and authorization (are they allowed?), rate limiting completes the access control triangle: **can they call us at all, can they do this specific thing, and how fast can they do it?**

In this lesson we add rate limiting to RustFlow using Tower's built-in `RateLimitLayer` — zero external crates beyond what we already depend on.

### Rate Limiting in Enterprise Services

Rate limiting appears at multiple layers in production:

| Layer | Tool | Purpose |
|---|---|---|
| **Edge / CDN** | Cloudflare, AWS WAF | Block bad actors before traffic reaches you |
| **API Gateway** | Kong, Envoy | Per-client quotas, burst limits |
| **Application** | Tower `RateLimitLayer` | Protect local resources, backpressure |
| **Database** | Connection pool limits | Prevent query floods |

We're adding the **application layer** — it protects the Rust process itself. In a full deployment, you'd combine this with edge-level rate limiting for defense in depth.

### The Tower Approach

Tower provides `RateLimitLayer` in its `limit` feature. Unlike external rate-limiting crates that often require Redis or shared state, Tower's implementation is **in-process** — a simple token bucket that tracks request count per time window. It's lightweight, zero-dependency, and works perfectly for single-instance services.

For multi-instance deployments (behind a load balancer), you'd need distributed rate limiting (Redis-backed, for example). We'll discuss that in Section 10 (Deployment). For now, in-process limiting is exactly right.

## How Token Bucket Rate Limiting Works

Tower's `RateLimitLayer` uses a **token bucket** algorithm:

```text
Bucket capacity: 50 tokens
Refill rate: 50 tokens every 10 seconds

Request 1:  Bucket has 50 tokens → consume 1 → 49 left → ✅ 200 OK
Request 2:  Bucket has 49 tokens → consume 1 → 48 left → ✅ 200 OK
...
Request 50: Bucket has 1 token  → consume 1 → 0 left  → ✅ 200 OK
Request 51: Bucket has 0 tokens → ❌ 429 Too Many Requests

(10 seconds pass — bucket refills to 50)

Request 52: Bucket has 50 tokens → consume 1 → 49 left → ✅ 200 OK
```

Key properties:
- **Burst-friendly** — the full bucket allows short bursts (all 50 at once)
- **Self-recovering** — after the window, the bucket refills automatically
- **Global** — applies to all clients combined (not per-client)

The two parameters are:
- `num` — how many requests per window (bucket capacity)
- `per` — the time window (refill interval)

```rust
use tower::limit::RateLimitLayer;
use std::time::Duration;

// Allow 100 requests per 10 seconds
RateLimitLayer::new(100, Duration::from_secs(10))
```

### What Happens When the Limit Is Exceeded?

When the bucket is empty, Tower's `RateLimitLayer` doesn't immediately reject the request. Instead, it **waits** — it holds the request in a queue until a token becomes available. This is called **backpressure** rather than rejection.

However, from the client's perspective, this manifests as very slow response times. If the server is overwhelmed, requests pile up and eventually time out. The client sees timeouts rather than explicit `429` responses.

For our use case, we want explicit `429 Too Many Requests` responses — the client should know immediately that they're being rate-limited, not just experience slow responses. We'll handle this by combining the rate limiter with a load-shedding approach.

Tower provides `LoadShedLayer` for this purpose. When the inner service isn't ready (bucket empty), `LoadShedLayer` immediately rejects with an error rather than waiting.

Conceptually, you'd want to stack them like this:

```rust
// ⚠️ Conceptual — this WON'T compile with Axum!
Router::new()
    .layer(LoadShedLayer::new())
    .layer(RateLimitLayer::new(100, Duration::from_secs(10)))
```

But if you try this, `cargo build` fails with **two compile errors**. Understanding why is key to working with Tower layers in Axum.

### Problem 1: `RateLimit<Route>` Doesn't Implement `Clone`

Axum clones the inner service for every incoming connection. `RateLimitLayer` wraps your router in `RateLimit<S>`, which holds internal mutable state (a token bucket counter). That state **can't be trivially cloned** — if it could, each clone would have its own independent counter and rate limiting wouldn't work.

```text
error[E0277]: the trait bound `RateLimit<Route>: Clone` is not satisfied
```

**The fix:** `BufferLayer`. It spawns a background task that owns the single `RateLimit` instance, and hands out cheap, cloneable "handles" (channel senders) to it:

```text
Request → Buffer (cloneable handle) → RateLimit (single instance) → Router
```

### Problem 2: `Infallible` vs `BoxError`

Axum routes use `Infallible` as their error type — meaning "this service never fails at the middleware level; errors are always converted into HTTP responses." But `LoadShed` **can** produce a `BoxError` when it rejects (the "overloaded" error). The types are incompatible:

```text
error[E0277]: the trait bound `Infallible: From<Box<(dyn StdError + Send + Sync)>>`
              is not satisfied
```

**The fix:** `HandleErrorLayer` from `axum::error_handling`. It catches the `BoxError` and lets you convert it into a proper HTTP response (e.g., `503 Service Unavailable`).

### The Combined Solution

Both problems are solved together with `ServiceBuilder`:

```rust
use axum::error_handling::HandleErrorLayer;
use tower::{BoxError, ServiceBuilder, buffer::BufferLayer, limit::RateLimitLayer, load_shed::LoadShedLayer};

.layer(
    ServiceBuilder::new()
        .layer(HandleErrorLayer::new(|err: BoxError| async move {
            (StatusCode::SERVICE_UNAVAILABLE, format!("Service overloaded: {}", err))
        }))
        .layer(BufferLayer::new(100))
        .layer(LoadShedLayer::new())
        .layer(RateLimitLayer::new(50, Duration::from_secs(10)))
)
```

Request flow through the stack:

```text
Request → HandleError → Buffer → LoadShed → RateLimit → Router → Handler
              ↑            ↑          ↑
       catches BoxError  makes it   rejects if
       → HTTP response   cloneable  not ready
```

- **`HandleErrorLayer`** (outermost): catches `BoxError` from `LoadShed` (forwarded through `Buffer`) and converts it to an HTTP 503 response. Without this, the `BoxError` can't become `Infallible`.
- **`BufferLayer(100)`**: wraps everything below in a channel with capacity 100. The buffer's handle implements `Clone`, satisfying Axum's requirement. Errors from `LoadShed` propagate back through the channel to `HandleErrorLayer`.
- **`LoadShedLayer`**: checks if `RateLimit` is ready. If not (bucket empty), returns `BoxError` immediately. **Must directly wrap `RateLimit`** — if `Buffer` sits between them, `LoadShed` only sees the buffer (which is always "ready"), and rate limiting never triggers.
- **`RateLimitLayer`** (innermost): the actual token bucket.

### Why Three Tower Features?

| Feature | Provides | Purpose |
|---|---|---|
| `limit` | `RateLimitLayer` | Token bucket rate limiting |
| `load-shed` | `LoadShedLayer` | Convert backpressure into immediate rejection |
| `buffer` | `BufferLayer` | Wrap non-Clone services in a cloneable channel handle |

### Why `tower` and Not a Rate-Limiting Crate?

Several crates offer rate limiting (`governor`, `tower-governor`, `rate-limiter`). We use Tower's built-in `RateLimitLayer` because:

1. **Zero new dependencies** — `tower` is already in our dependency tree (Axum depends on it). We're just enabling features.
2. **Idiomatic** — it's a Tower layer, composes naturally with our existing middleware stack.
3. **Sufficient for single-instance** — we don't need Redis-backed distributed limiting yet.
4. **Educational** — understanding Tower's native building blocks prepares you for building custom middleware.

For production multi-instance services, `tower-governor` (backed by the `governor` rate-limiting library) is a popular choice — it supports keyed rate limiting (per-client), more algorithms, and can be backed by shared state. We'll discuss this in the exercises.

## Step 3: Add a Rate-Limited Error Variant

**Update** `crates/rustflow-server/src/errors.rs` — add a `RateLimited` variant so we can return a proper `429` response:

```rust name=crates/rustflow-server/src/errors.rs
// ── The unified error type ──────────────────────────────────

use axum::response::{IntoResponse, Response};
use axum::Json;
use reqwest::StatusCode;
use thiserror::Error;
use uuid::Uuid;

#[derive(Debug, Error)]
pub enum RustFlowError {
    #[error("Not found `{0}`")]
    NotFound(String),
    #[error("Bad request `{0}`")]
    BadRequest(String),
    #[error("Validation Failed `{0}`")]
    UnprocessableEntity(String),
    #[error("External Service Error `{0}`")]
    ExternalService(String),
    #[error("Internal Server Error `{0}`")]
    Internal(String),
    #[error("Conflict error `{0}`")]
    Conflict(String),
    #[error("Unauthorized `{0}`")]
    Unauthorized(String),
    #[error("Forbidden `{0}`")]
    Forbidden(String),
    #[error("Too Many Requests")]
    RateLimited,
}

impl IntoResponse for RustFlowError {
    fn into_response(self) -> Response {
        let (status, error, details) = match self {
            Self::NotFound(msg) => (StatusCode::NOT_FOUND, "Not Found", msg),
            Self::BadRequest(msg) => (StatusCode::BAD_REQUEST, "Bad Request", msg),

            Self::UnprocessableEntity(msg) => {
                (StatusCode::UNPROCESSABLE_ENTITY, "Validation Failed", msg)
            }

            Self::ExternalService(msg) => (StatusCode::BAD_GATEWAY, "External Service Error", msg),
            Self::Internal(msg) => (
                StatusCode::INTERNAL_SERVER_ERROR,
                "Internal Server Error",
                msg,
            ),
            Self::Conflict(msg) => (StatusCode::CONFLICT, "Conflict error", msg),
            Self::Unauthorized(msg) => (StatusCode::UNAUTHORIZED, "Unauthorized", msg),
            Self::Forbidden(msg) => (StatusCode::FORBIDDEN, "Forbidden", msg),
            Self::RateLimited => (
                StatusCode::TOO_MANY_REQUESTS,
                "Too Many Requests",
                "Rate limit exceeded. Please try again later.".to_string(),
            ),
        };

        let body = serde_json::json!({
            "request_id": Uuid::new_v4().to_string(),
            "error": error,
            "details": details
        });

        (status, Json(body)).into_response()
    }
}
```

### Why Add `RateLimited` to `RustFlowError`?

Tower's `LoadShedLayer` returns `503 Service Unavailable` by default. We want `429 Too Many Requests` with our standard JSON error format. By mapping the load-shed response to our error type, we maintain the consistent error structure that every RustFlow endpoint uses.

## Step 4: Add Rate Limiting to the Application

**Update** `crates/rustflow-server/src/main.rs` — add rate limiting as a layer:

```rust name=crates/rustflow-server/src/main.rs
mod extractors;
mod routes;
mod state;
mod errors;

use crate::state::AppState;
use axum::http::{HeaderName, HeaderValue, Method, StatusCode};
use axum::Router;
use axum::error_handling::HandleErrorLayer;
use rustflow_common::{APP_NAME, APP_VERSION};
use std::time::Duration;
use tokio::net::TcpListener;
use tower::{BoxError, ServiceBuilder, buffer::BufferLayer, limit::RateLimitLayer, load_shed::LoadShedLayer};
use tower_http::cors::CorsLayer;
use tower_http::services::{ServeDir, ServeFile};

#[tokio::main]
async fn main() {
    let state: AppState = AppState::new();

    // ── CORS configuration ──────────────────────────────────
    let cors = CorsLayer::new()
        .allow_origin("http://localhost:3000".parse::<HeaderValue>().unwrap())
        .allow_methods([
            Method::GET,
            Method::POST,
            Method::PUT,
            Method::PATCH,
            Method::DELETE,
        ])
        .allow_headers([
            HeaderName::from_static("content-type"),
            HeaderName::from_static("x-api-key"),
        ])
        .max_age(Duration::from_secs(3600));

    // Build the application router
    let app = Router::new()
        // Serve the dashboard at root
        .route_service("/", ServeFile::new("crates/rustflow-server/static/index.html"))
        // Serve static files from /static/*
        .nest_service(
            "/static",
            ServeDir::new("crates/rustflow-server/static")
                .append_index_html_on_directories(true)
        )
        .route_service("/favicon.ico", ServeFile::new("crates/rustflow-server/static/favicon.ico"))
        // Health & config — merged at root level (no prefix)
        .merge(routes::health::router())
        // Domain routes — nested under /api/*
        .nest("/api/tasks", routes::tasks::router(state.clone()))
        .nest("/api/projects", routes::projects::router(state.clone()))
        .nest("/api/users", routes::users::router(state.clone()))
        // Enrichment — combines local data with external API calls
        .nest("/api/enrichment", routes::enrichment::router())
        // Provide state to ALL routes (merged and nested)
        .with_state(state)
        // ── Layer stack ─────────────────────────────────────
        //
        // Chained .layer() calls: LAST applied = OUTERMOST (runs first).
        //   Request → CORS → HandleError → Buffer → LoadShed → RateLimit → Router
        //
        // 1. Rate limiting stack (applied first → innermost)
        .layer(
            ServiceBuilder::new()
                // HandleError: catches BoxError from LoadShed → HTTP 503
                .layer(HandleErrorLayer::new(|err: BoxError| async move {
                    (
                        StatusCode::SERVICE_UNAVAILABLE,
                        format!("Service overloaded: {}", err),
                    )
                }))
                // Buffer: makes everything below Clone (Axum requirement)
                // Also forwards errors from LoadShed back to HandleError
                .layer(BufferLayer::new(100))
                // LoadShed: MUST directly wrap RateLimit — checks its poll_ready.
                // If RateLimit has no tokens → "not ready" → LoadShed rejects immediately
                .layer(LoadShedLayer::new())
                // RateLimit: token bucket — 50 requests per 10s window
                .layer(RateLimitLayer::new(50, Duration::from_secs(10))),
        )
        // 2. CORS (applied last → outermost, runs first)
        //    OPTIONS preflights are handled here before reaching rate limiting
        .layer(cors);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr)
        .await
        .expect("Failed to bind to address");

    println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);
    println!("Rate limit: 50 requests per 10 seconds");

    axum::serve(listener, app).await.expect("Server error");
}
```

### Understanding the Layer Order

This is the trickiest part. With chained `.layer()` calls, the **last applied = outermost** (runs first on the incoming request). The `ServiceBuilder` block is applied first (innermost), and `.layer(cors)` is applied last (outermost). Inside `ServiceBuilder`, layers apply top-to-bottom. Let's trace a request through the full stack:

```text
Incoming request
  │
  ├── 1. CORS layer (outermost — applied last via .layer(cors))
  │     OPTIONS? → respond immediately with CORS headers
  │     Otherwise → add Origin, continue
  │
  ├── 2. HandleErrorLayer (ServiceBuilder top)
  │     Catches BoxError from LoadShed (forwarded through Buffer) → converts to HTTP 503
  │     No error? → passes through unchanged
  │
  ├── 3. BufferLayer
  │     Wraps everything below in a cloneable channel handle
  │     Forwards requests to background worker; forwards errors back
  │
  ├── 4. LoadShedLayer
  │     Is RateLimit ready? (checks poll_ready DIRECTLY on RateLimit)
  │     NO  → return BoxError immediately (propagates back through Buffer → HandleError → 503)
  │     YES → continue
  │
  ├── 5. RateLimitLayer (ServiceBuilder bottom)
  │     Tokens available?
  │     YES → consume token, pass through to router
  │     NO  → signal "not ready" (LoadShed catches this)
  │
  └── 6. Router → Handler
```

Why this order?

- **CORS outermost**: `OPTIONS` preflight requests should never count against the rate limit. If rate limiting ran first, preflight requests would consume tokens — and each non-simple request costs two tokens (preflight + actual).
- **HandleError before Buffer**: `HandleErrorLayer` catches the `BoxError` that `LoadShedLayer` produces (forwarded through `Buffer`) and converts it into a valid HTTP response. Without it, Axum can't compile — it expects `Infallible` errors, not `BoxError`.
- **Buffer before LoadShed**: `BufferLayer` wraps `LoadShed<RateLimit<...>>` in a channel, making it `Clone`. Axum clones the service for each connection — without `Buffer`, the compiler rejects the code. `Buffer` forwards errors from `LoadShed` back through the channel.
- **LoadShed directly wrapping RateLimit**: This is **critical**. `LoadShed` calls `poll_ready` on its inner service. If `Buffer` sat between `LoadShed` and `RateLimit`, `LoadShed` would check `Buffer`'s readiness — and `Buffer` is always "ready" (it has channel capacity). `LoadShed` would never reject anything. By placing `LoadShed` directly around `RateLimit`, it sees the actual token bucket state.

### Why Are HandleErrorLayer and BufferLayer Necessary?

These two layers solve **compile-time type errors**, not runtime behavior. To understand why, you need to know what "service" means in this context.

#### What Is a Service?

In Axum/Tower terminology, a **Service** is any type that implements the `tower::Service` trait — meaning it can receive a request and produce a response:

```rust
trait Service<Request> {
    type Response;
    type Error;
    fn call(&mut self, req: Request) -> Future<Output = Result<Response, Error>>;
}
```

Your entire built `Router` — after all routes, middleware, and layers are applied — becomes **one single Service**. It's the final object that takes an HTTP request and returns an HTTP response. Each layer wraps the previous service in a new one:

```text
Your Router (implements Service)
  → wrapped by RateLimitLayer  → RateLimit<Router>    (also a Service)
  → wrapped by LoadShedLayer   → LoadShed<...>        (also a Service)
  → wrapped by CorsLayer       → CorsService<...>     (also a Service)
```

The outermost wrapper is what Hyper (the HTTP server underneath Axum) actually calls to handle requests.

#### Why Does Axum Clone the Service?

Hyper handles TCP connections, and for each new connection it needs its own copy of the service to process requests concurrently:

```text
TCP Connection 1  →  Service clone A  →  handles requests on this connection
TCP Connection 2  →  Service clone B  →  handles requests on this connection
TCP Connection 3  →  Service clone C  →  handles requests on this connection
```

This means **every layer in the stack must implement `Clone`**. If any layer can't be cloned, the entire stack can't be cloned, and the compiler rejects it.

#### `BufferLayer` → Fixes `Clone`

`RateLimit<S>` holds internal mutable state (the token counter). If Rust let you clone it, each clone would get its own independent counter:

```text
Connection 1 → RateLimit clone A (50 tokens) → consumes tokens from A
Connection 2 → RateLimit clone B (50 tokens) → consumes tokens from B
Connection 3 → RateLimit clone C (50 tokens) → consumes tokens from C

// Each connection has its own 50-token bucket — rate limiting is useless!
```

So `RateLimit<S>` deliberately does **not** implement `Clone`. But Axum requires `Clone`. Deadlock.

`BufferLayer` resolves this by putting a **channel** (like `tokio::sync::mpsc`) in front:

```text
                     ┌─────── channel ───────┐
Buffer handle A ──► │                        │
Buffer handle B ──► │  single RateLimit<S>   │──► Router
Buffer handle C ──► │  (one token bucket)    │
                     └───────────────────────┘
```

The `Buffer` handle is just a channel sender — **cheap to clone**, and all clones send to the same single `RateLimit` instance. One shared bucket, correct counting.

The `100` in `BufferLayer::new(100)` is the channel capacity — how many requests can queue in the channel before the buffer itself starts rejecting.

#### `HandleErrorLayer` → Fixes `Infallible`

Axum routes use `Infallible` as their error type. This is a Rust type that literally means **"this can never happen"** — Axum guarantees that all errors are converted into HTTP responses, never propagated as Rust errors.

But `LoadShedLayer` **can** fail. When it rejects a request (bucket empty), it returns a `BoxError` — a heap-allocated error. The types don't match:

```text
Axum expects:     Service<Request, Error = Infallible>     // "never errors"
LoadShed gives:   Service<Request, Error = BoxError>       // "can error with BoxError"
```

Rust won't let you put a `BoxError`-producing service where `Infallible` is expected. `HandleErrorLayer` bridges the gap — it wraps the `LoadShed` service and **catches** any `BoxError`, converting it into a normal HTTP response. After that, the error type is `Infallible` again — every possible error has been handled.

#### The Full Picture

```text
Request
  │
  ├─ HandleErrorLayer    Error type: Infallible ✅ (catches BoxError → HTTP 503)
  │    │
  │    ├─ BufferLayer       Clone: ✅ (channel sender is cloneable)
  │    │    │                Forwards errors from LoadShed back to HandleError
  │    │    │
  │    │    ├─ LoadShedLayer   Error type: BoxError (rejected → forwarded through Buffer → caught above)
  │    │    │    │
  │    │    │    ├─ RateLimitLayer   Clone: ❌ (but Buffer hides it)
  │    │    │    │    │               poll_ready: "not ready" when bucket empty
  │    │    │    │    └─ Router → Handler
```

Remove `BufferLayer` → **compile error**: `RateLimit<Route>: Clone` not satisfied.
Remove `HandleErrorLayer` → **compile error**: `Infallible: From<BoxError>` not satisfied.

Both are **type-system bridges**, not optional features. Rust's compiler won't let you skip them.

### Why Is LoadShed Necessary?

Without `LoadShedLayer`, Tower's `RateLimitLayer` uses **backpressure** — it holds excess requests in memory until tokens are available. This is fine for internal service-to-service calls where the caller cooperates, but bad for an HTTP API:

- Clients see very slow responses instead of a clear "you're rate limited" signal
- Memory grows as requests accumulate in the queue
- Health checks time out, triggering false alarms

`LoadShedLayer` converts backpressure into immediate rejection — the correct behavior for an HTTP API.

### The 503 vs 429 Problem

Our `HandleErrorLayer` returns `503 Service Unavailable` with a plain text body. This works, but it's not ideal:

- `503` means "server temporarily unavailable" — it's ambiguous (is it overloaded? deploying? crashed?)
- `429 Too Many Requests` is the correct status for rate limiting — clients and proxies recognize it
- The response body is plain text, not our structured JSON error format with `request_id`

We added `RustFlowError::RateLimited` in Step 3 for exactly this. You could change the `HandleErrorLayer` closure to return `429` with a JSON body, or write a response-mapping middleware. The exercises explore both approaches. For now, the `503` is functional — clients know to back off.

```bash
  -d '{"title": "Test"}' \
  http://localhost:3000/api/tasks
# → 201 (if within limit) or 503 (if exceeded)
```

### Health Check Is Also Rate-Limited

```bash
# Even health checks count against the limit!
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/health
```

This is a known limitation of applying rate limiting globally. In lesson 2.20, we'll reorganize so that health checks bypass the rate limiter. The exercises also address this.

### CORS Still Works

```bash
# Preflight + actual request
curl -s -D - -o /dev/null -X OPTIONS \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type, x-api-key" \
  http://localhost:3000/api/tasks
# → 200 with CORS headers (OPTIONS handled before rate limit)
```

## Choosing Rate Limit Values

The numbers `50 requests / 10 seconds` are deliberately low for testing — you want to see the limit kick in. Production values depend on your service's profile:

| Service Type | Typical Limit | Window |
|---|---|---|
| **Public API** | 100-1000 req/min | 60s |
| **Internal service** | 5000-10000 req/min | 60s |
| **Heavy computation** | 10-50 req/min | 60s |
| **Health check** | Unlimited | — |

### Burst vs Sustained Rate

Tower's `RateLimitLayer(50, 10s)` allows a burst of 50 requests instantly, then nothing for 10 seconds. This is a **fixed-window** approach. Alternatives:

- **Sliding window** — smoother, prevents bursts at window boundaries
- **Token bucket with refill** — tokens drip in gradually (e.g., 5 per second rather than 50 per 10 seconds)
- **Per-client limiting** — each API key gets its own bucket

Tower's built-in layer is fixed-window. For more sophisticated algorithms, consider `governor` or `tower-governor` crates — discussed in the exercises.

## Rate Limiting at Different Scopes

We applied the rate limiter to the entire application. You can also apply it at different granularities. The examples below are **conceptual** — in practice, each `RateLimitLayer` needs the full `ServiceBuilder` stack (`HandleErrorLayer` + `BufferLayer` + `LoadShedLayer` + `RateLimitLayer`) to compile:

```rust
// Global — all routes share one bucket (what we did)
let app = Router::new()
    .nest("/api/tasks", task_router)
    .nest("/api/projects", project_router)
    .layer(rate_limit_stack);  // ServiceBuilder with HandleError + Buffer + LoadShed + RateLimit

// Per-domain — each domain has its own bucket
// Each domain gets its own ServiceBuilder stack with different limits
let task_stack = ServiceBuilder::new()
    .layer(HandleErrorLayer::new(/* ... */))
    .layer(BufferLayer::new(100))
    .layer(LoadShedLayer::new())
    .layer(RateLimitLayer::new(50, Duration::from_secs(10)));

let project_stack = ServiceBuilder::new()
    .layer(HandleErrorLayer::new(/* ... */))
    .layer(BufferLayer::new(100))
    .layer(LoadShedLayer::new())
    .layer(RateLimitLayer::new(30, Duration::from_secs(10)));

Router::new()
    .nest("/api/tasks", task_router.layer(task_stack))
    .nest("/api/projects", project_router.layer(project_stack))
```

Each approach has trade-offs:

| Scope | Pros | Cons |
|---|---|---|
| **Global** | Simple, one config | Reads and writes compete for tokens |
| **Per-domain** | Independent limits per resource | More config, more buckets |
| **Per-endpoint-type** | Reads are unlimited, writes are controlled | Complex routing |

In lesson 2.20, we'll reorganize for a cleaner approach.

## Key Takeaways

1. **Rate limiting protects your service from abuse.** Without it, a single aggressive client can monopolize server resources. Even trusted internal clients can accidentally flood you with a misconfigured retry loop.

2. **Tower's `RateLimitLayer` is in-process and stateless.** It tracks tokens per time window inside the process — no Redis, no external state. Simple and sufficient for single-instance deployments.

3. **`LoadShedLayer` converts backpressure to rejection.** Without it, rate-limited requests wait indefinitely. With it, they get an immediate rejection. For HTTP APIs, immediate rejection is almost always what you want.

4. **`HandleErrorLayer` and `BufferLayer` are required for Axum compatibility.** `RateLimit` isn't `Clone` (Axum needs it) — `BufferLayer` fixes that. `LoadShed` produces `BoxError` (Axum expects `Infallible`) — `HandleErrorLayer` fixes that. Both are compile-time requirements, not optional enhancements.

5. **`ServiceBuilder` makes layer composition readable.** Layers are listed top-to-bottom in request order, instead of the confusing reverse-order of chained `.layer()` calls.

6. **Layer order matters critically.** CORS must be outermost (so preflights don't consume rate-limit tokens). `LoadShedLayer` must directly wrap `RateLimitLayer` (to see its `poll_ready` state). `BufferLayer` must wrap `LoadShed<RateLimit<...>>` (to make it `Clone`). `HandleErrorLayer` must be outermost in the `ServiceBuilder` (to catch `BoxError`). Getting this wrong causes compile errors or — worse — silent runtime bugs where rate limiting never triggers.

7. **Global rate limiting has limitations.** Health checks, static files, and API endpoints all share the same bucket. In 2.20, we'll reorganize the middleware stack to apply rate limiting only where it's needed.

## Exercises

1. **Custom 429 response** — Write a middleware that sits **outside** `HandleErrorLayer` in the `ServiceBuilder`. `HandleErrorLayer` converts `LoadShed`'s `BoxError` into a `503` HTTP response — your middleware sees that `503` and rewrites it to `429 Too Many Requests`. Write this as an `axum::middleware::from_fn` that calls `next.run()`, checks `response.status()`, and uses `*response.status_mut() = StatusCode::TOO_MANY_REQUESTS` to rewrite it. Note: it must be outside `HandleErrorLayer` because the `503` only exists as an HTTP response *after* `HandleErrorLayer` runs — between `LoadShed` and the router, the error is still a `BoxError`, not a status code.

2. **Exempt health checks** — Restructure the router so that `/health` is outside the rate-limited group. Apply rate limiting only to `/api/*` routes. Verify that spamming `/api/tasks` triggers the limit while `/health` always responds.

3. **Per-domain rate limits** — Apply different rate limits to tasks (50/10s), projects (30/10s), and enrichment (10/10s). Verify they're independent — exhausting the task limit doesn't affect project requests.

4. **Measure the burst pattern** — Write a script that sends requests at a steady 6/second rate (60 requests over 10 seconds). With a limit of 50/10s, how many succeed? Now compare with 50 requests sent in 1 second followed by 10 requests over 9 seconds. The burst pattern matters — explain why.

5. **Add `Retry-After` header** — When rate limited, the response should include a `Retry-After` header indicating how many seconds until the bucket refills. This is a standard HTTP header that well-behaved clients use to schedule retries.
    Run the following command after implementation:
```
    for i in $(seq 1 60); do
        response=$(curl -s -D - -o /dev/null -w "\n%{http_code}" http://localhost:3000/api/tasks)
        code=$(echo "$response" | tail -1)
        retry=$(echo "$response" | grep -i "retry-after" | tr -d '\r')
        echo "Request $i: $code $retry"
    done

```

6. **Explore `tower-governor`** — Install `tower-governor` and replace `RateLimitLayer` with `GovernorLayer`. Compare: per-client rate limiting (keyed by `x-api-key`), sliding window algorithm, and custom error responses. When would you choose one over the other?
