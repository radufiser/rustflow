# 2.14 - Simple Header-Based Authentication

## Overview

RustFlow's API is completely open — anyone can create, update, and delete tasks without any credentials. That's fine for development, but in production you need to control who can mutate data.

In this lesson we add **header-based API key authentication** to RustFlow's task mutation endpoints. Any request that creates, updates, or deletes a task must include a valid `x-api-key` header. Read operations remain open.

We implement this using a **custom Axum extractor** — the same pattern we used for `ValidatedJson` and `ValidatedQuery`. Each protected handler gains an additional parameter that checks the header before the handler body runs. If the key is missing or invalid, the request is rejected with a `401 Unauthorized` response before any state is touched.

This approach is intentionally **manual** — you'll add the extractor to every mutation handler one by one. By the end, you'll feel the repetition. That friction is the motivation for lesson 2.15, where we refactor the same logic into a reusable **Tower middleware layer** that protects routes automatically.

### Why This Matters in Enterprise Services

Every production API needs authentication. The patterns here scale from simple API keys to full OAuth2/JWT schemes:

- **API keys** — simplest model, used for service-to-service calls and internal tools
- **Bearer tokens (JWT)** — stateless authentication, common for user-facing APIs
- **mTLS** — mutual TLS for zero-trust service meshes

The extractor pattern works for all of these — you swap the validation logic inside the extractor, but the handler signature stays the same. The key architectural idea is: **authentication is an extraction concern, not a business logic concern**. Your handler shouldn't know or care _how_ the caller was authenticated — it just needs to know that they were.

## How It Works

The approach has three parts:

1. **A known API key** — for now, a hardcoded constant. In Section 5 (Configuration), we'll move this to environment variables and secrets management.

2. **A new error variant** — `RustFlowError::Unauthorized` maps to HTTP `401 Unauthorized` with a structured JSON body, consistent with every other error.

3. **A custom extractor** — `RequireApiKey` implements `FromRequestParts`, which means it only needs the request headers (not the body). Axum runs it _before_ body-consuming extractors like `ValidatedJson`, so an unauthenticated request never even parses the body — efficient and correct.

```text
Request arrives: POST /api/tasks  { "title": "..." }
  │
  ├── Step 1: RequireApiKey extractor runs (reads x-api-key header)
  │     ├── Missing or invalid → 401 Unauthorized (body never read)
  │     └── Valid → continue
  │
  ├── Step 2: State extractor runs (provides AppState)
  │
  ├── Step 3: ValidatedJson extractor runs (reads + validates body)
  │     ├── Invalid → 422 Unprocessable Entity
  │     └── Valid → continue
  │
  └── Step 4: Handler body runs (creates the task)
        └── 201 Created + task JSON
```

### Why `FromRequestParts` and Not `FromRequest`?

Axum has two extractor traits:

| Trait | What it accesses | Can coexist? | Examples |
|---|---|---|---|
| `FromRequestParts` | Headers, URI, method, extensions | Multiple per handler | `State`, `Path`, `Query`, `HeaderMap` |
| `FromRequest` | The full request (including body) | **Only one** per handler | `Json`, `ValidatedJson`, `String`, `Bytes` |

`FromRequest` consumes the request body — that's why you can only have one. `FromRequestParts` only needs the metadata, so many can coexist. Since API key validation only reads a header, `FromRequestParts` is the correct choice.

Axum processes extractors in parameter order, but `FromRequestParts` extractors always run before `FromRequest` extractors regardless of where you place them. Putting auth first is idiomatic — it signals "this is checked before anything else":

```rust
async fn create(
    _auth: RequireApiKey,                            // ← checked first (header only)
    State(state): State<AppState>,                   // ← checked second (state ref)
    ValidatedJson(payload): ValidatedJson<CreateTask>, // ← checked last (reads body)
) -> Result<(StatusCode, Json<Task>), RustFlowError> {
```

```rust name=crates/rustflow-server/src/errors.rs
// ── The unified error type ──────────────────────────────────

use axum::response::{IntoResponse, Response};
use axum::Json;
use reqwest::StatusCode;
use thiserror::Error;
use uuid::Uuid;

/// A single error type for all RustFlow handler errors.
///
/// Every variant maps to a specific HTTP status code and produces
/// a consistent JSON response body:
///
/// ```json
/// {
///   "error": "Short description",
///   "details": "More context about what went wrong"
/// }
/// ```
#[derive(Debug, Error)]
pub enum RustFlowError {
    #[error("Not found `{0}`")]
    NotFound(String),
    #[error("Bad request `{0}`")]
    BadRequest(String),
    #[error("Validation Failed `{0}`")]
    UnprocessableEntity(String),
    #[error("External Service Error `{0}`")]
    ExternalService(String),
    #[error("Internal Server Error `{0}`")]
    Internal(String),
    #[error("Conflict error `{0}`")]
    Conflict(String),
    #[error("Unauthorized `{0}`")]
    Unauthorized(String),
}

impl IntoResponse for RustFlowError {
    fn into_response(self) -> Response {
        let (status, error, details) = match self {
            Self::NotFound(msg) => (StatusCode::NOT_FOUND, "Not Found", msg),
            Self::BadRequest(msg) => (StatusCode::BAD_REQUEST, "Bad Request", msg),

            Self::UnprocessableEntity(msg) => {
                (StatusCode::UNPROCESSABLE_ENTITY, "Validation Failed", msg)
            }

            Self::ExternalService(msg) => (StatusCode::BAD_GATEWAY, "External Service Error", msg),
            Self::Internal(msg) => (
                StatusCode::INTERNAL_SERVER_ERROR,
                "Internal Server Error",
                msg,
            ),
            Self::Conflict(msg) => (StatusCode::CONFLICT, "Conflict error", msg),
            Self::Unauthorized(msg) => (StatusCode::UNAUTHORIZED, "Unauthorized", msg),
        };

        let body = serde_json::json!({
            "request_id": Uuid::new_v4().to_string(),
            "error": error,
            "details": details
        });

        (status, Json(body)).into_response()
    }
}
```

### What Changed

Two additions:

1. **New variant**: `Unauthorized(String)` with `#[error("Unauthorized `{0}`")]`
2. **New match arm**: `Self::Unauthorized(msg) => (StatusCode::UNAUTHORIZED, "Unauthorized", msg)`

The `401 Unauthorized` status code tells the client: "I know what you want, but you haven't proven you're allowed to do it." This is distinct from `403 Forbidden` (you proved who you are, but you're not allowed) — a distinction we'll revisit when we add role-based access control later.

## Step 3: Create the `RequireApiKey` Extractor

**Update** `crates/rustflow-server/src/extractors.rs` — add the `RequireApiKey` extractor at the end of the file.

The existing `ValidatedJson` and `ValidatedQuery` extractors remain untouched. We're adding a new extractor alongside them.

```rust name=crates/rustflow-server/src/extractors.rs (append to end of file)
// ── API Key Authentication ──────────────────────────────────

use crate::errors::RustFlowError;
use rustflow_common::API_KEY;

/// Extractor that validates the `x-api-key` header.
///
/// Add this to any handler that requires authentication:
///
/// ```rust
/// async fn create(
///     _auth: RequireApiKey,   // ← rejects before body is read
///     State(state): State<AppState>,
///     ValidatedJson(payload): ValidatedJson<CreateTask>,
/// ) -> Result<(StatusCode, Json<Task>), RustFlowError> {
/// ```
///
/// If the header is missing or invalid, the request is rejected with
/// 401 Unauthorized before any other extractor runs.
pub struct RequireApiKey;

impl<S> FromRequestParts<S> for RequireApiKey
where
    S: Send + Sync,
{
    type Rejection = RustFlowError;

    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, Self::Rejection> {
        let api_key = parts
            .headers
            .get("x-api-key")
            .and_then(|value| value.to_str().ok());

        match api_key {
            Some(key) if key == API_KEY => Ok(RequireApiKey),
            Some(_) => Err(RustFlowError::Unauthorized(
                "Invalid API key".into(),
            )),
            None => Err(RustFlowError::Unauthorized(
                "Missing x-api-key header".into(),
            )),
        }
    }
}
```

### How It Works, Step by Step

1. **`parts.headers.get("x-api-key")`** — looks up the header by name. Returns `Option<&HeaderValue>`. Header names are case-insensitive in HTTP, and Axum normalizes them to lowercase internally, so `x-api-key`, `X-Api-Key`, and `X-API-KEY` all match.

2. **`.and_then(|value| value.to_str().ok())`** — `HeaderValue` is raw bytes, not necessarily valid UTF-8. `.to_str()` attempts conversion; `.ok()` turns any error into `None`. A non-UTF-8 API key is effectively a missing key.

3. **The match** — three cases:
   - `Some(key) if key == API_KEY` — header present and matches → allow through
   - `Some(_)` — header present but wrong value → `401 "Invalid API key"`
   - `None` — header missing (or non-UTF-8) → `401 "Missing x-api-key header"`

4. **Return type `RustFlowError`** — because `RequireApiKey`'s `Rejection` type is `RustFlowError`, a failed extraction automatically triggers our unified error response. No special handling needed — Axum calls `IntoResponse` on the rejection, and our `RustFlowError::Unauthorized` variant produces the correct `401` + JSON body.

### Why a Unit Struct?

`RequireApiKey` has no fields — it's a **marker type**. Its only purpose is the side effect of validation during extraction. The handler receives it but never uses it:

```rust
async fn create(
    _auth: RequireApiKey,  // underscore prefix = "I don't use this value"
    ...
```

This is a common Axum pattern for extractors that validate or gate access without producing data. In 2.16, we'll evolve this into a struct that carries the authenticated identity — but for now, passing the gate is enough.

```rust name=crates/rustflow-server/src/extractors.rs
use axum::{
    Json,
    extract::{
        FromRequest, FromRequestParts, Query, Request, rejection::JsonRejection,
        rejection::QueryRejection,
    },
    http::StatusCode,
    http::request::Parts,
    response::{IntoResponse, Response},
};
use serde::de::DeserializeOwned;
use validator::Validate;

// ── Validated JSON Extractor ────────────────────────────────

/// This is a tuple struct -  a struct over an unnamed field.
/// Think of it as a wrapper around any type `T`.
///
pub struct ValidatedJson<T>(pub T);

/// What can go wrong?
pub enum ValidatedJsonError {
    // the JSON itself is broken
    JsonError(JsonRejection),
    // the JSON is valid but breaks out rules
    ValidationError(validator::ValidationErrors),
}

impl IntoResponse for ValidatedJsonError {
    fn into_response(self) -> Response {
        match self {
            Self::JsonError(rejection) => {
                let body = serde_json::json!({
                    "error": "Invalid JSON",
                    "details": rejection.body_text(),
                });
                (rejection.status(), Json(body)).into_response()
            }
            Self::ValidationError(errors) => {
                // ... builds a JSON body like:
                // { "error": "Validation failed", "details": { "title": ["Title must be..."] } }
                // ... and returns it with status 422
                let body = serde_json::json!({
                    "error": "Validation failed",
                    "details": errors.field_errors().iter().map(|(field, errs)| {
                        (field.to_string(), errs.iter().filter_map(|e| {
                            e.message.as_ref().map(|m| m.to_string())
                        }).collect::<Vec<_>>())
                    }).collect::<std::collections::HashMap<_, _>>()
                });
                (StatusCode::UNPROCESSABLE_ENTITY, Json(body)).into_response()
            }
        }
    }
}

impl<T, S> FromRequest<S> for ValidatedJson<T>
where
    T: DeserializeOwned + Validate,
    S: Send + Sync, // S (server state) must be thread safe
{
    type Rejection = ValidatedJsonError; // What error type we return on failure

    async fn from_request(req: Request, state: &S) -> Result<Self, Self::Rejection> {
        // Step 1: Try to parse the JSON body into type T
        let Json(value) = Json::<T>::from_request(req, state)
            .await
            .map_err(ValidatedJsonError::JsonError)?;
        // Step 2: Run the validation rules on the parsed values
        value
            .validate()
            .map_err(ValidatedJsonError::ValidationError)?;

        // Step 3: both passed.
        Ok(ValidatedJson(value))
    }
}

## Step 4: Protect Task Mutation Handlers

**Update** `crates/rustflow-server/src/routes/tasks.rs` — add `_auth: RequireApiKey` as the first parameter to every handler that mutates data.

```rust name=crates/rustflow-server/src/routes/tasks.rs
use std::fmt::format;
use crate::errors::RustFlowError;
use crate::extractors::{RequireApiKey, ValidatedJson, ValidatedQuery};
use crate::state::AppState;
use axum::extract::{Path, State};
use axum::http::StatusCode;
use axum::routing::{get, patch};
use axum::{Json, Router};
use rustflow_common::{CreateTask, Task, TaskFilter, TaskStatus};

/// GET /tasks?status=pending&priority=high
///
/// No auth required — reading tasks is a public operation.
async fn list(
    State(state): State<AppState>,
    ValidatedQuery(filter): ValidatedQuery<TaskFilter>,
) -> Json<Vec<Task>> {
    let state = state.tasks.0.read().await;

    let filtered: Vec<Task> = state
        .tasks
        .iter()
        .filter(|task| filter.status.as_ref().map_or(true, |s| &task.status == s))
        .filter(|task| filter.status.as_ref().map_or(true, |s| &task.status == s))
        .filter(|task| {
            filter.search.as_ref().map_or(true, |s| {
                task.title.contains(s) || task.description.as_ref().map_or(false, |d| d.contains(s))
            })
        })
        .cloned()
        .collect();

    Json(filtered)
}

/// GET /tasks/:id
///
/// No auth required — reading a single task is a public operation.
async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Task>, RustFlowError> {
    let store = state.tasks.0.read().await;

    store
        .tasks
        .iter()
        .find(|task| task.id == id)
        .cloned()
        .map(Json)
        .ok_or(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
}

/// POST /tasks
///
/// Requires `x-api-key` header — creating tasks is a protected operation.
///
/// Note the extractor order:
///   1. `RequireApiKey` — validates the API key (FromRequestParts, header only)
///   2. `State`         — provides access to AppState (FromRequestParts)
///   3. `ValidatedJson` — reads and validates the body (FromRequest, consumes body)
///
/// If auth fails, the body is never read.
async fn create(
    _auth: RequireApiKey,
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    // Acquire a write lock - exclusive access, blocks all other readers/writers
    let mut store = state.tasks.0.write().await;

    if store.tasks.iter().any(|x| payload.title == x.title) {
        return Err(RustFlowError::Conflict(format!("Task with title {} already exists", payload.title)));
    }

    let task = Task {
        id: store.next_id,
        title: payload.title,
        description: payload.description,
        priority: payload.priority,
        status: TaskStatus::Pending,
    };

    store.next_id += 1;
    store.tasks.push(task.clone());

    Ok((StatusCode::CREATED, Json(task)))
}

/// DELETE /tasks/:id
///
/// Requires `x-api-key` header.
async fn delete(
    _auth: RequireApiKey,
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, RustFlowError> {
    let mut store = state.tasks.0.write().await;
    let len_before = store.tasks.len();

    store.tasks.retain(|task| task.id != id);

    if store.tasks.len() < len_before {
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(RustFlowError::NotFound(
            format!("Task with id {id} does not exist"),
        ))
    }
}

/// PUT /tasks/:id
///
/// Requires `x-api-key` header.
async fn update(
    _auth: RequireApiKey,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<Json<Task>, RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if let Some(task) = store.tasks.iter_mut().find(|task| task.id == id) {
        task.title = payload.title;
        task.description = payload.description;
        task.priority = payload.priority;
        Ok(Json(task.clone()))
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
    }
}

/// PATCH /tasks/:id/status
///
/// Requires `x-api-key` header.
async fn change_status(
    _auth: RequireApiKey,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    Json(payload): Json<TaskStatus>,
) -> Result<Json<Task>, RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if let Some(task) = store.tasks.iter_mut().find(|task| task.id == id) {
        task.status = payload;
        Ok(Json(task.clone()))
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
    }
}

pub fn router() -> Router<AppState> {
    Router::new()
        .route("/", get(list).post(create))
        .route("/{id}", get(get_one).put(update).delete(delete))
        .route("/{id}/status", patch(change_status))
}

### The Repetition Problem

Look at what we just did: we added `_auth: RequireApiKey` to four handlers in one file. If we wanted to protect project and user mutations too, that's another four or five handlers. Every new protected endpoint needs the same boilerplate.

This is fine for a small API, but it doesn't scale:
- Easy to forget on new handlers (silent security hole)
- Clutters every handler signature
- No single place to see "what's protected"

This is exactly what middleware solves — and that's lesson 2.15.

### Why the Router Didn't Change

Notice that `pub fn router()` at the bottom is identical to before. The routes and HTTP methods haven't changed. The auth check lives entirely within the handler signatures. This is a property of the **extractor approach**: protection is per-handler, not per-route.

In 2.15, we'll flip this — auth will be applied at the **router level** using `.layer()`, which means routes are protected by position in the router tree, not by what's in the handler signature.

## Key Takeaways

1. **Authentication is an extraction concern.** In Axum, custom extractors are the natural place for request-level validation like auth. The handler body only runs if all extractors succeed — separating "can you do this?" from "do this."

2. **`FromRequestParts` is for metadata, `FromRequest` is for body.** API key validation only needs a header, so `FromRequestParts` is the right trait. This ensures auth is checked before the body is even read — both secure and efficient.

3. **Extractor ordering matters.** `FromRequestParts` extractors run before `FromRequest` extractors. Putting `RequireApiKey` first is idiomatic and ensures unauthenticated requests are rejected early, before body parsing or state access.

4. **The unified error type pays off.** Because `RequireApiKey` returns `RustFlowError::Unauthorized` as its rejection, auth failures produce the same structured JSON response as every other error. No special error handling code was needed — just a new variant and a match arm.

5. **The extractor approach doesn't scale.** We added `_auth: RequireApiKey` to four handlers in one file. For a larger API with dozens of mutation endpoints across multiple modules, this becomes error-prone — easy to forget on new handlers, creating silent security holes. This motivates the middleware refactor in 2.15.

6. **Hardcoded keys are a stepping stone.** The `API_KEY` constant is fine for learning. In Section 5 (Configuration), we'll load the key from environment variables. The authentication _mechanism_ is correct regardless of where the key comes from.
