# 2.13 - Serving Static Content with Tower

## Overview

RustFlow is a full-featured API — but right now the only way to see tasks is by curling JSON endpoints. In this lesson we add a **static HTML dashboard** served at `/`, replacing the plain-text "RustFlow is running!" response with a real page that pulls live data from the API we've already built.

This introduces **`tower-http`**, the companion crate to Tower that provides pre-built middleware and services for common HTTP tasks. We'll use its `ServeFile` service — a single-file static asset server — to understand how Tower services compose with Axum.

By the end of this lesson, visiting `http://localhost:3000/` in a browser will show a live dashboard with task counts and a task table, all powered by the existing `/api/tasks` endpoint.

### Why This Matters in Enterprise Services

Serving static content from your Rust service is surprisingly common in production:

- **Admin dashboards** — lightweight UIs for internal monitoring (exactly what we're building)
- **Health/status pages** — human-readable views of service health
- **Embedded documentation** — serving OpenAPI/Swagger UI directly (we'll do this in Section 4)
- **Single-page apps** — small internal tools that don't warrant a separate frontend deployment

In a microservices architecture, having a self-contained service that includes its own minimal UI reduces deployment complexity — one container, one binary, one port.

## The Tower Service Model

Before we use `tower-http`, let's understand why it exists.

Axum is built on [Tower](https://github.com/tower-rs/tower), a framework for composable network services. Tower defines a single core trait:

```rust
pub trait Service<Request> {
    type Response;
    type Error;
    type Future: Future<Output = Result<Self::Response, Self::Error>>;

    fn poll_ready(&mut self, cx: &mut Context<'_>) -> Poll<Result<(), Self::Error>>;
    fn call(&mut self, req: Request) -> Self::Future;
}
```

Every Axum handler, every middleware layer, and every router — they're all Tower `Service` implementations under the hood. This uniformity is what makes the entire stack composable.

### Services vs Layers

Tower has two core abstractions, and the distinction matters:

A **Service** is anything that takes a request and produces a response. Your handler function is a Service. A static file server is a Service. An entire Axum `Router` is a Service.

A **Layer** is a *factory* that wraps one Service inside another to add behavior. It has one method:

```rust
pub trait Layer<S> {
    type Service;

    fn layer(&self, inner: S) -> Self::Service;
}
```

Think of a Layer as a blueprint for wrapping. It takes an existing Service (`S`) and returns a new, decorated Service that adds behavior before and/or after the inner one runs:

```text
Layer::layer(inner_service)  →  new_service
                                  │
                                  ├── do something before (e.g., check auth header)
                                  ├── call inner_service
                                  └── do something after  (e.g., add response headers)
```

The relationship is straightforward:

| Concept | What it is | Example |
|---|---|---|
| **Service** | Does the work — takes request, returns response | `ServeFile`, your handler, the router itself |
| **Layer** | Wraps a Service to add behavior | `CorsLayer`, `TraceLayer`, `CompressionLayer` |

A Layer *produces* a Service. The produced Service calls the inner Service. This is how middleware works in Tower — it's just Services wrapping Services, all the way down:

```text
┌─────────────────────────────────────────────────┐
│  Your Axum Router                               │
│  ┌────────────────────────────────────────────┐  │
│  │  Layer: rate limiting                      │  │  ← Service wrapping a Service
│  │  ┌──────────────────────────────────────┐  │  │
│  │  │  Layer: auth                         │  │  │  ← Service wrapping a Service
│  │  │  ┌────────────────────────────────┐  │  │  │
│  │  │  │  Your handler fn              │  │  │  │  ← Service (leaf)
│  │  │  └────────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

In Axum you apply layers with `.layer()`:

```rust
Router::new()
    .route("/tasks", get(list_tasks))
    .layer(CorsLayer::permissive())       // ← Layer wraps the router's Service
    .layer(TraceLayer::new_for_http())     // ← another Layer wraps that
```

Each `.layer()` call wraps everything above it. The outermost layer runs first on the way *in* and last on the way *out* — like Russian nesting dolls.

**In this lesson we're using a Service (`ServeFile`), not a Layer.** `ServeFile` doesn't wrap another service — it *is* the service. It handles the request directly by reading a file from disk. We'll use our first Layer in 2.15 (auth middleware) and many more after that (CORS, tracing, compression, rate limiting).

### `tower-http` — Pre-Built Services and Layers

**`tower-http`** extends the Tower model with pre-built Services and Layers for common HTTP tasks. Think of it as the standard library for Tower-based HTTP services.

| Kind | Examples from `tower-http` | Feature flag |
|---|---|---|
| **Services** | `ServeFile`, `ServeDir` | `fs` |
| **Layers** | `CorsLayer`, `TraceLayer`, `CompressionLayer`, `SetResponseHeaderLayer` | `cors`, `trace`, `compression`, etc. |

We'll use Services today and start adding Layers in upcoming sections.

### `ServeFile` vs `ServeDir`

`tower-http` offers two static-serving services:

| Service | Use case | Example |
|---|---|---|
| `ServeFile` | Serve a **single file** at a specific route | Dashboard at `/`, favicon at `/favicon.ico` |
| `ServeDir` | Serve an **entire directory** with path-based lookup | `/static/css/app.css`, `/static/js/main.js` |

We're using `ServeFile` because we have one dashboard page. When we add more static assets (CSS, JS, images), we'll switch to `ServeDir`.

### `route` vs `route_service`

Axum's `Router` has two methods for mounting endpoints:

```rust
// .route() — takes a handler function, Axum wraps it into a Service for you
.route("/health", get(health_handler))

// .route_service() — takes a raw Tower Service directly
.route_service("/", ServeFile::new("static/index.html"))
```

`.route()` requires a handler (an async function with extractors). `.route_service()` accepts any type that implements Tower's `Service` trait. Since `ServeFile` is already a `Service` — not a handler function — we use `.route_service()`.

```text
.route("/path", handler)           → handler function → Axum wraps → Service
.route_service("/path", service)   → Service directly (no wrapping needed)
```

### Design Decisions for the Dashboard

**Why a single HTML file?**

For an internal admin dashboard, a single self-contained file is ideal. No build tools, no asset pipeline, no CDN configuration. The file is tiny (< 5 KB), loads instantly, and is trivially cacheable. In later sections (WebSockets — Section 7), we'll add real-time updates to this page.

**Why does it call `/api/tasks`?**

The dashboard demonstrates a key service pattern: **the same server that serves the API also serves the UI that consumes it.** There are no CORS issues because the HTML and the API share the same origin. This is the simplest deployment topology — one binary, one port, everything works.

```text
Browser
  │
  ├── GET /                    → ServeFile → index.html
  │
  └── GET /api/tasks           → Axum handler → JSON
       (called by JavaScript
        inside index.html)
```

**Why `setInterval(load, 5000)`?**

Polling is simple and works. In Section 7 (WebSockets) we'll replace this with a persistent connection that pushes updates in real time. This polling approach is a useful baseline to contrast against.

```rust name=crates/rustflow-server/src/main.rs
mod errors;
mod extractors;
mod routes;
mod state;

use crate::state::AppState;
use axum::Router;
use rustflow_common::{APP_NAME, APP_VERSION};
use tokio::net::TcpListener;
use tower_http::services::ServeFile;

#[tokio::main]
async fn main() {
    let state: AppState = AppState::new();

    // Build the application router
    let app = Router::new()
        // Serve the static dashboard at GET /
        .route_service("/", ServeFile::new("crates/rustflow-server/static/index.html"))
        // Health & config — merged at root level (no prefix)
        .merge(routes::health::router())
        // Domain routes — nested under /api/*
        .nest("/api/tasks", routes::tasks::router())
        .nest("/api/projects", routes::projects::router())
        .nest("/api/users", routes::users::router())
        // Enrichment — combines local data with external API calls
        .nest("/api/enrichment", routes::enrichment::router())
        // Provide state to ALL routes (merged and nested)
        .with_state(state);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr)
        .await
        .expect("Failed to bind to address");

    println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

    axum::serve(listener, app).await.expect("Server error");
}
```

### The File Path Question

Notice the path `"crates/rustflow-server/static/index.html"` — this is **relative to the working directory where `cargo run` is executed**, which is typically the workspace root. This works for development.

```text
Workspace root (where you run `cargo run`)
└── crates/
    └── rustflow-server/
        └── static/
            └── index.html    ← ServeFile resolves relative to CWD
```

In production, you'd handle this differently:

```rust
// Option 1: Environment variable
ServeFile::new(std::env::var("STATIC_DIR").unwrap_or("static".into()))

// Option 2: Embed the file in the binary at compile time (no disk dependency)
// (We'll cover this in Section 10 when we containerize)

// Option 3: Resolve relative to the executable
let exe_dir = std::env::current_exe().unwrap().parent().unwrap().to_owned();
ServeFile::new(exe_dir.join("static/index.html"))
```

For now, the relative path is fine — it works with `cargo run -p rustflow-server` from the workspace root.

### Why `ServeFile` Instead of `include_str!`?

You might be tempted to embed the HTML directly:

```rust
// ❌ Works but misses the point
async fn root() -> Html<&'static str> {
    Html(include_str!("../static/index.html"))
}
```

This compiles the HTML into the binary — changes require recompilation. More importantly, it **doesn't teach the Tower service model** that the rest of the course builds on. `ServeFile` introduces:

- `route_service()` — mounting raw Tower services
- Automatic `Content-Type` detection (based on file extension)
- Automatic `Last-Modified` and conditional `304 Not Modified` responses
- The `tower-http` crate that we'll use extensively for CORS, tracing, and compression

### What `ServeFile` Does Under the Hood

`ServeFile` is more than a file reader. It handles several HTTP concerns automatically:

```text
GET / HTTP/1.1
Host: localhost:3000

ServeFile processing:
  1. Open the file from disk
  2. Detect Content-Type from extension (.html → text/html)
  3. Read file metadata (size, last modified time)
  4. Check If-Modified-Since / If-None-Match headers
     → 304 Not Modified if the file hasn't changed
  5. Set response headers:
     Content-Type: text/html
     Content-Length: 4827
     Last-Modified: Tue, 18 Mar 2026 10:00:00 GMT
  6. Stream the file body
```

This is production-grade static file serving — you get caching semantics for free.

```bash
# Verify conditional caching works (304 Not Modified)
#
# ⚠️  HTTP uses CRLF (\r\n) line endings, so header values extracted by
#     grep/cut will contain a trailing \r.  If you pass that invisible
#     character back in If-Modified-Since, the server sees a malformed
#     date and returns 400 Bad Request.  Piping through `tr -d '\r'`
#     strips the carriage return so the date is clean.

# First request — get the Last-Modified header (strip trailing \r)
LAST_MOD=$(curl -sI http://localhost:3000/ \
  | grep -i last-modified | cut -d' ' -f2- | tr -d '\r')

# Second request — send If-Modified-Since
curl -s -o /dev/null -w "%{http_code}" \
  -H "If-Modified-Since: $LAST_MOD" http://localhost:3000/
# → 304  (file hasn't changed, so ServeFile returns Not Modified)
```

> **Common pitfall — invisible `\r` in shell pipelines.**
> HTTP/1.1 terminates every header line with `\r\n` (RFC 9110 §5.2).
> Tools like `curl -I` faithfully preserve those bytes, but Unix shells
> and utilities expect plain `\n`.  The trailing `\r` is invisible in
> most terminals yet corrupts any value you try to reuse.  Always strip
> it with `tr -d '\r'` (or `sed 's/\r$//'`) when capturing HTTP headers
> in shell variables.  You can reveal the hidden bytes with `cat -v`
> (they show up as `^M`).

## Key Takeaways

1. **`tower-http` is the utility belt for Tower-based services** — it provides pre-built middleware and services for static files, CORS, tracing, compression, and more. We'll use it throughout the rest of the course.

2. **`.route_service()` mounts raw Tower services** — unlike `.route()` which takes handler functions, `.route_service()` accepts any type that implements the Tower `Service` trait. This is how you integrate non-handler services like `ServeFile` into your Axum router.

3. **`ServeFile` is production-grade** — it doesn't just read a file and return bytes. It handles `Content-Type` detection, `Content-Length`, `Last-Modified` headers, and conditional `304 Not Modified` responses automatically. Free caching semantics.

4. **Same-origin simplicity** — serving the dashboard and the API from the same server means no CORS issues, no proxy configuration, and no separate deployment. The JavaScript in `index.html` calls `/api/tasks` as a relative URL and it just works.

5. **File paths are relative to the working directory** — `ServeFile::new("crates/rustflow-server/static/index.html")` resolves from wherever `cargo run` is executed (typically the workspace root). In production, you'd use environment variables or embed assets in the binary.

6. **Tower has two building blocks: Services and Layers** — a Service does work (handles a request), a Layer wraps a Service to add behavior (middleware). `ServeFile` is a Service; the auth, CORS, and tracing middleware we'll add later are Layers. Everything in Axum — handlers, routers, middleware stacks — reduces to these two concepts.
