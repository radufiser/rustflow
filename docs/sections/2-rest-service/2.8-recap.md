### Extractors (2.3–2.4)

Extractors are Axum's mechanism for pulling typed data out of incoming HTTP requests. Instead of manually parsing headers, query strings, or JSON bodies, you declare what you need as **handler function arguments** — and Axum does the rest at compile time.

```text
Handler arguments = Extractors

async fn my_handler(
    State(state): State<AppState>,              ← FromRequestParts (doesn't consume body)
    Path(id): Path<u64>,                        ← FromRequestParts
    ValidatedQuery(filter): ValidatedQuery<T>,  ← FromRequestParts (with validation)
    ValidatedJson(body): ValidatedJson<T>,      ← FromRequest (consumes body — must be LAST)
) -> impl IntoResponse
```

#### The Two Traits: `FromRequestParts` vs `FromRequest`

Axum splits extraction into two traits based on whether the extractor needs to consume the request body:

| Trait | Consumes body? | Max per handler | Examples |
|---|---|---|---|
| `FromRequestParts<S>` | No — only reads headers, URI, extensions | Unlimited | `State`, `Path`, `Query`, `ValidatedQuery`, `HeaderMap` |
| `FromRequest<S>` | Yes — takes ownership of the body stream | **One** | `Json`, `ValidatedJson`, `String`, `Bytes`, `Request` |

The body is a streaming byte buffer — once consumed, it's gone. That's why only **one** `FromRequest` extractor is allowed per handler, and it **must be the last argument**.

```text
Request
  ├── Parts (headers, URI, method, extensions)  ← shared, read by FromRequestParts
  └── Body  (streaming bytes)                   ← consumed once by FromRequest
```

#### Built-in Extractors We've Used

| Extractor | Trait | Source | Example Input | Extracted Type |
|---|---|---|---|---|
| `Path<T>` | `FromRequestParts` | URL path segments | `/tasks/42` | `Path(42u64)` |
| `Query<T>` | `FromRequestParts` | URL query string | `?status=done` | `Query(TaskFilter { status: Some(Done), .. })` |
| `Json<T>` | `FromRequest` | Request body (JSON) | `{"title":"..."}` | `Json(CreateTask { title: "...", .. })` |
| `State<S>` | `FromRequestParts` | App state (injected by `.with_state()`) | — | `State(AppState { .. })` |

#### Custom Extractors: `ValidatedJson<T>` and `ValidatedQuery<T>`

Built-in extractors like `Json<T>` and `Query<T>` handle deserialization but **not** business rule validation. We built two custom extractors that add a validation step using the `validator` crate:

```text
ValidatedJson<T>  (implements FromRequest)
  Step 1: Deserialize JSON body → T           (reuses Json<T> internally)
  Step 2: Run validator rules → T.validate()  (checks #[validate(...)] attributes)
  Step 3: Return ValidatedJson(T) on success

ValidatedQuery<T>  (implements FromRequestParts)
  Step 1: Deserialize query string → T        (reuses Query<T> internally)
  Step 2: Run validator rules → T.validate()  (checks #[validate(...)] attributes)
  Step 3: Return ValidatedQuery(T) on success
```

**How the validation attributes work on our types:**

```rust
#[derive(Deserialize, Validate)]
pub struct CreateTask {
    #[validate(length(min = 1, max = 100, message = "Title must be between 1 and 100 characters"))]
    pub title: String,

    #[validate(length(max = 500, message = "Description cannot exceed 500 characters"))]
    pub description: Option<String>,

    #[serde(default)]           // ← defaults to Priority::Medium if omitted
    pub priority: Priority,

    #[validate(custom(function = "validate_due_date"))]
    pub due_date: Option<String>,   // ← custom validator checks YYYY-MM-DD format
}
```

#### Error Handling: What Happens When Extraction Fails

Each custom extractor defines its own error enum that implements `IntoResponse`, producing structured JSON errors with the appropriate HTTP status code:

```text
Request: POST /api/tasks  body: { "title": "" }

  1. ValidatedJson deserializes body      → Ok(CreateTask { title: "", .. })
  2. ValidatedJson runs .validate()       → Err(ValidationErrors)
  3. ValidatedJsonError::ValidationError  → 422 Unprocessable Entity

Response:
  {
    "error": "Validation failed",
    "details": { "title": ["Title must be between 1 and 100 characters"] }
  }
```

```text
Request: POST /api/tasks  body: { not valid json

  1. ValidatedJson tries to deserialize   → Err(JsonRejection)
  2. ValidatedJsonError::JsonError        → 400 Bad Request (status from rejection)

Response:
  {
    "error": "Invalid JSON",
    "details": "Failed to parse the request body as JSON: ..."
  }
```

This two-phase error design means clients always get a clear, machine-readable error response — never a raw Axum panic or opaque 500.

#### Ordering Rules

```text
✅ Valid ordering:
async fn handler(
    State(state): State<AppState>,         // FromRequestParts — any position
    Path(id): Path<u64>,                   // FromRequestParts — any position
    ValidatedQuery(q): ValidatedQuery<T>,  // FromRequestParts — any position
    ValidatedJson(body): ValidatedJson<T>, // FromRequest — MUST be last
) -> impl IntoResponse

❌ Compile error:
async fn handler(
    ValidatedJson(body): ValidatedJson<T>, // FromRequest — body consumed here!
    Path(id): Path<u64>,                   // Too late — can't read parts after body
) -> impl IntoResponse
```

**Rules summary:**
- Multiple `FromRequestParts` extractors in any order: ✅
- Only **one** `FromRequest` extractor (body consumer): ✅
- Body consumer must be the **last** argument: ✅
- Use `ValidatedJson<T>` for JSON payloads that need validation: ✅
- Use `ValidatedQuery<T>` for query params that need validation: ✅
- Type mismatches (e.g., wrong state type) are caught at **compile time**: ✅

### State Evolution (2.5–2.7)

```text
2.5: Arc<AppState>              → Read-only shared state
2.6: Arc<RwLock<AppState>>      → Mutable shared state (single lock)
2.7: AppState {                 → Split state (independent locks)
       tasks: TaskState(Arc<RwLock<TaskStore>>),
       projects: ProjectState(Arc<RwLock<ProjectStore>>),
       config: AppConfig,       → No lock (immutable)
     }
```

**Choosing the right approach:**

| Scenario | Use |
|---|---|
| Data never changes after startup | `Arc<T>` or just `T: Clone` (e.g., `AppConfig`) |
| Data changes, low contention | `Arc<RwLock<T>>` |
| Data changes, high contention | Split into independent `Arc<RwLock<T>>` per domain |
| Very high write contention | Consider `dashmap` or `tokio::sync::Mutex` |

### Tower Layers

Everything in Axum flows through Tower layers:

```text
Request
  │
  ├──► Layer 1 (State injection)     ← .with_state() — we've used this
  ├──► Layer 2 (Logging)             ← coming in Section 3
  ├──► Layer 3 (Auth)                ← coming in Section 2.17
  ├──► Layer 4 (Rate limiting)       ← coming in Section 2.22
  │
  ▼
Handler
```

`.with_state(state)` is syntactic sugar for adding a state injection layer. In upcoming sections, we'll add our own custom layers.

### Current Architecture

```text
                    ┌─────────────────────────────────┐
                    │            AppState              │
                    │    (Clone — cheap per request)    │
                    ├───────────┬───────────┬──────────┤
                    │ TaskState │ ProjState │ AppConfig │
                    │Arc<RwLock>│Arc<RwLock> │ (no lock)│
                    └───────────┴───────────┴──────────┘
                          │           │          │
  GET  /tasks ───────► read lock  (untouched) (untouched)
  POST /tasks ───────► write lock (untouched) (untouched)
  PUT  /tasks/:id ───► write lock (untouched) (untouched)
  PATCH /tasks/:id ──► write lock (untouched) (untouched)
  GET  /projects ────► (untouched) read lock  (untouched)
  POST /projects ────► (untouched) write lock (untouched)
  GET  /config ──────► (untouched) (untouched) direct read
```

**Key insight:** Because each domain has its own lock, creating a task doesn't block listing projects. This is the split-state pattern in action.

### Current Route Map

After 2.7, RustFlow serves these endpoints:

```text
GET    /                        → liveness check
GET    /health                  → service health (JSON)
GET    /config                  → app configuration (JSON)
GET    /tasks                   → list tasks (filterable by status, priority, search)
POST   /tasks                   → create a task (validated)
GET    /tasks/:id               → get a task
PUT    /tasks/:id               → update a task (validated)
DELETE /tasks/:id               → delete a task
PATCH  /tasks/:id/status        → change task status
GET    /projects                → list projects
POST   /projects                → create a project (validated)
GET    /projects/:id            → get a project
```
