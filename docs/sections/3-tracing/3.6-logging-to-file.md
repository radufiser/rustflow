# 3.6 — Logging to File

## Overview

Stop the server. Now answer this question: what happened at 3:47 AM last Tuesday?

You can't. Every log line RustFlow has ever produced went to stdout — and stdout is gone the moment the process exits. Restart the server, and the entire history vanishes. Pipe it to a file manually with `cargo run 2>&1 | tee server.log`? That works until someone forgets, or the pipe breaks, or the file grows to 50 GB because nobody set up rotation.

This is fine for development. It's unacceptable in production:

- **Post-mortem debugging** — A customer reports an error that happened hours ago. Without persistent logs, you're guessing.
- **Compliance and audit** — Regulated industries require log retention. "We printed it to stdout and it's gone" doesn't satisfy auditors.
- **Incident investigation** — When a cascade failure takes down the service at 3 AM, the on-call engineer needs to read what happened *before* the crash — not just what happens after the restart.
- **Log aggregation** — Tools like ELK, Datadog, and Grafana Loki can ingest log files. They can't ingest a terminal that no longer exists.

The solution: write logs to a **rotated file** alongside stdout. Every event goes to both destinations simultaneously. The file persists across restarts, and daily rotation prevents unbounded growth.

### Why Not Just Redirect stdout?

You *could* redirect stdout to a file at the OS level:

```bash
cargo run -p rustflow-server > /var/log/rustflow/server.log 2>&1
```

But this has problems:

1. **No rotation** — The file grows forever. You'd need an external tool like `logrotate` to manage it.
2. **No dual output** — You lose the terminal. During development, you want both: see logs in the terminal *and* persist them to a file.
3. **Blocking I/O** — Writing to a file from the async runtime blocks the thread. If the disk is slow (network-mounted storage, full disk), your request handling stalls.
4. **No graceful degradation** — If the log directory doesn't exist, the process fails to start. You want the server to keep running even if file logging can't be set up.

`tracing-appender` solves all four problems.

### The `tracing-appender` Crate

`tracing-appender` is part of the `tracing` ecosystem. It provides:

| Feature | What It Does |
|---|---|
| `rolling::daily()` | Creates a file writer that rotates to a new file every day |
| `rolling::hourly()` | Rotates every hour (for high-volume services) |
| `rolling::never()` | Single file, no rotation |
| `NonBlocking` | Wraps any writer in a background thread — writes never block the caller |
| `WorkerGuard` | A handle that keeps the background writer alive; dropping it flushes and stops the writer |

The key insight: `NonBlocking` moves all file I/O to a dedicated background thread. Your async handlers call `tracing::info!(...)`, the event is formatted and sent to a channel, and the background thread writes it to disk. The handler never waits for disk I/O.

### The Architectural Shift: From `fmt().init()` to `registry().with().init()`

This lesson introduces a fundamental change to how we build the tracing subscriber. Until now, `init_tracing()` used the convenience builder:

```rust
// 3.1–3.5: Single-layer convenience builder
tracing_subscriber::fmt()
    .with_env_filter(env_filter)
    .init();
```

This creates a single `fmt` layer writing to stdout. It's simple, but it can only have **one output destination**. We need two: stdout *and* a file.

The solution is the **layered subscriber pattern** using `tracing_subscriber::registry()`:

```rust
// 3.6+: Layered subscriber with multiple outputs
use tracing_subscriber::prelude::*;

tracing_subscriber::registry()
    .with(env_filter)
    .with(stdout_layer)    // fmt layer → stdout
    .with(file_layer)      // fmt layer → file (optional)
    .init();
```

A `Registry` is a subscriber that holds multiple **layers**. Each layer independently processes every event. When you call `tracing::info!("task created")`, the registry fans the event out to all layers — stdout sees it, the file sees it, and (in later lessons) the JSON layer and OpenTelemetry exporter see it too.

This is the same pattern as Axum's middleware stack: composable layers that each do one thing. The registry is the backbone that connects them.

```text
tracing::info!("task created")
    │
    ▼
┌──────────────────────┐
│      Registry         │
│                       │
│  ┌─────────────────┐  │
│  │   EnvFilter      │  │  ← filters events by level/target
│  └────────┬────────┘  │
│           │            │
│  ┌────────▼────────┐  │
│  │  fmt Layer       │  │  ← formats + writes to stdout
│  │  (stdout)        │  │
│  └────────┬────────┘  │
│           │            │
│  ┌────────▼────────┐  │
│  │  fmt Layer       │  │  ← formats + writes to log file
│  │  (file)          │  │
│  └─────────────────┘  │
└──────────────────────┘
```

### The `WorkerGuard` Lifetime Pattern

This is the most important concept in this lesson — and the most common source of bugs.

When you create a `NonBlocking` writer, it returns two things:

```rust
let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);
//   ^^^^^^^^^^^^  ^^^^^
//   the writer    the guard
```

The `non_blocking` writer sends events to a channel. A background thread reads from the channel and writes to disk. The `guard` is a `WorkerGuard` — when it's dropped, the background thread is signaled to flush remaining events and stop.

**If the guard is dropped too early, buffered events are lost.** This is the critical rule:

```rust
// ❌ WRONG — guard is dropped immediately, file logging silently stops
fn init_tracing() {
    let (non_blocking, _guard) = tracing_appender::non_blocking(file_appender);
    // _guard is dropped here at the end of init_tracing()
    // The background writer thread stops
    // All subsequent file writes are silently lost
}

// ✅ CORRECT — guard is returned and held by main()
fn init_tracing() -> Option<WorkerGuard> {
    let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);
    // ... set up subscriber ...
    Some(guard)  // caller must hold this
}

// In main():
let _guard = init_tracing(config);
// _guard lives until main() returns → all events are flushed on shutdown
```

The `_guard` variable in `main()` uses the underscore prefix convention: "I know this looks unused, but dropping it has side effects." Rust won't warn about unused variables that start with `_`. The guard sits there, doing nothing visible, but its existence keeps the background writer alive for the entire application lifetime.

## Step 2: Introduce `TracingConfig`

Until now, `init_tracing()` took no arguments — it had a hardcoded default filter and always wrote to stdout. With file logging, we need configuration: *where* should the log files go? Should file logging be enabled at all?

This is where `TracingConfig` comes in — a struct that drives the tracing setup.

**Add to** `crates/rustflow-common/src/tracing.rs`:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;

/// Configuration for the tracing subsystem.
///
/// Controls which layers are active in the subscriber pipeline.
/// Passed to [`init_tracing()`] at application startup.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    ///
    /// - `Some(path)` — enable file logging to this directory (e.g., `"logs"`)
    /// - `None` — stdout only, no file logging
    ///
    /// If the directory doesn't exist or isn't writable, file logging is
    /// skipped with a warning — the server continues operating with stdout only.
    pub log_directory: Option<PathBuf>,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
        }
    }
}
```

### Why a Struct Instead of Function Parameters?

We could add a parameter to `init_tracing()`:

```rust
// Option A: parameter
pub fn init_tracing(log_dir: Option<PathBuf>) -> Option<WorkerGuard> { ... }

// Option B: config struct
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> { ... }
```

The struct is better because it's **extensible without breaking changes**. In lesson 3.7, we'll add `json_output: bool`. In 3.8, `otlp_endpoint: Option<String>`. Each addition is a new field on the struct — the function signature stays the same. With individual parameters, every new feature would change the function signature and break all callers.

This is the same pattern as Axum's `CorsLayer::new().allow_origin(...)` builder — configuration grows without API churn.

### The `Default` Implementation

`TracingConfig::default()` creates a config with no file logging — identical to the behavior from lessons 3.1–3.5. This means existing code that doesn't need file logging can use:

```rust
init_tracing(TracingConfig::default());
```

And get exactly the same behavior as before. No regression, no surprises.

### Re-Exporting `TracingConfig`

The `TracingConfig` struct needs to be accessible from `rustflow-server`. Since `tracing.rs` is already a public module (`pub mod tracing` in `lib.rs`), the struct is available as `rustflow_common::tracing::TracingConfig`. No additional re-exports needed.


## Step 3: The `NonBlocking` Writer and `WorkerGuard`

Before we refactor `init_tracing()`, let's understand the `NonBlocking` wrapper in detail — it's the key to safe file logging in an async application.

### Why Blocking I/O Is Dangerous in Async Rust

Tokio's async runtime uses a small pool of threads (typically equal to the number of CPU cores). When a handler calls `tracing::info!(...)`, the subscriber formats the event and writes it somewhere. If "somewhere" is a file, that's a `write()` system call — and system calls can block:

- The disk is busy (other processes writing, SSD garbage collection)
- The filesystem is network-mounted (NFS, EFS) and the network is slow
- The disk is full and the OS is trying to free space
- The file is on a spinning disk and the head needs to seek

While the thread is blocked on `write()`, it can't process other async tasks. With 4 Tokio worker threads and 4 concurrent file writes that each block for 10ms, your entire server stalls for 10ms — no requests are processed.

```text
Without NonBlocking:
  Handler → tracing::info!() → fmt layer → write() to file → BLOCKS THREAD
                                                               ↑
                                                    Other tasks wait

With NonBlocking:
  Handler → tracing::info!() → fmt layer → send to channel → RETURNS IMMEDIATELY
                                                    ↓
                                          Background thread → write() to file
                                          (not a Tokio thread — can block safely)
```

### How `NonBlocking` Works

`tracing_appender::non_blocking()` takes any `Write` implementor and wraps it:

```rust
let file_appender = tracing_appender::rolling::daily("logs", "rustflow.log");
let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);
```

Internally:

1. Creates a bounded channel (ring buffer)
2. Spawns a dedicated OS thread (not a Tokio task — a real `std::thread`)
3. The `non_blocking` writer sends formatted events to the channel
4. The background thread reads from the channel and calls `write()` on the file appender
5. The `guard` (`WorkerGuard`) holds a handle to the background thread

The channel is bounded — if the background thread falls behind (slow disk), the channel fills up and events are dropped rather than blocking the caller. This is the right tradeoff: losing a few log lines is better than stalling request handling.

### The `WorkerGuard` Contract

The `WorkerGuard` has one job: when dropped, it signals the background thread to:

1. Stop accepting new events
2. Flush all remaining events in the channel to disk
3. Close the file
4. Join the background thread (wait for it to finish)

This flush-on-drop behavior is why the guard must live for the entire application lifetime. If it's dropped early:

```rust
// ❌ Guard dropped at end of function — background thread stops
fn setup_logging() {
    let (writer, guard) = tracing_appender::non_blocking(appender);
    // ... configure subscriber with writer ...
    // guard dropped here — background thread stops
    // All subsequent events sent to the channel are lost
}
```

The subscriber still *accepts* events (it doesn't know the writer is dead), but the `NonBlocking` writer's sends go to a closed channel. Events vanish silently. No error, no panic — just silent data loss.

```rust
// ✅ Guard returned to caller — lives as long as caller holds it
fn setup_logging() -> WorkerGuard {
    let (writer, guard) = tracing_appender::non_blocking(appender);
    // ... configure subscriber with writer ...
    guard  // caller is responsible for keeping this alive
}
```

### The `_guard` Convention

In `main()`, the guard is bound to a variable that's never read:

```rust
let _guard = init_tracing(config);
// _guard is never used — but dropping it stops file logging
// The underscore prefix tells Rust (and other developers): "this is intentional"
```

Without the underscore, Rust would warn: `unused variable: guard`. The `_` prefix suppresses the warning and communicates intent: "I'm holding this for its drop behavior, not its value."

This is a common Rust pattern for RAII (Resource Acquisition Is Initialization) guards:

```rust
let _lock = mutex.lock().await;     // hold the lock until scope ends
let _guard = span.enter();          // stay in the span until scope ends
let _guard = init_tracing(config);  // keep the file writer alive until main() ends
```


## Step 4: Refactor `init_tracing()` — The Layered Registry Pattern

Now the big change. We're replacing the single-layer `fmt().init()` with a multi-layer `registry().with().init()`.

**Update** `crates/rustflow-common/src/tracing.rs` — the complete refactored file:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::EnvFilter;
use tracing_subscriber::prelude::*;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
const DEFAULT_LOG_FILTER: &str =
    "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

/// Configuration for the tracing subsystem.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    ///
    /// - `Some(path)` — enable file logging to this directory
    /// - `None` — stdout only, no file logging
    ///
    /// If the directory doesn't exist or isn't writable, file logging is
    /// skipped with a warning.
    pub log_directory: Option<PathBuf>,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
        }
    }
}

/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — human-readable `fmt` output to stdout (always active)
/// - **file layer** — human-readable `fmt` output to a daily-rotated log file
///   (only when `config.log_directory` is `Some`)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime. Dropping the guard stops the background file writer and may lose
/// buffered events. Bind it in `main()`:
///
/// ```rust,ignore
/// let _guard = init_tracing(config);
/// // _guard lives until main() returns
/// ```
///
/// # Graceful Degradation
///
/// If `log_directory` is set but the directory cannot be created or written to,
/// a warning is printed to stderr and the server continues with stdout-only logging.
///
/// # Panics
///
/// Panics if called more than once (the global subscriber can only be set once).
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer (always active) ────────────────────────
    let stdout_layer = tracing_subscriber::fmt::layer()
        .with_target(true)
        .with_level(true);

    // ── file layer (optional) ───────────────────────────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_layer(dir) {
            Some((layer, guard)) => (Some(layer), Some(guard)),
            None => (None, None),
        },
        None => (None, None),
    };

    // ── assemble the registry ───────────────────────────────
    tracing_subscriber::registry()
        .with(env_filter)
        .with(stdout_layer)
        .with(file_layer)
        .init();

    guard
}

/// Attempts to build a file logging layer with daily rotation.
///
/// Returns `None` if the directory doesn't exist and can't be created,
/// or if the appender can't write to it. Prints a warning to stderr
/// (tracing isn't initialized yet at this point, so we use eprintln!).
fn try_build_file_layer(
    dir: &PathBuf,
) -> Option<(
    tracing_subscriber::fmt::Layer<
        tracing_subscriber::Registry,
        tracing_subscriber::fmt::format::DefaultFields,
        tracing_subscriber::fmt::format::Format,
        tracing_appender::non_blocking::NonBlocking,
    >,
    WorkerGuard,
)> {
    // Attempt to create the directory if it doesn't exist
    if let Err(e) = std::fs::create_dir_all(dir) {
        eprintln!(
            "WARNING: Cannot create log directory '{}': {}. File logging disabled.",
            dir.display(),
            e
        );
        return None;
    }

    // Verify the directory is writable by creating and removing a temp file
    let test_path = dir.join(".rustflow-log-test");
    match std::fs::write(&test_path, b"test") {
        Ok(_) => {
            let _ = std::fs::remove_file(&test_path);
        }
        Err(e) => {
            eprintln!(
                "WARNING: Log directory '{}' is not writable: {}. File logging disabled.",
                dir.display(),
                e
            );
            return None;
        }
    }

    // Create the daily-rotating file appender
    let file_appender = tracing_appender::rolling::daily(dir, "rustflow.log");

    // Wrap in NonBlocking — moves I/O to a background thread
    let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);

    // Build the fmt layer targeting the non-blocking file writer
    let file_layer = tracing_subscriber::fmt::layer()
        .with_target(true)
        .with_level(true)
        .with_ansi(false)  // no ANSI color codes in log files
        .with_writer(non_blocking);

    Some((file_layer, guard))
}
```

### Anatomy of the Refactored `init_tracing()`

Let's walk through every piece of this function.

#### The Signature Change

```rust
// Before (3.2–3.5):
pub fn init_tracing() { ... }

// After (3.6):
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> { ... }
```

Two changes:
1. **Takes `TracingConfig`** — the caller controls whether file logging is enabled
2. **Returns `Option<WorkerGuard>`** — `Some` when file logging is active, `None` when stdout-only

The return type is `Option` because file logging might not be configured (`log_directory: None`) or might fail gracefully (directory not writable). In both cases, the caller gets `None` and the server runs fine with stdout-only logging.

#### The `EnvFilter` — Unchanged

```rust
let env_filter = EnvFilter::try_from_default_env()
    .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));
```

Identical to 3.2. The filter logic doesn't change — it still reads `RUST_LOG` with a compiled-in fallback. The filter is applied to the *registry*, which means it affects all layers equally. Both stdout and file output respect the same filter directives.

#### The stdout Layer

```rust
let stdout_layer = tracing_subscriber::fmt::layer()
    .with_target(true)
    .with_level(true);
```

This replaces the old `tracing_subscriber::fmt()` builder. Instead of creating a complete subscriber, `fmt::layer()` creates a **layer** — a component that can be added to a registry. The layer formats events and writes them to stdout (the default writer).

`.with_target(true)` and `.with_level(true)` are the same defaults that `fmt::init()` used — we're just being explicit now. The output format is identical to what you've been seeing since 3.1.

#### The File Layer (Optional)

```rust
let (file_layer, guard) = match config.log_directory {
    Some(ref dir) => match try_build_file_layer(dir) {
        Some((layer, guard)) => (Some(layer), Some(guard)),
        None => (None, None),
    },
    None => (None, None),
};
```

This is a two-level match:
1. **Is file logging configured?** (`config.log_directory` is `Some` or `None`)
2. **Did the file layer build successfully?** (`try_build_file_layer` returns `Some` or `None`)

If either check fails, both `file_layer` and `guard` are `None`. The server continues with stdout-only logging.

#### Assembling the Registry

```rust
tracing_subscriber::registry()
    .with(env_filter)
    .with(stdout_layer)
    .with(file_layer)
    .init();
```

This is the new pattern. Let's compare:

```rust
// Before (3.2): Single-layer convenience builder
tracing_subscriber::fmt()
    .with_env_filter(env_filter)
    .init();

// After (3.6): Multi-layer registry
tracing_subscriber::registry()
    .with(env_filter)
    .with(stdout_layer)
    .with(file_layer)    // Option<Layer> — None means "skip this layer"
    .init();
```

The `registry()` function creates an empty subscriber. Each `.with()` call adds a layer. The order matters for filters (the `EnvFilter` must come first so it filters events before they reach the formatting layers), but the formatting layers (stdout and file) are independent — they each receive every event that passes the filter.

#### The `Option<Layer>` Trick

Notice that `file_layer` is an `Option`. The `tracing-subscriber` crate implements the `Layer` trait for `Option<L> where L: Layer` — meaning you can pass `None` as a layer and it's simply skipped. No conditional logic needed:

```rust
// This works even when file_layer is None:
registry()
    .with(stdout_layer)
    .with(file_layer)  // None → no-op, as if this line didn't exist
    .init();
```

This is elegant — the registry doesn't need to know whether file logging is active. It just processes whatever layers it's given.

#### The `prelude::*` Import

```rust
use tracing_subscriber::prelude::*;
```

This import is required for the `.with()` method on the registry. The `Layer` trait's `.with()` extension method is defined in the prelude. Without it, you'll get a compile error:

```text
error[E0599]: no method named `with` found for struct `Registry`
```

This is a common gotcha when switching from `fmt().init()` to `registry().with().init()`.


## Step 5: The `try_build_file_layer()` Helper

The helper function handles the messy details of setting up file logging — directory creation, write permission checks, and the `NonBlocking` wrapper.

### Directory Creation

```rust
if let Err(e) = std::fs::create_dir_all(dir) {
    eprintln!(
        "WARNING: Cannot create log directory '{}': {}. File logging disabled.",
        dir.display(),
        e
    );
    return None;
}
```

`create_dir_all` creates the directory and all parent directories (like `mkdir -p`). If it already exists, it succeeds silently. If it fails (permission denied, read-only filesystem), we print a warning and return `None`.

Why `eprintln!` instead of `tracing::warn!`? Because the tracing subscriber hasn't been initialized yet — we're still *building* it. Any `tracing` macro called before `.init()` is a no-op. `eprintln!` writes directly to stderr, which is always available.

### Write Permission Check

```rust
let test_path = dir.join(".rustflow-log-test");
match std::fs::write(&test_path, b"test") {
    Ok(_) => {
        let _ = std::fs::remove_file(&test_path);
    }
    Err(e) => {
        eprintln!(
            "WARNING: Log directory '{}' is not writable: {}. File logging disabled.",
            dir.display(),
            e
        );
        return None;
    }
}
```

The directory might exist but not be writable (wrong permissions, mounted read-only). We verify by writing a small test file and immediately removing it. If the write fails, we skip file logging.

This is a pragmatic check — it catches the most common failure mode (permission issues) without being overly complex. In a production system, you might also check available disk space, but that's overkill for a learning project.

### The Rolling File Appender

```rust
let file_appender = tracing_appender::rolling::daily(dir, "rustflow.log");
```

`rolling::daily()` creates a file appender that:
- Writes to the specified directory
- Uses the prefix `"rustflow.log"` for file names
- Rotates to a new file every day at midnight (UTC)
- Names files with the date: `rustflow.log.2026-01-15`, `rustflow.log.2026-01-16`, etc.

Old files are **not** automatically deleted — you'd use an external tool (logrotate, a cron job, or a Kubernetes sidecar) to clean up old files in production. For development, daily rotation means you won't accidentally fill your disk during a long debugging session.

### The `NonBlocking` Wrapper

```rust
let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);
```

Wraps the file appender in a `NonBlocking` writer. Returns the writer (for the fmt layer) and the guard (for the caller to hold).

### The File `fmt` Layer

```rust
let file_layer = tracing_subscriber::fmt::layer()
    .with_target(true)
    .with_level(true)
    .with_ansi(false)
    .with_writer(non_blocking);
```

Almost identical to the stdout layer, with two differences:

1. **`.with_ansi(false)`** — disables ANSI color codes. Colors are great in a terminal but produce garbage in log files (`\x1b[32mINFO\x1b[0m` instead of `INFO`). Always disable ANSI for file output.

2. **`.with_writer(non_blocking)`** — redirects output from stdout (the default) to the `NonBlocking` file writer. Every event formatted by this layer goes to the background thread → the log file.

The stdout layer doesn't need `.with_writer()` because stdout is the default. The file layer explicitly overrides the writer.

### Before (3.5)

#[tokio::main]

```

### After (3.6)

```rust
use rustflow_common::tracing::{TracingConfig, init_tracing};
use std::path::PathBuf;

#[tokio::main]
async fn main() {
    // ── Initialize tracing with file logging ────────────────
    let tracing_config = TracingConfig {
        log_directory: Some(PathBuf::from("logs")),
    };

    let _guard = init_tracing(tracing_config);
    // _guard keeps the file writer alive — DO NOT drop it early.
    // When main() returns, the guard is dropped, flushing all buffered events.

    let state: AppState = AppState::new();
    // ... rest of main unchanged ...
}
```

### What Changed

Three things:

1. **`TracingConfig` with `log_directory`** — tells the tracing module to write logs to the `logs/` directory (relative to the working directory — typically the workspace root when running with `cargo run`).

2. **`let _guard = init_tracing(tracing_config)`** — captures the `Option<WorkerGuard>`. The `_guard` variable lives until `main()` returns, keeping the background file writer alive for the entire server lifetime.

3. **The import** — `TracingConfig` and `init_tracing` are now imported from `rustflow_common::tracing`.

### Why `PathBuf::from("logs")`?

The `"logs"` directory is relative to the current working directory. When you run `cargo run -p rustflow-server` from the workspace root, the working directory is the workspace root — so logs go to `rustflow/logs/`.

In production, you'd use an absolute path like `/var/log/rustflow` or read the path from an environment variable or config file. For development, a relative `logs/` directory is convenient — it's in the project root, easy to find, and `.gitignore`-able.

### Don't Forget `.gitignore`

Add `logs/` to your `.gitignore` so log files don't get committed:

```text
# .gitignore
/target
/logs
```

Log files contain runtime data — timestamps, request IDs, potentially sensitive information. They don't belong in version control.

### The Guard Lifetime Visualized

```text
main() starts
  │
  ├── let _guard = init_tracing(config);
  │     │
  │     ├── Creates NonBlocking writer
  │     ├── Spawns background writer thread
  │     ├── Installs subscriber with stdout + file layers
  │     └── Returns WorkerGuard
  │
  ├── let state = AppState::new();
  ├── let app = build_app(&state);
  ├── axum::serve(listener, app)
  │       .with_graceful_shutdown(shutdown_signal())
  │       .await;                                      ← server runs here
  │
  ├── tracing::info!("shut down gracefully");
  │
  └── _guard dropped here (end of main)
        │
        ├── Signals background thread to stop
        ├── Flushes remaining events to disk
        ├── Closes the log file
        └── Joins the background thread
```

The guard lives from tracing initialization until the very end of `main()` — after the server has drained all connections and logged its final shutdown message. Every event during the server's lifetime is captured.

### What If You Forget the Guard?

```rust
// ❌ Common mistake — guard is immediately dropped
init_tracing(tracing_config);  // return value ignored!
```

Rust will warn you:

```text
warning: unused `Option` that must be used
  --> src/main.rs:10:5
   |
10 |     init_tracing(tracing_config);
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: this `Option` may be a `WorkerGuard` that must be held
```

If you ignore this warning, file logging silently stops working. The subscriber still formats events and sends them to the `NonBlocking` writer, but the writer's channel is closed (the background thread exited when the guard was dropped). Events are silently lost.

This is why the doc comment on `init_tracing()` emphasizes the guard — it's the most common pitfall with `tracing-appender`.


## Step 7: Understanding Dual Output

With the layered registry, every event flows through both layers simultaneously:

```text
tracing::info!("task created")

┌──────────────────────────────────────────────┐
│                  Registry                     │
│                                               │
│  ┌───────────────┐                            │
│  │   EnvFilter    │  ← "Does this pass?"      │
│  │                │     INFO ≥ DEBUG? Yes ✓    │
│  └───────┬───────┘                            │
│          │                                    │
│    ┌─────┴─────┐                              │
│    │           │                              │
│    ▼           ▼                              │
│  ┌───────┐  ┌───────────┐                     │

│  │ layer │  │   layer    │                     │

If you need per-layer filtering, you'd add a separate `EnvFilter` to each layer — but that's an advanced pattern we don't need yet.

### Daily Rotation

At midnight UTC, `tracing-appender` automatically switches to a new file:

```text

├── rustflow.log.2026-01-15    ← today's logs (active)

No configuration needed — `rolling::daily()` handles the rotation. The old file is closed, a new file is opened with the new date suffix. Events are never split across files — each event goes entirely to one file.

The file name pattern is `{prefix}.{date}`:

```


## Step 8: Graceful Degradation in Action

Let's trace through the failure scenarios to understand how the server behaves when file logging can't be set up.

### Scenario 1: Directory Doesn't Exist (But Can Be Created)

```rust
let config = TracingConfig {
    log_directory: Some(PathBuf::from("logs")),
};
```

If `logs/` doesn't exist, `create_dir_all("logs")` creates it. File logging works normally. This is the happy path — the first time you run the server, the directory is created automatically.

### Scenario 2: Directory Can't Be Created (Permission Denied)

```rust
let config = TracingConfig {
    log_directory: Some(PathBuf::from("/root/logs")),  // no permission
};
```

`create_dir_all("/root/logs")` fails with `Permission denied`. Output:

```text
WARNING: Cannot create log directory '/root/logs': Permission denied (os error 13). File logging disabled.
2026-01-15T10:30:00.123456Z  INFO rustflow_server: rustflow v0.1.0 listening on 0.0.0.0:3000
```

The warning goes to stderr (via `eprintln!`). The server starts normally with stdout-only logging. No panic, no crash.

### Scenario 3: Directory Exists But Not Writable

```rust
let config = TracingConfig {
    log_directory: Some(PathBuf::from("/etc")),  // exists but not writable
};
```

`create_dir_all("/etc")` succeeds (directory already exists). But the write test fails:

```text
WARNING: Log directory '/etc' is not writable: Permission denied (os error 13). File logging disabled.
2026-01-15T10:30:00.123456Z  INFO rustflow_server: rustflow v0.1.0 listening on 0.0.0.0:3000
```

Same result: warning + stdout-only logging.

### Scenario 4: No File Logging Configured

```rust
let config = TracingConfig {
    log_directory: None,
};
// or equivalently:
let config = TracingConfig::default();
```

No warning, no file layer. The registry has only the stdout layer. This is identical to the behavior from 3.1–3.5.

### Why Graceful Degradation Matters

In production, the log directory might become unavailable after deployment:
- A mounted volume is disconnected
- Disk fills up and the filesystem goes read-only
- A container's ephemeral storage is reclaimed

If the server crashed because it couldn't write logs, you'd have a cascading failure: the thing that's supposed to help you debug problems (logging) causes the problem. Graceful degradation means the server keeps serving requests — you just lose file logging until the issue is resolved.

The warning message tells the operator what happened and why. They can fix the directory permissions and restart the server to re-enable file logging.

## The Complete `tracing.rs` After 3.6

For reference, here's the full file after all changes:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::EnvFilter;
use tracing_subscriber::prelude::*;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
const DEFAULT_LOG_FILTER: &str =
    "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

/// Configuration for the tracing subsystem.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    ///
    /// - `Some(path)` — enable file logging to this directory
    /// - `None` — stdout only, no file logging
    pub log_directory: Option<PathBuf>,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
        }
    }
}

/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — human-readable `fmt` output to stdout (always active)
/// - **file layer** — human-readable `fmt` output to a daily-rotated log file
///   (only when `config.log_directory` is `Some`)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime. Dropping the guard stops the background file writer and may lose
/// buffered events.
///
/// # Graceful Degradation
///
/// If `log_directory` is set but the directory cannot be created or written to,
/// a warning is printed to stderr and the server continues with stdout-only logging.
///
/// # Panics
///
/// Panics if called more than once.
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer (always active) ────────────────────────
    let stdout_layer = tracing_subscriber::fmt::layer()
        .with_target(true)
        .with_level(true);

    // ── file layer (optional) ───────────────────────────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_layer(dir) {
            Some((layer, guard)) => (Some(layer), Some(guard)),
            None => (None, None),
        },
        None => (None, None),
    };

    // ── assemble the registry ───────────────────────────────
    tracing_subscriber::registry()
        .with(env_filter)
        .with(stdout_layer)
        .with(file_layer)
        .init();

    guard
}

/// Attempts to build a file logging layer with daily rotation.
///
/// Returns `None` if the directory can't be created or isn't writable.
fn try_build_file_layer(
    dir: &PathBuf,
) -> Option<(
    tracing_subscriber::fmt::Layer<
        tracing_subscriber::Registry,
        tracing_subscriber::fmt::format::DefaultFields,
        tracing_subscriber::fmt::format::Format,
        tracing_appender::non_blocking::NonBlocking,
    >,
    WorkerGuard,
)> {
    if let Err(e) = std::fs::create_dir_all(dir) {
        eprintln!(
            "WARNING: Cannot create log directory '{}': {}. File logging disabled.",
            dir.display(),
            e
        );
        return None;
    }

    let test_path = dir.join(".rustflow-log-test");
    match std::fs::write(&test_path, b"test") {
        Ok(_) => {
            let _ = std::fs::remove_file(&test_path);
        }
        Err(e) => {
            eprintln!(
                "WARNING: Log directory '{}' is not writable: {}. File logging disabled.",
                dir.display(),
                e
            );
            return None;
        }
    }

    let file_appender = tracing_appender::rolling::daily(dir, "rustflow.log");
    let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);

    let file_layer = tracing_subscriber::fmt::layer()
        .with_target(true)
        .with_level(true)
        .with_ansi(false)
        .with_writer(non_blocking);

    Some((file_layer, guard))
}
```

## Key Takeaways

1. **The `WorkerGuard` must live for the application lifetime.** This is the single most important rule when using `tracing-appender`. If the guard is dropped, the background writer stops and buffered events are lost. Bind it to `_guard` in `main()` and never move it.

2. **`NonBlocking` moves file I/O off the async runtime.** Writing to disk can block — and blocking a Tokio worker thread stalls all async tasks on that thread. `NonBlocking` sends events to a channel and a dedicated OS thread handles the writes. Your handlers never wait for disk I/O.

3. **The `registry().with().init()` pattern replaces `fmt().init()`.** This is the transition to composable, multi-layer subscribers. Each `.with()` adds a layer — filter, stdout, file, and (in later lessons) JSON and OpenTelemetry. The registry fans events to all layers.

4. **`Option<Layer>` is a no-op layer.** When file logging is disabled or fails, the file layer is `None`. The registry accepts `Option<L>` and simply skips `None` layers. No conditional branching needed in the assembly code.

5. **Graceful degradation keeps the server running.** If the log directory doesn't exist or isn't writable, the server starts with stdout-only logging and a warning. Logging should never be the reason a server fails to start.

6. **`.with_ansi(false)` is essential for file output.** ANSI color codes are terminal escape sequences. In a log file, they're garbage characters that make the file harder to read and parse. Always disable ANSI for non-terminal writers.

7. **Daily rotation prevents unbounded file growth.** `rolling::daily()` creates a new file each day. Old files accumulate but are bounded by time — you can clean them up with a cron job or log management tool. Without rotation, a single file would grow until the disk is full.

8. **`TracingConfig` makes the tracing module extensible.** Adding new features (JSON output in 3.7, OpenTelemetry in 3.8) means adding new fields to the struct — the function signature doesn't change. Callers that don't need new features use `TracingConfig::default()` and get the same behavior as before.

6. **Add per-layer filtering** — The current setup uses a single `EnvFilter` for both stdout and file. What if you want `DEBUG` on stdout but only `INFO` in the file? Research how to add a separate `EnvFilter` to each layer using `.with_filter()` instead of adding the filter to the registry. This is an advanced pattern that `tracing-subscriber` supports via the `filter::Targets` or per-layer `EnvFilter`.
