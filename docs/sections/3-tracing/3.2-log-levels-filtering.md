# 3.2 — Log Levels & Filtering

## Overview

Run the server from lesson 3.1 and send a few requests:

```bash
cargo run -p rustflow-server
```

```bash
curl http://localhost:3000/api/tasks
```

Look at the terminal. Mixed in with your application output, you'll see lines like these:

```text
2026-01-15T10:30:00.123456Z  INFO rustflow_server: rustflow v0.1.0 listening on 0.0.0.0:3000
2026-01-15T10:30:01.456789Z DEBUG hyper_util::client::legacy::pool: pooling idle connection for ("http", localhost:3000)
2026-01-15T10:30:01.457000Z TRACE tower::buffer::worker: processing request
2026-01-15T10:30:01.457100Z DEBUG hyper::proto::h1::io: flushed 245 bytes
2026-01-15T10:30:01.457200Z  INFO rustflow_server::routes::middleware: GET /api/tasks
2026-01-15T10:30:01.457300Z DEBUG rustflow_server::routes::middleware: Took 42μs
2026-01-15T10:30:01.457400Z TRACE tokio::runtime::scheduler: tick complete
```

Three of those lines are yours. The rest are internal noise from `hyper`, `tower`, and `tokio`. With `fmt::init()`, the subscriber shows **everything** — every `TRACE`-level event from every crate in the dependency tree. In a real application with dozens of dependencies, your output drowns in a flood of internal diagnostics.

This is the problem `EnvFilter` solves.

### What Is `EnvFilter`?

`EnvFilter` is a **directive-based filter** from `tracing-subscriber` that controls which events reach the subscriber's formatting layer. Instead of a single global log level, it lets you set different levels for different crates and modules:

```text
rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn
│                      │                      │                 │
│                      │                      │                 └── global default: warn
│                      │                      └── tower_http at debug
│                      └── rustflow_common at debug
└── rustflow_server at debug
```

This single string says:
- Show `DEBUG` and above for `rustflow_server` (our server crate)
- Show `DEBUG` and above for `rustflow_common` (our shared crate)
- Show `DEBUG` and above for `tower_http` (HTTP tracing — we'll use this in 3.3)
- Show `WARN` and above for **everything else** (hyper, tokio, tower internals, reqwest, etc.)

The result: your application output is clean and focused. Dependency noise only appears when something goes wrong (at `WARN` or `ERROR` level).

### Directive Syntax

An `EnvFilter` string is a comma-separated list of **directives**. Each directive has the form:

```text
target=level
```

| Component | Meaning | Examples |
|---|---|---|
| `target` | A crate name or module path | `rustflow_server`, `hyper`, `tower::buffer` |
| `level` | The minimum severity to show | `trace`, `debug`, `info`, `warn`, `error`, `off` |

A bare level without a target sets the **global default** — the fallback for any crate not explicitly listed:

```text
rustflow_server=debug,warn
│                      │
│                      └── global default: everything else at warn
└── rustflow_server at debug
```

Important: crate names in directives use **underscores**, not hyphens. The crate `rustflow-server` becomes `rustflow_server` in filter directives (Rust converts hyphens to underscores in module paths).

### The `RUST_LOG` Environment Variable

`EnvFilter` reads its directives from the `RUST_LOG` environment variable. This is a Rust ecosystem convention — virtually every Rust application that uses `tracing` or `log` respects `RUST_LOG`:

```bash
# Show only warnings and errors from everything
RUST_LOG=warn cargo run -p rustflow-server

# Show debug output from your crates, info from everything else
RUST_LOG=rustflow_server=debug,rustflow_common=debug,info cargo run -p rustflow-server

# Show trace-level output from a specific module
RUST_LOG=rustflow_server::routes::tasks=trace cargo run -p rustflow-server
```

The power of `RUST_LOG` is that it's a **runtime override**. You don't recompile to change log verbosity — you just set an environment variable. This is essential in production: when debugging an issue, you can restart the service with `RUST_LOG=debug` to get detailed output, then switch back to `RUST_LOG=warn` when the issue is resolved.

### The Problem with `RUST_LOG` Alone

If `RUST_LOG` is not set, `EnvFilter::from_default_env()` falls back to showing everything — which is the noisy behavior we're trying to fix. We need a **compiled-in default** that provides a good developer experience out of the box, with `RUST_LOG` available as an override when needed.

The pattern:

```text
1. Is RUST_LOG set?
   ├── Yes → use RUST_LOG directives (developer/operator override)
   └── No  → use compiled-in default (sensible dev experience)
```

## Step 1: Update `init_tracing()` with `EnvFilter`

**Update** `crates/rustflow-common/src/tracing.rs`:

```rust name=crates/rustflow-common/src/tracing.rs
use tracing_subscriber::EnvFilter;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
///
/// - `rustflow_server=debug`  — our server crate at debug level
/// - `rustflow_common=debug`  — our shared crate at debug level
/// - `tower_http=debug`       — HTTP tracing (TraceLayer, added in 3.3) at debug level
/// - `warn`                   — everything else (hyper, tokio, tower, reqwest) at warn only
const DEFAULT_LOG_FILTER: &str = "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

/// Initialize the global tracing subscriber with environment-based filtering.
///
/// Reads the `RUST_LOG` environment variable for filter directives. If `RUST_LOG`
/// is not set, applies [`DEFAULT_LOG_FILTER`] as a sensible default that shows
/// debug output for RustFlow crates while silencing noisy dependencies.
///
/// # Examples
///
/// ```bash
/// # Use the compiled-in default (no RUST_LOG set):
/// cargo run -p rustflow-server
///
/// # Override at runtime:
/// RUST_LOG=info cargo run -p rustflow-server
/// RUST_LOG=rustflow_server=trace,warn cargo run -p rustflow-server
/// ```
///
/// # Panics
///
/// Panics if called more than once (the global subscriber can only be set once).
pub fn init_tracing() {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    tracing_subscriber::fmt()
        .with_env_filter(env_filter)
        .init();
}
```

### Anatomy of the Changes

Let's break down every line.

#### The Default Filter Constant

```rust
const DEFAULT_LOG_FILTER: &str = "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";
```

This is the filter that applies when `RUST_LOG` is not set. It's a compile-time constant — no allocation, no parsing at startup unless needed. The directives:

| Directive | Effect |
|---|---|
| `rustflow_server=debug` | Show `DEBUG`, `INFO`, `WARN`, `ERROR` from our server crate |
| `rustflow_common=debug` | Show `DEBUG`, `INFO`, `WARN`, `ERROR` from our shared crate |
| `tower_http=debug` | Show `DEBUG`, `INFO`, `WARN`, `ERROR` from tower-http (for `TraceLayer` in 3.3) |
| `warn` | Global default — show only `WARN` and `ERROR` from everything else |

Why `debug` for our crates? During development, you want to see diagnostic output — request timing, counter values, task lookups. In production, you'd override with `RUST_LOG=rustflow_server=info,warn` to reduce noise.

Why `warn` as the global default? Dependencies like `hyper`, `tokio`, and `tower` emit a lot of `DEBUG` and `TRACE` output that's only useful when debugging those libraries themselves. `WARN` means you'll still see if something goes wrong in a dependency, but you won't be flooded with their internal diagnostics.

Why include `tower_http=debug`? We'll add `TraceLayer` in lesson 3.3, which uses `tower_http` to log HTTP requests and responses. Including it now means the output will "just work" when we add the layer — no filter changes needed.

#### Building the `EnvFilter`

```rust
let env_filter = EnvFilter::try_from_default_env()
    .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));
```

This is the core logic — two lines that implement the "try `RUST_LOG`, fall back to default" pattern:

1. **`EnvFilter::try_from_default_env()`** — reads the `RUST_LOG` environment variable and tries to parse it as filter directives. Returns `Ok(EnvFilter)` if `RUST_LOG` is set and valid, `Err` if `RUST_LOG` is unset or contains invalid syntax.

2. **`.unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER))`** — if `RUST_LOG` is not set (or invalid), create an `EnvFilter` from our compiled-in default string. `EnvFilter::new()` parses the directive string at runtime.

The `|_|` closure discards the error — we don't care *why* `RUST_LOG` failed (unset vs. invalid syntax). In both cases, the default is a good fallback. If you wanted to distinguish between "unset" and "invalid," you could check `std::env::var("RUST_LOG")` first, but for a development tool, the simple approach is fine.

#### Assembling the Subscriber

```rust
tracing_subscriber::fmt()
    .with_env_filter(env_filter)
    .init();
```

Compare this to the 3.1 version:

```rust
// 3.1 — no filtering
tracing_subscriber::fmt::init();

// 3.2 — with EnvFilter
tracing_subscriber::fmt()
    .with_env_filter(env_filter)
    .init();
```

The difference:
- `fmt::init()` is a convenience function that creates a subscriber with defaults and installs it. No filtering — everything passes through.
- `fmt()` returns a **builder**. `.with_env_filter(env_filter)` adds the filter layer. `.init()` installs the assembled subscriber as the global default.

The builder pattern is how `tracing-subscriber` stays composable. In later lessons, we'll chain more methods:

```rust
// Preview of where this is heading (3.6, 3.7):
tracing_subscriber::fmt()
    .with_env_filter(env_filter)
    .json()                        // 3.7: JSON output
    .init();
```

Each `.with_*()` call adds a capability. The subscriber grows incrementally — exactly like the Axum middleware stack grows with `.layer()`.

### Why Not `EnvFilter::from_default_env()`?

You might see examples using `EnvFilter::from_default_env()` (without `try_`). The difference:

```rust
// Panics if RUST_LOG is not set or invalid:
let filter = EnvFilter::from_default_env();

// Returns Err if RUST_LOG is not set or invalid:
let filter = EnvFilter::try_from_default_env();
```

We use `try_` because we *want* the fallback behavior. `from_default_env()` would panic on startup if `RUST_LOG` isn't set — terrible developer experience. The `try_` + `unwrap_or_else` pattern gives us graceful degradation: no `RUST_LOG`? No problem, use the default.

### The `env-filter` Feature

Back in lesson 3.1, we added `tracing-subscriber` with the `env-filter` feature:

```toml
tracing-subscriber = { version = "0.3", features = ["fmt", "env-filter"] }
```

This is why `EnvFilter` is available. Without the `env-filter` feature, the `EnvFilter` type doesn't exist and the code won't compile. The feature pulls in the `regex` and `matchers` crates that `EnvFilter` uses to parse directive strings.


## Step 2: Understanding Filter Directives in Depth

Before testing, let's understand the full directive syntax — you'll use this constantly when debugging.

### Directive Precedence

When multiple directives match an event, the **most specific** one wins:

```text
RUST_LOG=warn,rustflow_server=debug,rustflow_server::routes::tasks=trace
```

For an event from `rustflow_server::routes::tasks`:
1. `rustflow_server::routes::tasks=trace` matches (most specific) → **TRACE** ✓
2. `rustflow_server=debug` also matches (less specific) → ignored
3. `warn` is the global default → ignored

For an event from `rustflow_server::routes::middleware`:
1. `rustflow_server=debug` matches → **DEBUG** ✓
2. `warn` is the global default → ignored

For an event from `hyper::proto::h1`:
1. No specific directive matches → falls through to `warn` → **WARN** ✓

### The `off` Level

You can completely silence a crate:

```text
RUST_LOG=rustflow_server=debug,hyper=off,warn
```

`hyper=off` means no events from `hyper` will ever reach the subscriber — not even `ERROR`. Use this sparingly, but it's useful when a dependency is extremely chatty and you're sure you don't need its output.

### Module-Level Granularity

Directives can target specific modules within a crate:

```text
RUST_LOG=rustflow_server::routes::tasks=trace,rustflow_server=info,warn
```

This shows `TRACE`-level output from the tasks module, `INFO` from the rest of the server, and `WARN` from everything else. This is incredibly powerful for debugging a specific handler without drowning in output from the entire application.

### Common Directive Patterns

| Pattern | Effect |
|---|---|
| `warn` | Global: only warnings and errors from everything |
| `info` | Global: info, warnings, and errors from everything |
| `rustflow_server=debug,warn` | Debug for our server, warn for everything else |
| `rustflow_server=debug,rustflow_common=debug,warn` | Debug for our crates, warn for deps |
| `rustflow_server::routes::tasks=trace,info` | Trace one module, info for everything else |
| `hyper=off,tokio=off,debug` | Silence hyper and tokio, debug for everything else |
| `tower_http=debug,rustflow_server=info,warn` | Debug HTTP tracing, info for server, warn for rest |


## Step 3: How `RUST_LOG` Overrides Work

The relationship between the compiled-in default and `RUST_LOG` is simple: **`RUST_LOG` wins completely when set**. There's no merging — the environment variable replaces the default entirely.

```text
Compiled-in default:
  rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn

RUST_LOG=info
  → The default is IGNORED. Only "info" applies.
  → Everything at INFO and above is shown. No per-crate filtering.

RUST_LOG=rustflow_server=trace,error
  → The default is IGNORED. Only these two directives apply.
  → TRACE for rustflow_server, ERROR for everything else.
  → rustflow_common is now at ERROR (not debug!) because the default was replaced.
```

This is important to understand: setting `RUST_LOG=info` doesn't mean "start with the default and change the global level to info." It means "throw away the default and use `info` as the entire filter."

If you want to keep the per-crate filtering but change the global default:

```bash
# Keep per-crate debug, but change global default from warn to info
RUST_LOG=rustflow_server=debug,rustflow_common=debug,tower_http=debug,info cargo run -p rustflow-server
```

You have to repeat the per-crate directives because `RUST_LOG` is a complete replacement.

### Why Complete Replacement?

This design is intentional. In production, the operator needs full control over what's logged. If `RUST_LOG` merged with the default, you couldn't silence a crate that the default enables — you'd always get at least the default's output. Complete replacement means `RUST_LOG` is the single source of truth when set.

The compiled-in default is for the common case: a developer who just runs `cargo run` and wants sensible output without thinking about `RUST_LOG`. The override is for the uncommon case: debugging a specific issue, running in production, or testing a particular module.


## Step 4: Filtering Noisy Dependencies

Let's look at the specific dependencies that produce the most noise and how our default filter handles them:

### The Usual Suspects

| Crate | What It Logs | Default Level | Why |
|---|---|---|---|
| `hyper` | HTTP/1.1 parsing, connection pooling, byte flushing | `warn` | Extremely verbose at debug/trace — hundreds of lines per request |
| `tokio` | Runtime scheduling, task polling, I/O driver events | `warn` | Internal scheduler details — only useful when debugging Tokio itself |
| `tower` | Service readiness, buffer worker events, load shedding | `warn` | Middleware internals — useful for Tower contributors, noise for users |
| `reqwest` | Connection establishment, TLS handshake, redirect following | `warn` | HTTP client internals — only relevant when debugging outbound calls |
| `h2` | HTTP/2 frame-level details (if HTTP/2 is used) | `warn` | Protocol-level noise |
| `rustls` / `native_tls` | TLS certificate validation, cipher negotiation | `warn` | Security layer internals |

Our default filter (`warn` as the global fallback) silences all of these at `DEBUG` and `TRACE` level. You'll only see output from them if something goes wrong — a connection failure, a TLS error, a buffer overflow.

### When to Temporarily Enable Dependency Logging

Sometimes you *need* to see what a dependency is doing:

```bash
# Debugging a connection issue with an external API
RUST_LOG=reqwest=debug,rustflow_server=debug,warn cargo run -p rustflow-server

# Debugging HTTP/1.1 parsing issues
RUST_LOG=hyper=trace,rustflow_server=info,warn cargo run -p rustflow-server

# Debugging tower middleware ordering
RUST_LOG=tower=debug,rustflow_server=debug,warn cargo run -p rustflow-server
```

The key insight: you enable dependency logging **temporarily**, for a specific debugging session, via `RUST_LOG`. You never change the compiled-in default for this — the default stays clean for everyday development.

### The `tower_http` Exception

Notice that `tower_http=debug` is in our default filter, not silenced like other dependencies. This is deliberate:

```text
rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn
                                             │
                                             └── tower_http is NOT silenced
```

`tower_http` is different from `tower`. While `tower` logs internal service machinery, `tower_http` logs **HTTP-level events** — request method, URI, response status, latency. This is exactly the output we want to see during development. In lesson 3.3, we'll add `TraceLayer` from `tower_http`, and its output will flow through because we've already included it in the filter.

If we had `tower_http` at `warn` like other dependencies, the `TraceLayer` output would be invisible until someone sets `RUST_LOG` — a confusing experience for a student who just added the layer and sees nothing.

## How `EnvFilter` Works Under the Hood

When an event is emitted (e.g., `tracing::info!("listening")`), the subscriber pipeline processes it in order:

```text
tracing::info!("listening")
    │
    ▼
┌─────────────────────┐
│     EnvFilter        │  ← Does this event pass the filter?
│                      │
│  target: rustflow_server
│  level:  INFO        │
│                      │
│  Check directives:   │
│  1. rustflow_server=debug → INFO ≥ DEBUG? Yes ✓
│                      │
│  Result: PASS        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│     fmt Layer        │  ← Format and write to stdout
│                      │
│  2026-01-15T10:30:00.123456Z  INFO rustflow_server: listening
└─────────────────────┘
```

For a filtered-out event:

```text
tracing::debug!("connection pooled")
    │
    ▼
┌─────────────────────┐
│     EnvFilter        │
│                      │
│  target: hyper_util::client::legacy::pool
│  level:  DEBUG       │
│                      │
│  Check directives:   │
│  1. No specific match for hyper_util
│  2. Global default: warn → DEBUG ≥ WARN? No ✗
│                      │
│  Result: REJECT      │
└─────────────────────┘
           │
           ✗ (event never reaches fmt layer — zero formatting cost)
```

The key performance insight: **rejected events never reach the formatting layer**. The `EnvFilter` short-circuits before any string formatting, timestamp generation, or I/O happens. This means having thousands of `debug!` calls in your code costs essentially nothing when the filter is set to `info` — the check is a simple integer comparison.

## Key Takeaways

1. **`EnvFilter` gives you per-crate log level control.** Instead of a single global level, you set different levels for different crates: `debug` for your code, `warn` for dependencies. This is the difference between useful output and an unreadable flood.

2. **The "try env, fall back to default" pattern is idiomatic.** `EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new(DEFAULT))` is the standard way to handle `RUST_LOG` in Rust applications. Zero-config for developers, full control for operators.

3. **`RUST_LOG` is a complete replacement, not a merge.** When set, it replaces the compiled-in default entirely. If you want per-crate filtering with a different global default, you must repeat all the per-crate directives in `RUST_LOG`.

4. **Filtered events have near-zero cost.** `EnvFilter` rejects events before any formatting happens. You can leave `debug!` calls throughout your code and they cost nothing when the filter is set to `info`.

5. **Crate names use underscores in directives.** `rustflow-server` becomes `rustflow_server`. Rust converts hyphens to underscores in module paths — filter directives must match the module path, not the crate name.

6. **The abstraction from 3.1 paid off immediately.** `main.rs` didn't change. The server calls `init_tracing()` and gets filtering for free. This pattern continues through the rest of Section 3 — every enhancement happens inside `tracing.rs`.

7. **Include `tower_http` in your default filter.** Unlike `hyper` and `tokio`, `tower_http` produces HTTP-level output that's useful during development. Setting it to `debug` in the default means `TraceLayer` output (lesson 3.3) will work out of the box.

## What's Next

We can now control *what* appears in the output. But we're still manually logging requests with our `log_request` middleware — and it only captures the method and URI. In lesson 3.3, we'll add `tower-http`'s `TraceLayer`, which automatically creates spans for every HTTP request and emits response events with status codes and latency. It replaces our custom `log_request` and `log_elapsed_time` middleware entirely — and because we set `tower_http=debug` in our default filter, the output will appear immediately.
