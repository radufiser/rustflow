# 3.9 — Distributed Trace Propagation

## Overview

Open Jaeger. Find a trace for `GET /api/enrichment/tasks/1/user/1`. You see something like this:

```text
rustflow: HTTP request GET /api/enrichment/tasks/1/user/1 (450ms)
├── rustflow: enrich_task (440ms)
│   └── rustflow: store read (0.1ms)
└── rustflow: response sent
```

Where's the outbound HTTP call to JSONPlaceholder? It took ~400ms — the dominant cost — but it's invisible. The `reqwest` call to `https://jsonplaceholder.typicode.com/users/1` doesn't appear as a child span. Worse, if JSONPlaceholder were *your* service (another microservice in your infrastructure), its traces would be completely disconnected from RustFlow's traces. Two independent trace trees, no way to connect them.

This is the **distributed tracing problem**: when a request crosses a service boundary (an HTTP call from Service A to Service B), the trace breaks. Each service creates its own independent trace with its own trace ID. You can't follow a request from end to end.

```text
Without propagation:

Client → RustFlow                    JSONPlaceholder
         trace-id: abc123            trace-id: xyz789  ← different!
         ├── HTTP request            ├── HTTP request
         │   └── enrich_task         │   └── get user
         └── response                └── response

Two separate traces. No connection between them.
```

The solution is **trace context propagation** — passing the current trace identity from the caller to the callee via HTTP headers. The callee continues the same trace instead of starting a new one:

```text
With propagation:

Client → RustFlow ──────────────────→ JSONPlaceholder
         trace-id: abc123              trace-id: abc123  ← same!
         ├── HTTP request              ├── HTTP request (child span)
         │   └── enrich_task           │   └── get user
         │       └── outbound call ────┘
         └── response

One trace. One trace ID. The outbound call from RustFlow appears as a parent
of the inbound request in JSONPlaceholder. You can follow the request across
every service it touches.
```

### W3C TraceContext: The Standard

How does the trace identity travel between services? Through HTTP headers. But which headers? In what format? Every vendor used to have their own:

| Vendor | Header | Format |
|---|---|---|
| Zipkin | `X-B3-TraceId` | Hex trace ID |
| AWS X-Ray | `X-Amzn-Trace-Id` | `Root=1-xxx;Parent=yyy` |
| Jaeger | `uber-trace-id` | `{trace-id}:{span-id}:{parent-id}:{flags}` |
| Datadog | `x-datadog-trace-id` | Decimal trace ID |

This was chaos. If Service A used Zipkin headers and Service B used Jaeger headers, propagation broke. The W3C standardized this with **TraceContext** — a single header format that all vendors now support.

### The `traceparent` Header

The W3C TraceContext standard defines one required header: `traceparent`. Its format is:

```text
traceparent: {version}-{trace-id}-{parent-id}-{trace-flags}
```

Each field:

| Field | Length | Description | Example |
|---|---|---|---|
| `version` | 2 hex chars | Protocol version (always `00` today) | `00` |
| `trace-id` | 32 hex chars | Globally unique trace identifier | `4bf92f3577b34da6a3ce929d0e0e4736` |
| `parent-id` | 16 hex chars | The span ID of the calling span | `00f067aa0ba902b7` |
| `trace-flags` | 2 hex chars | Flags (e.g., `01` = sampled) | `01` |

A complete example:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

This tells the receiving service:
- "You are part of trace `4bf92f3577b34da6a3ce929d0e0e4736`"
- "Your parent span is `00f067aa0ba902b7`"
- "This trace is being sampled (`01`)"

The receiving service creates a new span with a new span ID, but uses the same trace ID and sets the parent to the span ID from the header. The result: a connected tree of spans across services.

### Two Directions of Propagation

Trace propagation has two sides:

1. **Injection** (outbound) — When RustFlow makes an HTTP call to another service, it *injects* the current trace context into the request headers. The `traceparent` header carries the trace ID and the current span ID.

2. **Extraction** (inbound) — When RustFlow receives an HTTP request with a `traceparent` header, it *extracts* the trace context and continues that trace instead of starting a new one.

```text
Injection (outbound):                    Extraction (inbound):

RustFlow span context                    Incoming request
    │                                        │
    ▼                                        ▼
W3C Propagator.inject()                  W3C Propagator.extract()
    │                                        │
    ▼                                        ▼
traceparent header on                    New span linked to
outgoing request                         incoming trace context
```

OpenTelemetry provides a `TraceContextPropagator` that handles both directions. We don't need to manually format or parse the `traceparent` header — the propagator does it for us.

## Step 1: Install the W3C TraceContext Propagator

The first step is telling OpenTelemetry *how* to propagate trace context. OpenTelemetry supports multiple propagation formats (W3C, B3, Jaeger, etc.), but we want the W3C standard. We set this during tracing initialization.

**Update** `crates/rustflow-common/src/tracing.rs` — add the propagator setup inside `init_tracing()`:

```rust name=crates/rustflow-common/src/tracing.rs
#[cfg(feature = "otel")]
use opentelemetry::propagation::TextMapPropagator;
#[cfg(feature = "otel")]
use opentelemetry_sdk::propagation::TraceContextPropagator;

pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    // ... existing filter, stdout, file layer setup ...

    // ── Install the W3C TraceContext propagator (feature-gated) ──
    #[cfg(feature = "otel")]
    {
        opentelemetry::global::set_text_map_propagator(
            TraceContextPropagator::new(),
        );
    }

    // ── assemble the registry ───────────────────────────────
    let registry = tracing_subscriber::registry()
        .with(env_filter)
        .with(human_layer)
        .with(json_layer)
        .with(file_layer);

    #[cfg(feature = "otel")]
    {
        let otel_layer = config
            .otlp_endpoint
            .as_deref()
            .and_then(build_otel_layer);
        registry.with(otel_layer).init();
    }

    #[cfg(not(feature = "otel"))]
    {
        registry.init();
    }

    guard
}
```

### What Does `set_text_map_propagator` Do?

The global propagator is a singleton that knows how to:

1. **Inject** — given a span context, write it into a set of key-value pairs (HTTP headers)
2. **Extract** — given a set of key-value pairs (HTTP headers), reconstruct a span context

`TraceContextPropagator` implements the W3C TraceContext specification. When you call `inject()`, it writes the `traceparent` header. When you call `extract()`, it reads the `traceparent` header and returns a `SpanContext` with the trace ID and parent span ID.

We install it globally so that both injection (outbound) and extraction (inbound) use the same format. This must happen before any requests are processed — that's why it's in `init_tracing()`.

### Why Not Install It in `build_otel_layer`?

The propagator is independent of the exporter. Even if the OTLP exporter fails to initialize (collector unreachable), you still want propagation to work. A downstream service might have its own collector — your job is to pass the trace context along, regardless of whether *you* can export traces.

That said, propagation only produces meaningful results when at least one service in the chain exports to a collector. If nobody exports, the `traceparent` headers flow through but nobody records the spans.


## Step 2: Inject `traceparent` on Outbound HTTP Requests

When RustFlow calls an external service (like JSONPlaceholder in `enrichment.rs`), we need to inject the current trace context into the outgoing request headers. This way, the downstream service can continue the same trace.

The injection process:

1. Get the current span's context
2. Use the global propagator to write it into the request headers
3. Send the request with the `traceparent` header attached

**Update** `crates/rustflow-server/src/routes/enrichment.rs`:

```rust name=crates/rustflow-server/src/routes/enrichment.rs
use crate::state::AppState;
use axum::extract::{Path, State};
use axum::{routing::get, Json, Router};
use crate::errors::RustFlowError;

// ... ExternalUser, EnrichedTask structs unchanged ...

/// Injects the current OpenTelemetry trace context into HTTP request headers.
///
/// This enables distributed tracing: the outbound request carries the
/// `traceparent` header so the downstream service can continue the same trace.
#[cfg(feature = "otel")]
fn inject_trace_context(headers: &mut reqwest::header::HeaderMap) {
    use opentelemetry::propagation::TextMapPropagator;
    use opentelemetry::global;
    use tracing_opentelemetry::OpenTelemetrySpanExt;

    let propagator = global::get_text_map_propagator(|p| p.clone());
    let cx = tracing::Span::current().context();

    // HeaderInjector adapts a HeaderMap to the TextMapPropagator interface
    let mut injector = opentelemetry_http::HeaderInjector(headers);
    propagator.inject_context(&cx, &mut injector);
}

async fn enrich_task(
    State(state): State<AppState>,
    Path((task_id, user_id)): Path<(u64, u64)>,
) -> Result<Json<EnrichedTask>, RustFlowError> {
    // Step 1: Find the task in local state (lock scoped)
    let task = {
        let store = state.tasks.0.read().await;
        store
            .tasks
            .iter()
            .find(|t| t.id == task_id)
            .cloned()
            .ok_or(RustFlowError::NotFound(
                format!("Task with id {task_id} not found"),
            ))?
    };

    // Step 2: Build the outbound request
    let url = format!(
        "https://jsonplaceholder.typicode.com/users/{}",
        user_id
    );

    let mut request = state.http_client.get(&url);

    // Step 3: Inject trace context into outbound headers
    #[cfg(feature = "otel")]
    {
        let mut headers = reqwest::header::HeaderMap::new();
        inject_trace_context(&mut headers);
        request = request.headers(headers);
    }

    // Step 4: Send the request
    let user: ExternalUser = request
        .send()
        .await
        .map_err(|e| RustFlowError::ExternalService(e.to_string()))?
        .error_for_status()
        .map_err(|e| RustFlowError::ExternalService(e.to_string()))?
        .json()
        .await
        .map_err(|e| RustFlowError::ExternalService(e.to_string()))?;

    // Step 5: Combine into enriched response
    let enriched = EnrichedTask {
        id: task_id,
        title: task.title,
        description: task.description,
        priority: format!("{:?}", task.priority),
        status: format!("{:?}", task.status),
        assign_to: user,
    };
    Ok(Json(enriched))
}
```

### Anatomy of `inject_trace_context`

Let's break down the injection function:

```rust
#[cfg(feature = "otel")]
fn inject_trace_context(headers: &mut reqwest::header::HeaderMap) {
    use opentelemetry::propagation::TextMapPropagator;
    use opentelemetry::global;
    use tracing_opentelemetry::OpenTelemetrySpanExt;

    let propagator = global::get_text_map_propagator(|p| p.clone());
    let cx = tracing::Span::current().context();

    let mut injector = opentelemetry_http::HeaderInjector(headers);
    propagator.inject_context(&cx, &mut injector);
}
```

**Line by line:**

1. `global::get_text_map_propagator(|p| p.clone())` — retrieves the global propagator we installed in Step 1 (the `TraceContextPropagator`). The closure clones it because the global is behind a lock.

2. `tracing::Span::current().context()` — this is the bridge between `tracing` and OpenTelemetry. `Span::current()` gets the active `tracing` span. `.context()` (from `OpenTelemetrySpanExt`) extracts the OpenTelemetry `Context` from that span — which contains the trace ID and span ID.

3. `opentelemetry_http::HeaderInjector(headers)` — wraps a `reqwest::header::HeaderMap` so the propagator can write headers into it. The propagator doesn't know about `reqwest` — it works with a generic `Injector` trait. `HeaderInjector` is the adapter.

4. `propagator.inject_context(&cx, &mut injector)` — writes the `traceparent` header into the `HeaderMap`. After this call, `headers` contains something like:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

### The `opentelemetry-http` Crate

You'll notice we use `opentelemetry_http::HeaderInjector`. This is a small utility crate that provides adapters between HTTP header types and the OpenTelemetry propagation API. You'll need to add it to your dependencies:

```toml name=crates/rustflow-common/Cargo.toml

```

```toml name=Cargo.toml
# Add to workspace dependencies

```

And update the `otel` feature:

```toml
[features]

    "dep:opentelemetry",
    "dep:opentelemetry-sdk",
    "dep:opentelemetry-otlp",
    "dep:tracing-opentelemetry",
    "dep:opentelemetry-http",
]
```

### The `#[cfg(feature = "otel")]` Pattern

Notice how the injection is wrapped in `#[cfg(feature = "otel")]`:

```rust
#[cfg(feature = "otel")]
{
    let mut headers = reqwest::header::HeaderMap::new();
    inject_trace_context(&mut headers);
    request = request.headers(headers);
}
```

When the `otel` feature is disabled, this block doesn't exist. The request is sent without any trace headers — exactly the same behavior as before lesson 3.9. Zero cost when you don't need propagation.

### Why Not Use reqwest Middleware?

An alternative approach is to use `reqwest-middleware` to automatically inject headers on every outbound request. This is cleaner for production code — you configure it once and every request gets trace headers automatically:

```rust
// Alternative: reqwest middleware approach (not used here for simplicity)
use reqwest_middleware::{ClientBuilder, ClientWithMiddleware};
use reqwest_tracing::TracingMiddleware;

let client = ClientBuilder::new(reqwest::Client::new())
    .with(TracingMiddleware::default())
    .build();
```

We use the manual approach in this lesson because:
1. It's more explicit — you see exactly what's happening
2. It doesn't require additional crates (`reqwest-middleware`, `reqwest-tracing`)
3. It teaches the underlying mechanism that middleware abstracts away

In a production service with many outbound calls, the middleware approach is better — you don't want to remember to inject headers on every call.


## Step 3: Extract `traceparent` on Inbound HTTP Requests

The other direction: when RustFlow *receives* a request with a `traceparent` header, it should continue that trace instead of starting a new one. This is how an upstream service (or a load balancer, or an API gateway) passes its trace context to RustFlow.

Without extraction, every request to RustFlow starts a fresh trace — even if the caller already has a trace in progress. With extraction, RustFlow's spans become children of the caller's span.

**Update** `crates/rustflow-server/src/routes/middleware.rs` — add an extraction middleware:

```rust name=crates/rustflow-server/src/routes/middleware.rs
/// Middleware that extracts W3C TraceContext from inbound request headers.
///
/// If the incoming request carries a `traceparent` header, this middleware
/// extracts the trace context and sets it as the parent of the current span.
/// This means RustFlow's spans become children of the caller's trace.
///
/// If no `traceparent` header is present, the request proceeds normally
/// with a fresh trace (the default behavior).
#[cfg(feature = "otel")]
pub async fn extract_trace_context(
    request: axum::extract::Request,
    next: axum::middleware::Next,
) -> axum::response::Response {
    use opentelemetry::global;
    use opentelemetry::propagation::TextMapPropagator;
    use tracing_opentelemetry::OpenTelemetrySpanExt;

    // Extract the trace context from the incoming request headers
    let propagator = global::get_text_map_propagator(|p| p.clone());
    let extractor = opentelemetry_http::HeaderExtractor(request.headers());
    let cx = propagator.extract(&extractor);

    // Set the extracted context as the parent of the current span
    tracing::Span::current().set_parent(cx);

    next.run(request).await
}
```

### How Extraction Works

```rust
let extractor = opentelemetry_http::HeaderExtractor(request.headers());
let cx = propagator.extract(&extractor);
```

`HeaderExtractor` wraps the request's `HeaderMap` so the propagator can read from it. The propagator looks for the `traceparent` header and parses it:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                 │                                  │                │
                 trace-id                           parent-id        sampled
```

If the header is present and valid, `extract()` returns a `Context` containing the remote span context. If the header is missing or malformed, it returns an empty context — and the request proceeds with a fresh trace. No errors, no panics.

```rust
tracing::Span::current().set_parent(cx);
```

This is the key line. `.set_parent(cx)` tells the current `tracing` span (created by `TraceLayer`) to adopt the extracted context as its parent. The span's trace ID changes to match the incoming `traceparent` header. Now all spans within this request — the handler, the store operations, the outbound calls — are part of the caller's trace.

### Wiring the Middleware into the Router

The extraction middleware should run early — before the handler creates any spans. Add it to the router stack in `main.rs`:

```rust name=crates/rustflow-server/src/main.rs
// ── Compose everything ──────────────────────────────────
let mut app = Router::new()
    .merge(static_router)
    .merge(infra_router)
    .nest("/api", api_router)
    .with_state(state)
    .layer(cors);

// Add trace context extraction when OTel is enabled
#[cfg(feature = "otel")]
{
    use crate::routes::middleware::extract_trace_context;
    app = app.layer(axum::middleware::from_fn(extract_trace_context));
}
```

The extraction middleware sits outside the `TraceLayer` — it runs first, extracts the context, and then `TraceLayer` creates a span that inherits the extracted parent. The ordering matters:

```text
Inbound request with traceparent header
    │
    ▼
extract_trace_context middleware    ← extracts parent context
    │
    ▼
TraceLayer                          ← creates span (inherits parent)
    │
    ▼
Handler                             ← all spans are children of the incoming trace
```

If you put the extraction *after* `TraceLayer`, the `TraceLayer` span would already be created with a fresh trace ID, and the extraction would be too late.

### What If There's No `traceparent` Header?

Most requests to RustFlow won't have a `traceparent` header — direct `curl` calls, browser requests, and API clients that don't do tracing. In that case:

1. `propagator.extract()` returns an empty context (no remote parent)
2. `set_parent(empty_context)` is a no-op
3. `TraceLayer` creates a span with a fresh trace ID — exactly the same as before

The middleware is transparent for requests without trace headers. It only activates when a `traceparent` is present.

### What Jaeger Shows

After sending the enrichment request, open Jaeger and find the trace:

```text
rustflow: HTTP request GET /api/enrichment/tasks/1/user/1 (450ms)
├── rustflow: enrich_task (440ms)
```

The outbound HTTP call now appears as a child span. You can see exactly how long the external call took (430ms) and that it dominates the total request time (450ms). Without propagation, this call was invisible.

### With an Upstream Caller

Now imagine another service calls RustFlow with a `traceparent` header:

```bash
curl -s http://localhost:3000/api/enrichment/tasks/1/user/1 \

```

In Jaeger, the trace `4bf92f3577b34da6a3ce929d0e0e4736` now includes RustFlow's spans as children of span `00f067aa0ba902b7`:

```text
└── rustflow: HTTP request GET /api/enrichment/tasks/1/user/1

    └── rustflow: response sent
```

The entire request flow — from the upstream service, through RustFlow, to JSONPlaceholder — is one connected trace. This is the power of distributed tracing.


## Step 5: The `traceparent` Header in Detail

Let's look at a real `traceparent` header that RustFlow would inject:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ││                                  │                ││
             ││         trace-id (32 hex)        │  parent-id     ││
             │└──────────────────────────────────┘  (16 hex)      ││
             │                                                    ││
             version (2 hex)                          trace-flags ┘│
                                                      (2 hex)     │
```

### Version (`00`)

Always `00` in the current spec. Future versions might add fields. Receivers that don't understand a version should still attempt to parse the trace-id and parent-id — forward compatibility is built into the spec.

### Trace ID (`4bf92f3577b34da6a3ce929d0e0e4736`)

A 128-bit (16-byte) globally unique identifier for the entire trace. Every span in the trace shares this ID. It's generated by the service that starts the trace (the "root" service) and propagated to all downstream services.

32 hex characters = 128 bits = enough uniqueness that collisions are astronomically unlikely (2^128 possible values).

### Parent ID (`00f067aa0ba902b7`)

A 64-bit (8-byte) identifier for the specific span that made the outbound call. The receiving service uses this as the parent of its root span, creating the parent-child relationship in the trace tree.

16 hex characters = 64 bits. Each span in the trace has a unique span ID. The parent ID in the `traceparent` header points to the calling span.

### Trace Flags (`01`)

A single byte of flags. Currently only one flag is defined:

| Bit | Name | Meaning |
|---|---|---|
| 0 (LSB) | `sampled` | `1` = this trace is being recorded; `0` = this trace is not sampled |

`01` means "sampled" — the trace is being recorded. `00` means "not sampled" — the trace context is propagated but spans are not recorded. This is useful for high-traffic services that only sample a percentage of traces.

### Generating and Parsing

You never need to manually construct or parse `traceparent` headers. The `TraceContextPropagator` handles it:

```rust
// Injection: propagator reads the span context and writes the header
propagator.inject_context(&cx, &mut injector);
// Result: headers now contain "traceparent: 00-{trace-id}-{span-id}-{flags}"

// Extraction: propagator reads the header and returns a context
let cx = propagator.extract(&extractor);
// Result: cx contains the trace-id and parent-id from the header
```

The propagator also handles the optional `tracestate` header (vendor-specific key-value pairs), but `traceparent` is the essential one.

## Key Takeaways

1. **Without trace propagation, distributed traces are disconnected.** Each service creates its own trace with its own trace ID. You can't follow a request across service boundaries. Propagation connects the dots.

2. **W3C TraceContext is the standard.** The `traceparent` header (`{version}-{trace-id}-{parent-id}-{trace-flags}`) is supported by all major tracing vendors. Use it instead of vendor-specific headers (B3, X-Ray, etc.) for interoperability.

3. **Injection and extraction are symmetric.** Injection writes the current span context into outbound request headers. Extraction reads the span context from inbound request headers. The `TraceContextPropagator` handles both.

4. **The propagator is global and format-agnostic.** `set_text_map_propagator()` installs the propagator once. Both injection and extraction use the same propagator. You could swap W3C for B3 by changing one line.

5. **`tracing::Span::current().context()` bridges tracing and OpenTelemetry.** The `OpenTelemetrySpanExt` trait provides `.context()` (get the OTel context from a tracing span) and `.set_parent()` (set the OTel parent on a tracing span). These are the glue between the two ecosystems.

6. **Feature-gating keeps the cost zero when disabled.** All propagation code is behind `#[cfg(feature = "otel")]`. Without the feature, the enrichment endpoint works exactly as before — no trace headers, no overhead, no extra dependencies.

7. **Extraction middleware must run before `TraceLayer`.** The extraction middleware sets the parent context on the current span. If `TraceLayer` creates the span first, the parent is already set to "none" and extraction is too late.

8. **Graceful degradation everywhere.** Missing `traceparent` header? Fresh trace. Malformed header? Fresh trace. No collector running? Spans are dropped silently. The server never fails because of tracing infrastructure.

9. **The `traceparent` format is simple and debuggable.** `00-{32 hex}-{16 hex}-{2 hex}` — you can read it in logs, construct it in `curl` commands, and verify it visually. No binary encoding, no base64, no compression.

10. **The layered subscriber pattern paid off.** Nine lessons, nine layers, zero conflicts. Each lesson added capability without modifying previous layers. This is the power of composable middleware and subscriber architectures.
