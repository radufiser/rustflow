# 3.5 — Custom Per-Request Axum Spans

## Overview

After lesson 3.4, every request to RustFlow has a two-level span hierarchy:

```text
request{method=POST uri="/api/tasks"}          ← TraceLayer (3.3)
  └── task.create{task.id=4}                   ← #[instrument] (3.4)
        └── INFO "task created"
```

The outer span comes from `TraceLayer`'s `DefaultMakeSpan`. It includes the HTTP method and URI — and nothing else. That's a problem.

Open two terminals and send requests simultaneously:

```bash
# Terminal 1
curl -s http://localhost:3000/api/tasks &
curl -s -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" \
  -H "x-api-key: rustflow-api-key-2026" \
  -d '{"title": "Concurrent A"}' &

# Terminal 2
curl -s http://localhost:3000/api/tasks &
curl -s -X POST http://localhost:3000/api/tasks \
  -H "Content-Type: application/json" \
  -H "x-api-key: rustflow-api-key-2026" \
  -d '{"title": "Concurrent B"}' &
```

Now look at the server output:

```text
2026-01-15T10:30:01.456Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.456Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.457Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.457Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.457Z  INFO request{method=POST uri="/api/tasks"}: task.create{task.id=4}: rustflow_server::routes::tasks: task created
2026-01-15T10:30:01.458Z  INFO request{method=POST uri="/api/tasks"}: task.create{task.id=5}: rustflow_server::routes::tasks: task created
2026-01-15T10:30:01.458Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=2 ms status=200
2026-01-15T10:30:01.458Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=2 ms status=201
2026-01-15T10:30:01.459Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=2 ms status=200
2026-01-15T10:30:01.459Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=2 ms status=201
```

Which `GET /api/tasks` is which? Both have identical span fields: `method=GET uri="/api/tasks"`. Which `POST` created task 4 and which created task 5? You can guess from timestamps, but under real load with hundreds of concurrent requests, guessing doesn't work.

Three questions you can't answer from this output:

1. **Which specific request is this?** Two `GET /api/tasks` requests look identical. There's no unique identifier to distinguish them.
2. **Who made this request?** The POST requests required authentication — someone provided an API key. But the request span doesn't say who. Was it the `admin` client? The `ci-bot`? You'd have to cross-reference with the handler's `tracing::info!` event, which is buried deeper in the output.
3. **What entity was targeted?** For `GET /api/tasks/42`, the URI contains the ID — but it's embedded in a string. It's not a structured field you can filter on. And for nested resources like `/api/projects/5/tasks/42`, parsing IDs from URI strings is fragile.

### What We Need

The per-request span should carry **domain-specific context** — not just the raw HTTP method and URI:

```text
# What DefaultMakeSpan gives us:
request{method=POST uri="/api/tasks"}

# What we want:
request{method=POST uri="/api/tasks" request_id=a1b2c3d4-... client.name=admin}
request{method=GET uri="/api/tasks/42" request_id=e5f6a7b8-... entity.id=42}
request{method=GET uri="/api/tasks" request_id=c9d0e1f2-...}
```

With a unique `request_id`, you can trace every log line from a single request — even when thousands are interleaved. With `client.name`, you know who made the request without digging into handler events. With `entity.id`, you can filter for "show me everything that happened to task 42."

### The `MakeSpan` Trait

`TraceLayer` doesn't hardcode how spans are created. It delegates to a **`MakeSpan`** implementation. The `DefaultMakeSpan` we've been using is just the built-in default — you can replace it with your own.

The `MakeSpan` trait from `tower_http::trace` looks like this:

```rust
pub trait MakeSpan<B> {
    fn make_span(&mut self, request: &http::Request<B>) -> tracing::Span;
}
```

One method. It receives the incoming HTTP request and returns a `tracing::Span`. That span wraps the entire request lifecycle — handler execution, response generation, everything.

By implementing `MakeSpan`, you control exactly what fields appear on every request span. You have access to the full `http::Request` — headers, URI, method, extensions (where `AuthenticatedClient` lives after the `require_api_key` middleware runs), and the path.

1. Create a `RustFlowMakeSpan` struct that implements `MakeSpan`
2. Generate a UUID `request_id` for every request
3. Extract the `AuthenticatedClient` name from request extensions (when present)
4. Extract entity IDs from URI path segments (when present)
5. Wire `RustFlowMakeSpan` into `TraceLayer` via `.make_span_with()`

## Step 1: Understanding the `Empty` Field Pattern

Before we write the `MakeSpan` implementation, we need to understand a fundamental tracing concept: **how to declare span fields that might not have a value**.

When you create a span with `tracing::debug_span!`, all fields must be declared upfront. You can't add new fields to a span after it's created — you can only *record values* for fields that were already declared. This is a deliberate design choice: the tracing system pre-allocates storage for span fields at creation time for performance.

But some fields are conditional:

- `client.name` — only present when the request passed through `require_api_key` middleware (authenticated endpoints). Public read endpoints like `GET /api/tasks` don't have it.
- `entity.id` — only present when the URI contains a path parameter like `/api/tasks/42`. List endpoints like `GET /api/tasks` don't have one.

The solution is `tracing::field::Empty`:

```rust
use tracing::field::Empty;

let span = tracing::debug_span!(
    "request",
    http.method = %method,
    http.uri = %uri,
    request_id = %uuid::Uuid::new_v4(),
    client.name = Empty,    // ← declared but no value yet
    entity.id = Empty,      // ← declared but no value yet
);
```

`Empty` is a sentinel value that means "this field exists in the span's schema, but it has no value right now." In the formatted output, empty fields are simply omitted — they don't appear as `client.name=` or `client.name=null`. They're invisible until you record a value.

### Recording Values Later

After creating the span, you can fill in empty fields using `span.record()`:

```rust
// If we found an authenticated client:
if let Some(client) = request.extensions().get::<AuthenticatedClient>() {
    span.record("client.name", &client.name.as_str());
}

// If we found an entity ID in the path:
if let Some(id) = extract_entity_id(uri) {
    span.record("entity.id", id.as_str());
}
```

If you *don't* call `span.record()`, the field stays empty and doesn't appear in the output. This is exactly the behavior we want for optional fields.

### Why Not Just Use `Option`?

You might wonder: why not pass `Option<&str>` directly?

```rust
// This doesn't work the way you'd expect:
let span = tracing::debug_span!(
    "request",
    client.name = client_name,  // Option<&str> → records "None" or "Some(admin)"
);
```

`tracing` will format the `Option` using `Debug`, producing `Some("admin")` or `None` as the field value. That's ugly and not what we want. The `Empty` pattern gives us clean output: the field either has a plain value (`client.name=admin`) or doesn't appear at all.

### The Pattern Summary

```rust
// 1. Declare all fields upfront — use Empty for optional ones
let span = tracing::debug_span!(
    "request",
    required_field = %value,
    optional_field = Empty,
);

// 2. Conditionally record values for Empty fields
if let Some(val) = maybe_value {
    span.record("optional_field", val);
}

// Result:
// - If maybe_value is Some("hello"): span shows optional_field=hello
// - If maybe_value is None: span omits optional_field entirely
```

This is the same pattern we used in 3.4 with `fields(task.id)` and `Span::current().record("task.id", task.id)` — but now we're applying it at the request span level, inside our custom `MakeSpan` implementation.


## Step 2: Implement `RustFlowMakeSpan`

Now let's build the custom `MakeSpan` implementation. This struct replaces `DefaultMakeSpan` and creates enriched per-request spans.

**Add to** `crates/rustflow-server/src/main.rs` — define the struct and implement the trait:

```rust name=crates/rustflow-server/src/main.rs
use http::Request;
use rustflow_common::AuthenticatedClient;
use tower_http::trace::MakeSpan;
use tracing::field::Empty;

/// Custom span factory for TraceLayer.
///
/// For every incoming HTTP request, creates a span with:
/// - `http.method` and `http.uri` (always present)
/// - `request_id` — a unique UUID v4 for correlating all events in this request
/// - `client.name` — the authenticated client's name (if present in extensions)
/// - `entity.id` — the entity ID from the URI path (if present)
#[derive(Debug, Clone)]
struct RustFlowMakeSpan;

impl<B> MakeSpan<B> for RustFlowMakeSpan {
    fn make_span(&mut self, request: &Request<B>) -> tracing::Span {
        // Generate a unique ID for this request — correlates all log lines
        let request_id = uuid::Uuid::new_v4().to_string();

        // Create the span with all fields declared upfront.
        // Optional fields use Empty — they'll be filled in below if available.
        let span = tracing::debug_span!(
            "request",
            http.method = %request.method(),
            http.uri = %request.uri(),
            request_id = %request_id,
            client.name = Empty,
            entity.id = Empty,
        );

        // ── Extract authenticated client name ───────────────
        // The require_api_key middleware inserts AuthenticatedClient into
        // request extensions for protected routes. Public routes won't have it.
        if let Some(client) = request.extensions().get::<AuthenticatedClient>() {
            span.record("client.name", &client.name.as_str());
        }

        // ── Extract entity ID from path ─────────────────────
        // For URIs like /api/tasks/42 or /api/projects/5, extract the
        // numeric segment after the resource name.
        if let Some(id) = extract_entity_id(request.uri().path()) {
            span.record("entity.id", id.as_str());
        }

        span
    }
}
```

### Anatomy of the Implementation

Let's break down each piece.

**The struct itself** is a zero-sized type — no fields, no state. It implements `Clone` and `Debug` because `TraceLayer` requires its `MakeSpan` to be cloneable (Tower clones services per connection). A unit struct is the simplest option.

```rust
#[derive(Debug, Clone)]
struct RustFlowMakeSpan;
```

You could also use a closure instead of a struct (we'll discuss that in the exercises), but a named struct is clearer and easier to test.

**The `request_id`** is a UUID v4 — a 128-bit random identifier. Every request gets a unique one. This is the single most valuable field for debugging: when a user reports "my request failed," you can search logs for their `request_id` and see every event from that exact request.

```rust
let request_id = uuid::Uuid::new_v4().to_string();
```

We convert to `String` because `tracing` span fields need owned or static data. The `uuid` crate is already in our workspace dependencies — we've been using it since Section 2 for generating task IDs.

**The span creation** declares all five fields upfront:

```rust
let span = tracing::debug_span!(
    "request",
    http.method = %request.method(),
    http.uri = %request.uri(),
    request_id = %request_id,
    client.name = Empty,
    entity.id = Empty,
);
```

- `http.method` and `http.uri` — always available from the request
- `request_id` — always available (we just generated it)
- `client.name` — declared as `Empty`, filled in conditionally below
- `entity.id` — declared as `Empty`, filled in conditionally below

The `%` sigil means "format with `Display`." The `debug_span!` macro creates a span at `DEBUG` level — matching `DefaultMakeSpan`'s behavior so our `EnvFilter` (`tower_http=debug`) continues to work.

**The client name extraction** reads from request extensions:

```rust
if let Some(client) = request.extensions().get::<AuthenticatedClient>() {
    span.record("client.name", &client.name.as_str());
}
```

`AuthenticatedClient` is defined in `rustflow-common` and inserted into request extensions by the `require_api_key` middleware in `middleware.rs`. For protected routes (POST, PUT, DELETE), the client will be present. For public routes (GET), it won't be — and the field stays empty.

### Important: When Is `AuthenticatedClient` Available?

There's a subtlety here. The `require_api_key` middleware runs *inside* the router — it's applied per-route-group via `.layer()`. But `TraceLayer` (and therefore `RustFlowMakeSpan`) runs *outside* the router — it's a global layer applied after `.with_state()`.

The middleware execution order is:

```text
Request arrives
    │
    ▼
┌─────────────┐
│    CORS      │  ← outermost
└──────┬──────┘
       │
       ▼
┌─────────────────────────┐
│  TraceLayer              │  ← RustFlowMakeSpan runs HERE
│  (creates request span)  │
└──────┬──────────────────┘
       │
       ▼
┌─────────────┐
│   Router     │  ← routes to the correct handler group
└──────┬──────┘
       │
       ▼
┌──────────────────┐
│  require_api_key  │  ← inserts AuthenticatedClient HERE
└──────┬───────────┘
       │
       ▼
  (handler)
```

`RustFlowMakeSpan` runs *before* `require_api_key`. So when `make_span()` checks `request.extensions().get::<AuthenticatedClient>()`, the client **hasn't been inserted yet** — the extension won't be there, even for authenticated requests.

This means `client.name` will always be `Empty` in the request span when using this approach. The field is still useful as a placeholder — and there are two ways to fill it in:

1. **Record it from the handler** — after `require_api_key` runs, the handler can access `Span::current()` and record the client name into the parent request span. This is what we'll do.
2. **Move auth before TraceLayer** — restructure the middleware stack so authentication runs before tracing. This is more complex and couples concerns we want to keep separate.

The first approach is simpler and follows the same `Empty` → `record()` pattern we used for `task.id` in lesson 3.4. Let's see how it works.

### Recording `client.name` from Handlers

Since `require_api_key` runs after `RustFlowMakeSpan`, we need to record the client name from inside the handler — where the `AuthenticatedClient` extension is available.

The handlers already have access to the authenticated client via `Extension(client): Extension<AuthenticatedClient>`. We just need to record it into the *parent* span (the request span created by `RustFlowMakeSpan`):

```rust
#[tracing::instrument(name = "task.create", skip_all, fields(task.id))]
async fn create(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    // Record the client name into the request span (parent of task.create)
    tracing::Span::current()
        .parent()
        .map(|parent| parent.record("client.name", client.name.as_str()));

    // ... rest of handler unchanged ...
}
```

`Span::current()` returns the `task.create` span (the innermost active span). `.parent()` returns the `request` span created by `RustFlowMakeSpan`. We record `client.name` there so it appears on the request-level span — visible on every event in the request lifecycle.

Alternatively, you can use a simpler approach — record it on the *current* span and let the span hierarchy carry the context:

```rust
// Simpler: record on the current span's parent via Span::current()
// The tracing output will show client.name on the request span
Span::current().record("client.name", client.name.as_str());
```

Wait — that records on `task.create`, not on `request`. If you want it on the request span specifically, you need the `.parent()` approach. But in practice, the client name appearing on the operation span is equally useful — it's visible in the same log line.

The cleanest pattern is to record it in a small middleware or at the start of each protected handler. Since we already have `tracing::info!(client.name = %client.name, ...)` in our handlers from 3.4, the information is already in the log output. The request span's `client.name` field is an *additional* convenience for filtering and correlation.

For this lesson, we'll keep the `client.name = Empty` declaration in `RustFlowMakeSpan` and show how to record it from handlers. In a production system, you might create a small middleware that runs after `require_api_key` and records the client name into the current span — but that's an exercise for later.


## Step 3: Extract Entity IDs from the URI Path

The `extract_entity_id` helper function parses the URI path to find numeric entity IDs. This is a simple heuristic: look for path segments that are purely numeric.

**Add to** `crates/rustflow-server/src/main.rs`:

```rust name=crates/rustflow-server/src/main.rs
/// Extracts the first numeric path segment from a URI path.
///
/// Examples:
///   "/api/tasks/42"       → Some("42")
///   "/api/projects/5"     → Some("5")
///   "/api/tasks"          → None
///   "/api/tasks/42/users" → Some("42")
///   "/health"             → None
fn extract_entity_id(path: &str) -> Option<String> {
    path.split('/')
        .find(|segment| !segment.is_empty() && segment.chars().all(|c| c.is_ascii_digit()))
        .map(|s| s.to_string())
}
```

### How It Works

The function splits the URI path on `/` and looks for the first segment that is entirely numeric:

```text
"/api/tasks/42"
  → ["", "api", "tasks", "42"]
  → "42" is all digits → Some("42")

"/api/tasks"
  → ["", "api", "tasks"]
  → no all-digit segment → None

"/api/projects/5/tasks/42"
  → ["", "api", "projects", "5", "tasks", "42"]
  → "5" is the first all-digit segment → Some("5")
```

This is a heuristic — it doesn't know the routing structure. For RustFlow's current routes, it works well:

| URI | `entity.id` |
|---|---|
| `GET /api/tasks` | (empty) |
| `GET /api/tasks/42` | `42` |
| `POST /api/tasks` | (empty) |
| `PUT /api/tasks/42` | `42` |
| `DELETE /api/tasks/42` | `42` |
| `GET /api/projects/5` | `5` |
| `GET /health` | (empty) |
| `GET /` | (empty) |

For nested resources like `/api/projects/5/tasks/42`, it captures the *first* numeric ID (`5`). This is a reasonable default — the primary resource is usually the first ID in the path. If you need both IDs, you could extend the function to return all numeric segments, but for now one is sufficient.

### Why Not Use Axum's Path Extractor?

You might wonder: Axum already parses path parameters with `Path(id): Path<u64>`. Why not use that?

Because `MakeSpan` runs *before* routing. At the point where `make_span()` is called, Axum hasn't matched the request to a route yet — it doesn't know which path parameters exist. The raw URI path is all we have. Axum's `Path` extractor only works inside handlers, after routing is complete.

This is a fundamental constraint of the `TraceLayer` architecture: the span is created before the request enters the router. Any information we want in the span must come from the raw `http::Request` — headers, URI, method, and extensions.


## Step 4: Wire `RustFlowMakeSpan` into `TraceLayer`

Now connect the custom span factory to `TraceLayer` in the `build_app` function.

**Update** `crates/rustflow-server/src/main.rs` — replace `TraceLayer::new_for_http()` with a configured version:

### Before (3.3/3.4)

```rust
let app: Router = Router::new()
    .merge(static_router)
    .merge(infra_router)
    .nest("/api", api_router)
    .with_state(state.clone())
    // TraceLayer: automatic span per request + response event (status, latency)
    .layer(TraceLayer::new_for_http())
    // CORS outermost — OPTIONS preflights handled before tracing
    .layer(cors);
```

### After (3.5)

```rust
let app: Router = Router::new()
    .merge(static_router)
    .merge(infra_router)
    .nest("/api", api_router)
    .with_state(state.clone())
    // TraceLayer with custom span factory — enriched per-request spans
    .layer(
        TraceLayer::new_for_http()
            .make_span_with(RustFlowMakeSpan)
    )
    // CORS outermost — OPTIONS preflights handled before tracing
    .layer(cors);
```

### What Changed

One method call: `.make_span_with(RustFlowMakeSpan)`. This tells `TraceLayer` to use our `RustFlowMakeSpan` struct instead of `DefaultMakeSpan` when creating per-request spans.

Everything else about `TraceLayer` stays the same:
- `DefaultOnRequest` still emits the "started processing request" event
- `DefaultOnResponse` still emits the "finished processing request" event with status and latency
- `DefaultOnFailure` still handles error cases

We only replaced the span creation — the response/failure callbacks use the span we created, so they automatically inherit our enriched fields.

### The `.make_span_with()` Method

`TraceLayer` uses a builder pattern for customization:

```rust
TraceLayer::new_for_http()
    .make_span_with(/* MakeSpan implementation */)
    .on_request(/* OnRequest implementation */)
    .on_response(/* OnResponse implementation */)
    .on_failure(/* OnFailure implementation */)
```

Each method replaces one callback. You can customize any combination — we're only replacing `make_span_with` and keeping the defaults for everything else. In a future lesson, you might customize `on_response` to log additional fields or `on_failure` to emit alerts.

The argument to `.make_span_with()` can be:
- A struct implementing `MakeSpan<B>` (what we're doing)
- A closure `Fn(&http::Request<B>) -> tracing::Span` (simpler but less reusable)

We chose a struct because it's self-documenting, testable, and can be extended later (e.g., adding configuration fields).

// ── Application builder ─────────────────────────────────────

fn build_app(state: &AppState) -> Router {
    let cors: CorsLayer = CorsLayer::new()
        .allow_origin(
            state
                .config
                .cors_origins
                .iter()
                .filter_map(|o| o.parse::<HeaderValue>().ok())
                .collect::<Vec<_>>(),
        )
        .allow_methods([
            Method::GET,
            Method::POST,
            Method::PUT,
            Method::DELETE,
            Method::PATCH,
        ])
        .allow_headers([
            HeaderName::from_static("content-type"),
            HeaderName::from_static("x-api-key"),
        ])
        .expose_headers([HeaderName::from_static("x-authenticated-as")])
        .max_age(Duration::from_secs(3600));

    let static_router: Router<AppState> = Router::new()
        .route_service(
            "/",
            ServeFile::new("crates/rustflow-server/static/index.html"),
        )
        .nest_service(
            "/static",
            ServeDir::new("crates/rustflow-server/static")
                .append_index_html_on_directories(true),
        )
        .route_service(
            "/favicon.ico",
            ServeFile::new("crates/rustflow-server/static/favicon.ico"),
        );

    let infra_router: Router<AppState> = routes::health::router();

    let api_router: Router<AppState> = Router::new()
        .nest("/tasks", routes::tasks::router(state.clone()))
        .nest("/projects", routes::projects::router(state.clone()))
        .nest("/users", routes::users::router(state.clone()))
        .nest(
            "/enrichment",
            rate_limited(routes::enrichment::router(), 10, Duration::from_secs(10)),
        )
        .layer(
            ServiceBuilder::new()
                .layer(
                    CompressionLayer::new()
                        .compress_when(DefaultPredicate::new().and(SizeAbove::new(512))),
                )
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    request_counter,
                )),
        );

    let app: Router = Router::new()
        .merge(static_router)
        .merge(infra_router)
        .nest("/api", api_router)
        .with_state(state.clone())
        // TraceLayer with custom span factory — enriched per-request spans
        .layer(
            TraceLayer::new_for_http()
                .make_span_with(RustFlowMakeSpan)
        )
        .layer(cors);

    app
}

## Step 7: Understanding the Full Span Hierarchy After 3.5

With `RustFlowMakeSpan` in place, the complete span hierarchy for a request looks like this:

### Authenticated Write: `POST /api/tasks`

```text
request{http.method=POST http.uri="/api/tasks" request_id=a1b2... client.name=admin}
  └── task.create{task.id=4}
        ├── INFO "task created" (task.id=4, client.name=admin)
        └── (span closes → duration recorded)
  └── on_response: status=201, latency=2ms
```

Three levels of information:
1. **Request span** — who, what, and a unique ID
2. **Operation span** — which handler, which entity
3. **Events** — what happened inside the operation

### Public Read: `GET /api/tasks/42`

```text
request{http.method=GET http.uri="/api/tasks/42" request_id=b2c3... entity.id=42}
  └── task.get{task.id=42}
        └── (span closes → duration recorded)
  └── on_response: status=200, latency=0ms
```

The `entity.id=42` appears on both the request span (from `extract_entity_id`) and the operation span (from `#[instrument(fields(task.id = %id))]`). This redundancy is intentional — you can filter at either level.

### Health Check: `GET /health`

```text
request{http.method=GET http.uri="/health" request_id=c3d4...}
  └── on_response: status=200, latency=0ms
```

No `client.name`, no `entity.id`, no operation span (health handler isn't instrumented). Just the request span with a unique ID. Even health checks are traceable.

### The Span Field Summary

| Field | Source | Always Present? | Example |
|---|---|---|---|
| `http.method` | `request.method()` | Yes | `GET`, `POST`, `DELETE` |
| `http.uri` | `request.uri()` | Yes | `/api/tasks/42` |
| `request_id` | `Uuid::new_v4()` | Yes | `a1b2c3d4-e5f6-...` |
| `client.name` | `AuthenticatedClient` extension | No — only authenticated requests | `admin` |
| `entity.id` | URI path parsing | No — only when path has numeric segment | `42` |

## Key Takeaways

1. **`DefaultMakeSpan` is a starting point, not the destination.** It gives you method and URI — enough to get started. But production services need request IDs, client identity, and domain-specific context. The `MakeSpan` trait lets you replace the default with exactly what you need.

2. **`tracing::field::Empty` is the pattern for optional span fields.** Declare all fields upfront (tracing requires this for performance), use `Empty` for fields that might not have a value, and call `span.record()` to fill them in when the value becomes available. Empty fields are silently omitted from output — no `null`, no empty strings.

3. **Request IDs are the single most valuable observability field.** A UUID per request lets you trace every event from a single request across interleaved concurrent output. When a user reports a problem, the `request_id` is the key that unlocks the full story.

4. **Middleware ordering affects what's available in `MakeSpan`.** `TraceLayer` runs before the router and its middleware. `AuthenticatedClient` is inserted by `require_api_key` inside the router. So `MakeSpan` can't see it — you need to record it later from the handler. Understanding the layer execution order is critical for designing your span fields.

5. **Entity IDs in request spans enable powerful filtering.** "Show me everything that happened to task 42" becomes a simple log search for `entity.id=42`. This is especially valuable when debugging issues with specific resources — you see every request that touched that entity, across all operation types.

6. **A struct implementing `MakeSpan` is cleaner than a closure for non-trivial logic.** Closures work for simple cases, but a named struct is self-documenting, testable, and extensible. You can add configuration fields later (e.g., whether to extract entity IDs) without changing the `TraceLayer` wiring.

7. **The `Empty` → `record()` pattern appears at every level.** We used it in 3.4 for `task.id` in operation spans (`fields(task.id)` → `Span::current().record()`). Now we use it in 3.5 for `client.name` and `entity.id` in request spans. It's the universal pattern for deferred or conditional span fields in the tracing ecosystem.

    ```rust
    fn extract_entity_ids(path: &str) -> Vec<String> {

            .filter(|s| !s.is_empty() && s.chars().all(|c| c.is_ascii_digit()))
            .map(|s| s.to_string())
            .collect()
    }
    ```
