# 3.4 — Timing Spans for Store Operations

## Overview

After lesson 3.3, every HTTP request to RustFlow gets a `TraceLayer` span that records the method, URI, status code, and total latency. That's great for answering "how long did this request take?" — but it tells you nothing about *where* the time was spent.

Consider a `POST /api/tasks` request that takes 15ms. Where did those 15ms go?

- Was it the lock acquisition on `state.tasks`?
- Was it the duplicate-title check iterating over all tasks?
- Was it serializing the response?
- Was it somewhere in the middleware stack?

With only the `TraceLayer` span, you see this:

```text
2026-01-15T10:30:01.456Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=15 ms status=201
```

Fifteen milliseconds, somewhere. That's like a doctor saying "you're sick" without telling you what's wrong.

What we need is **operation-level timing** — a span that wraps each individual handler function, so we can see how long `task.create` took versus `task.list` versus `project.delete`. If a request is slow, we want to know *which operation* inside it is the bottleneck.

### The Manual Approach (Don't Do This)

You might be tempted to add manual timing:

```rust
async fn create(/* ... */) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    let start = std::time::Instant::now();
    
    // ... handler logic ...
    
    tracing::debug!("task.create took {}μs", start.elapsed().as_micros());
    Ok((StatusCode::CREATED, Json(task)))
}
```

This works, but it's tedious and error-prone:

- You have to add `Instant::now()` and `elapsed()` to every handler
- Early returns (from `?` or `return Err(...)`) skip the timing log
- The timing event is a standalone log line — it's not a *span*, so it doesn't nest inside the request span or carry structured fields
- You're back to the same "two separate concerns" problem we solved in 3.3

We already removed manual timing from middleware in 3.3. Let's not reintroduce it in handlers.

### The `#[tracing::instrument]` Approach

The `tracing` crate provides a procedural macro — `#[tracing::instrument]` — that does exactly what we need:

```rust
#[tracing::instrument(name = "task.create", skip_all)]
async fn create(/* ... */) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    // ... handler logic unchanged ...
}
```

When this function is called, `#[instrument]` automatically:

1. **Creates a named span** — `task.create` — and enters it
2. **Records the span's duration** — when the function returns (including early returns via `?`), the span exits and the subscriber records how long it was open
3. **Nests inside the parent span** — if there's an active `TraceLayer` request span, the `task.create` span becomes a child of it

No `Instant::now()`. No manual `elapsed()`. No risk of missing early returns. The macro handles everything, and the subscriber records the duration automatically.

### The Span Hierarchy

After this lesson, every request will have a two-level span hierarchy:

```text
request{method=POST uri="/api/tasks"}          ← TraceLayer (3.3)
  └── task.create{task.id=4}                   ← #[instrument] (3.4)
        ├── INFO "task created"                ← tracing::info! event
        └── (span closes → duration recorded)
```

The outer span tells you "a POST to /api/tasks took 15ms." The inner span tells you "the `task.create` operation inside that request took 12ms." The difference (3ms) is overhead — routing, middleware, serialization.

For read operations:

```text
request{method=GET uri="/api/tasks"}
  └── task.list{}
        └── (span closes → duration recorded)

request{method=GET uri="/api/tasks/42"}
  └── task.get{task.id=42}
        └── (span closes → duration recorded)
```

This hierarchy is the foundation of distributed tracing. In lesson 3.8, when we export spans to Jaeger, each of these nested spans becomes a node in the trace waterfall — you'll visually see how time is distributed across operations.

### Span Naming Conventions

We'll use a `domain.operation` naming convention for all operation spans:

| Span Name | Handler | Description |
|---|---|---|
| `task.list` | `tasks::list` | List/filter tasks |
| `task.create` | `tasks::create` | Create a new task |
| `task.get` | `tasks::get_one` | Get a single task by ID |
| `task.update` | `tasks::update` | Replace a task |
| `task.delete` | `tasks::delete` | Delete a task |
| `task.change_status` | `tasks::change_status` | Update task status |
| `project.list` | `projects::list` | List all projects |
| `project.get` | `projects::get_one` | Get a single project by ID |
| `project.create` | `projects::create` | Create a new project |
| `project.delete` | `projects::delete` | Delete a project |
| `user.list` | `users::list` | List all users |
| `user.get` | `users::get_one` | Get a single user by ID |
| `user.create` | `users::create` | Create a new user |
| `user.delete` | `users::delete` | Delete a user |

This convention is deliberate:

- **Dot-separated** — `task.create` not `task_create` or `createTask`. Dots are the standard separator in observability tools (Jaeger, Datadog, Prometheus). They enable hierarchical grouping: filter by `task.*` to see all task operations.
- **Domain first** — `task.create` not `create.task`. When you sort spans alphabetically, all task operations group together. In Jaeger's trace view, this makes it easy to spot which domain is slow.
- **Lowercase** — consistent with tracing conventions and the `tower_http` span names.

### What We'll Build in This Lesson

1. Add `#[tracing::instrument]` to every handler in `tasks.rs`, `projects.rs`, and `users.rs`
2. Use the `name` parameter to set the `domain.operation` span name

4. Use `fields(...)` to include entity IDs as structured span attributes

## Step 1: Understanding `#[tracing::instrument]`

Before we start adding the attribute to handlers, let's understand exactly what it does and the parameters we'll use.

### The Basic Form

```rust
#[tracing::instrument]
async fn my_function(x: i32, y: String) -> bool {
    // ...
}
```

This creates a span named `my_function` (the function name) with fields for every argument: `x=42, y="hello"`. When the function is called, the span is entered. When it returns, the span exits.

For our handlers, the basic form has problems:

1. **The function name isn't descriptive enough.** `list` doesn't tell you *what* is being listed. We want `task.list`.
2. **All arguments are recorded.** Handler arguments include `State(state)` — the entire `AppState` with all its `Arc<RwLock<...>>` stores. Recording that would produce enormous, useless span fields.
3. **Some arguments can't be recorded.** Types that don't implement `fmt::Debug` cause compilation errors.

So we'll use several parameters to customize the behavior.

### The `name` Parameter

```rust
#[tracing::instrument(name = "task.list")]
async fn list(/* ... */) { /* ... */ }
```

Overrides the default span name (function name) with a custom string. This is how we get our `domain.operation` naming convention. Without `name`, the span would be called `list` — ambiguous when you have `tasks::list`, `projects::list`, and `users::list`.

### The `skip_all` Parameter

```rust
#[tracing::instrument(name = "task.list", skip_all)]
async fn list(State(state): State<AppState>, /* ... */) { /* ... */ }
```

Tells `#[instrument]` to skip recording *all* function arguments as span fields. This is essential for Axum handlers because:

- `State(state)` contains the entire application state — recording it would be massive and meaningless
- `Extension(client)` contains the authenticated client — we might want to record the name, but not the whole struct
- `ValidatedJson(payload)` / `Json(payload)` contain the request body — potentially large
- `Path(id)` is the one we *do* want — but we'll add it back explicitly with `fields`

`skip_all` is the nuclear option: skip everything, then selectively add back what matters. This is cleaner than listing every argument to skip individually.

### The `fields` Parameter

```rust
#[tracing::instrument(name = "task.get", skip_all, fields(task.id = %id))]
async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Task>, RustFlowError> {
    // ...
}
```

Adds custom fields to the span. `fields(task.id = %id)` means:

- Create a span field named `task.id`
- Set its value to the `id` function parameter, formatted with `Display` (the `%` sigil)

The `%` prefix tells tracing to use the `Display` trait to format the value. You can also use `?` for `Debug` formatting, or omit the sigil for types that implement `tracing::Value` directly (integers, strings, bools).

For our handlers, we'll include entity IDs when they're available:

```rust
// Operations that target a specific entity — include the ID
#[tracing::instrument(name = "task.get", skip_all, fields(task.id = %id))]
#[tracing::instrument(name = "task.update", skip_all, fields(task.id = %id))]
#[tracing::instrument(name = "task.delete", skip_all, fields(task.id = %id))]

// Operations that don't target a specific entity — no ID field
#[tracing::instrument(name = "task.list", skip_all)]
```

### The `level` Parameter

```rust
#[tracing::instrument(name = "task.list", skip_all, level = "debug")]
```

Sets the span's verbosity level. The default is `INFO`. For handler spans, `INFO` is appropriate — these are meaningful operations you want to see in production. But if you had a very high-frequency internal function, you might use `level = "debug"` or `level = "trace"` to keep it quiet unless explicitly enabled.

We'll use the default (`INFO`) for all handler spans, so we won't specify `level` explicitly.

### Recording Fields After Creation

Sometimes you don't know a field's value when the span is created. For example, `task.create` doesn't know the new task's ID until *after* the task is inserted into the store. You can record a field later using `tracing::Span::current()`:

```rust
#[tracing::instrument(name = "task.create", skip_all, fields(task.id))]
async fn create(/* ... */) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    // ... create the task ...
    let task = Task { id: store.next_id, /* ... */ };
    
    // Record the ID now that we know it
    tracing::Span::current().record("task.id", task.id);
    
    Ok((StatusCode::CREATED, Json(task)))
}
```

The `fields(task.id)` declaration without a value creates an *empty* field — a placeholder. The `Span::current().record(...)` call fills it in later. This is how we handle create operations where the ID is generated during execution.


## Step 2: Instrument Task Handlers

**Update** `crates/rustflow-server/src/routes/tasks.rs` — add `#[tracing::instrument]` to every handler function.

### `list` — List/Filter Tasks

```rust name=crates/rustflow-server/src/routes/tasks.rs
#[tracing::instrument(name = "task.list", skip_all)]
async fn list(
    auth: Option<Extension<AuthenticatedClient>>,
    State(state): State<AppState>,
    ValidatedQuery(filter): ValidatedQuery<TaskFilter>,
) -> Json<Vec<Task>> {
    if let Some(Extension(client)) = auth {
        tracing::debug!(client.name = %client.name, "authenticated client listing tasks");
    }
    let state = state.tasks.0.read().await;

    let filtered: Vec<Task> = state
        .tasks
        .iter()
        .filter(|task| filter.status.as_ref().map_or(true, |s| &task.status == s))
        .filter(|task| {
            filter
                .priority
                .as_ref()
                .map_or(true, |p| &task.priority == p)
        })
        .filter(|task| {
            filter.search.as_ref().map_or(true, |s| {
                task.title.contains(s) || task.description.as_ref().map_or(false, |d| d.contains(s))
            })
        })
        .cloned()
        .collect();

    tracing::debug!(count = filtered.len(), "tasks listed");
    Json(filtered)
}
```

What changed:
- Added `#[tracing::instrument(name = "task.list", skip_all)]`
- Replaced the `println!` with `tracing::debug!` using structured fields
- Added a `tracing::debug!` at the end to log how many tasks were returned

The `skip_all` is critical here — without it, `#[instrument]` would try to record `State(state)`, `ValidatedQuery(filter)`, and `Option<Extension<AuthenticatedClient>>` as span fields. The state object is enormous, and the extractors may not implement `Debug` in a useful way.

### `get_one` — Get a Single Task

```rust name=crates/rustflow-server/src/routes/tasks.rs
#[tracing::instrument(name = "task.get", skip_all, fields(task.id = %id))]
async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Task>, RustFlowError> {
    let store = state.tasks.0.read().await;

    store
        .tasks
        .iter()
        .find(|task| task.id == id)
        .cloned()
        .map(Json)
        .ok_or(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
}
```

The `fields(task.id = %id)` captures the task ID from the `Path(id)` extractor. In the trace output, you'll see:

```text
request{method=GET uri="/api/tasks/42"}: task.get{task.id=42}: ...
```

Now you can search your logs for `task.id=42` and find every operation that touched task 42 — gets, updates, deletes, status changes.

### `create` — Create a New Task

```rust name=crates/rustflow-server/src/routes/tasks.rs
#[tracing::instrument(name = "task.create", skip_all, fields(task.id))]
async fn create(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if store.tasks.iter().any(|x| payload.title == x.title) {
        return Err(RustFlowError::Conflict(format!(
            "Task with title {} already exists",
            payload.title
        )));
    }

    let task = Task {
        id: store.next_id,
        title: payload.title,
        description: payload.description,
        priority: payload.priority,
        status: TaskStatus::Pending,
    };

    store.next_id += 1;
    store.tasks.push(task.clone());

    // Record the task ID now that we know it
    tracing::Span::current().record("task.id", task.id);
    tracing::info!(
        task.id = task.id,
        client.name = %client.name,
        "task created"
    );

    Ok((StatusCode::CREATED, Json(task)))
}
```

Notice the pattern for create operations:

1. `fields(task.id)` — declares the field *without* a value (empty placeholder)
2. After the task is created: `tracing::Span::current().record("task.id", task.id)` — fills in the value
3. The `tracing::info!` event also includes `task.id` and `client.name` as structured fields

The `println!("[audit] Task {} created by client '{}'", task.id, client.name)` is replaced with a structured `tracing::info!` call. The information is the same, but now it's structured data — searchable, filterable, and associated with the `task.create` span.

### `update` — Replace a Task

```rust name=crates/rustflow-server/src/routes/tasks.rs
#[tracing::instrument(name = "task.update", skip_all, fields(task.id = %id))]
async fn update(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<Json<Task>, RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if let Some(task) = store.tasks.iter_mut().find(|task| task.id == id) {
        task.title = payload.title;
        task.description = payload.description;
        task.priority = payload.priority;
        tracing::info!(client.name = %client.name, "task updated");
        Ok(Json(task.clone()))
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
    }
}
```

The `task.id` is known upfront (from the path parameter), so it's set directly in `fields(task.id = %id)`. The `println!` is replaced with `tracing::info!`.

### `delete` — Delete a Task

```rust name=crates/rustflow-server/src/routes/tasks.rs
#[tracing::instrument(name = "task.delete", skip_all, fields(task.id = %id))]
async fn delete(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, RustFlowError> {
    let mut store = state.tasks.0.write().await;
    let len_before = store.tasks.len();

    store.tasks.retain(|task| task.id != id);

    if store.tasks.len() < len_before {
        tracing::info!(client.name = %client.name, "task deleted");
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {id} does not exist"
        )))
    }
}
```

### `change_status` — Update Task Status


### The Complete Pattern

Every handler in `tasks.rs` now follows the same pattern:

```rust
#[tracing::instrument(name = "domain.operation", skip_all, fields(entity.id = %id))]
async fn handler_name(/* extractors */) -> /* return type */ {
    // ... business logic ...
    tracing::info!(/* structured fields */, "what happened");
    // ... return ...
}
```

- `name` = `domain.operation` naming convention
- `skip_all` = don't record extractor arguments
- `fields(...)` = include entity ID when available
- `tracing::info!` replaces `println!` for audit events

### `delete` — Delete a User

```rust name=crates/rustflow-server/src/routes/users.rs
#[tracing::instrument(name = "user.delete", skip_all, fields(user.id = %id))]
async fn delete(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, RustFlowError> {

    let len_before = store.users.len();
    store.users.retain(|user| user.id != id);

    if store.users.len() < len_before {
        tracing::info!("user deleted");
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(RustFlowError::NotFound(format!(
            "User with id {} not found",
            id
        )))
    }
}
```


## Step 5: How the Subscriber Records Span Duration

You might be wondering: where does the timing actually happen? We didn't write any timing code. There's no `Instant::now()`, no `elapsed()`, no duration calculation anywhere.

The answer is: **the subscriber does it automatically**.

When `#[instrument]` creates a span and the function is entered, the `fmt` subscriber (from `tracing-subscriber`) records the entry timestamp. When the function returns and the span is exited, the subscriber records the exit timestamp and calculates the duration. This duration appears in the span's metadata — visible in the formatted output and in exported traces (Jaeger, etc.).

### The Lifecycle of an Instrumented Call

```text
1. Handler function called
2. #[instrument] creates span: task.create{task.id=}
3. Span entered → subscriber records entry time
4. Function body executes
   - Lock acquired
   - Data written
   - tracing::info!("task created") emitted (inside the span)
   - Span::current().record("task.id", 4) fills in the field
5. Function returns Ok((StatusCode::CREATED, Json(task)))
6. Span exited → subscriber records exit time, calculates duration
7. Span dropped → subscriber may emit a "close" event (depending on configuration)
```

Steps 3 and 6 happen automatically. The subscriber sees every span enter/exit and tracks the timing. You don't need to opt into this — it's the default behavior of `tracing-subscriber`'s `fmt` layer.

### What About Early Returns?

This is one of the biggest advantages over manual timing. Consider:

```rust
#[tracing::instrument(name = "task.create", skip_all, fields(task.id))]
async fn create(/* ... */) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if store.tasks.iter().any(|x| payload.title == x.title) {
        return Err(RustFlowError::Conflict(/* ... */));  // ← early return
    }

    // ... rest of the function ...
}
```

With manual `Instant::now()` timing, the early `return` would skip the timing log at the end of the function. You'd have to add timing code before *every* return point — tedious and error-prone.

With `#[instrument]`, the span exits when the function returns — *regardless of how it returns*. Early returns, `?` operator, panics (via `Drop`) — the span always closes and the duration is always recorded. This is the power of RAII (Resource Acquisition Is Initialization) — the span's lifetime is tied to the function's scope.

### Seeing Duration in the Output

With the default `fmt` subscriber, span duration isn't printed as a separate field in the text output. Instead, you can observe it through:

1. **Timestamp differences** — the span's entry and exit events have different timestamps:

```text
2026-01-15T10:30:01.456Z DEBUG request{method=POST uri="/api/tasks"}: task.create{task.id=}: started
2026-01-15T10:30:01.458Z  INFO request{method=POST uri="/api/tasks"}: task.create{task.id=4}: task created
```

The 2ms gap between the span entry and the info event tells you the operation took at least 2ms.

2. **The `TraceLayer` response event** — shows the total request latency:

```text
2026-01-15T10:30:01.459Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=3 ms status=201
```

3. **Jaeger/OpenTelemetry** (lesson 3.8) — when we export spans, each span carries its exact duration. Jaeger's waterfall view shows this visually — you'll see the `task.create` span as a bar inside the `request` span, with precise millisecond timing.

For now, the timestamp-based approach gives you enough information. The real payoff comes in 3.8 when span durations become first-class data in the trace export.


## Step 6: Understanding Span Nesting

The most powerful aspect of `#[instrument]` is how operation spans nest inside `TraceLayer`'s request span. Let's trace through a complete request to see the full hierarchy.

### Example: `POST /api/tasks` (Create a Task)

```text
Client sends: POST /api/tasks
  Headers: x-api-key: rustflow-api-key-2026
  Body: {"title": "Learn tracing"}

1. CORS layer → pass through
2. TraceLayer creates span: request{method=POST uri="/api/tasks"}
3. Router matches /api/tasks → tasks::create handler
4. require_api_key middleware validates the API key, injects AuthenticatedClient
5. tasks::create is called
6. #[instrument] creates span: task.create{task.id=}
   ← This span is a CHILD of the request span
7. Handler body executes:
   - Write lock acquired
   - Duplicate check passes
   - Task created with id=4
   - Span::current().record("task.id", 4)
   - tracing::info!("task created") emitted
8. Handler returns Ok((201, Json(task)))
9. task.create span exits → duration recorded
10. TraceLayer emits response event: status=201, latency=3ms
11. request span exits → duration recorded
```

### The Output

```text
2026-01-15T10:30:01.456Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.458Z  INFO request{method=POST uri="/api/tasks"}: task.create{task.id=4}: rustflow_server::routes::tasks: task created
2026-01-15T10:30:01.459Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=3 ms status=201
```

Read the span context on the second line carefully:

```text
request{method=POST uri="/api/tasks"}: task.create{task.id=4}: rustflow_server::routes::tasks: task created
```

This shows the full span hierarchy:
1. `request{method=POST uri="/api/tasks"}` — the outer span from `TraceLayer`
2. `task.create{task.id=4}` — the inner span from `#[instrument]`
3. `rustflow_server::routes::tasks` — the module where the event was emitted
4. `task created` — the event message

The colon-separated chain is the span stack. Every event emitted inside the handler carries both spans as context. This is how you correlate "this task creation" with "this HTTP request."

### Example: `GET /api/tasks?status=pending` (List Tasks)

```text
2026-01-15T10:30:02.100Z DEBUG request{method=GET uri="/api/tasks?status=pending"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:02.101Z DEBUG request{method=GET uri="/api/tasks?status=pending"}: task.list{}: rustflow_server::routes::tasks: tasks listed count=3
2026-01-15T10:30:02.101Z DEBUG request{method=GET uri="/api/tasks?status=pending"}: tower_http::trace::on_response: finished processing request latency=1 ms status=200
```

The `task.list{}` span has no fields (no entity ID for list operations). The `count=3` field on the event tells you how many tasks matched the filter.

### Example: `GET /api/tasks/42` (Get a Specific Task)

```text
2026-01-15T10:30:03.200Z DEBUG request{method=GET uri="/api/tasks/42"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:03.200Z DEBUG request{method=GET uri="/api/tasks/42"}: task.get{task.id=42}: tower_http::trace::on_response: finished processing request latency=0 ms status=200
```

The `task.get{task.id=42}` span carries the entity ID. If you're debugging why task 42 is returning stale data, you can grep for `task.id=42` and find every operation that touched it.

### Example: `DELETE /api/tasks/99` (Task Not Found)

```text
2026-01-15T10:30:04.300Z DEBUG request{method=DELETE uri="/api/tasks/99"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:04.300Z DEBUG request{method=DELETE uri="/api/tasks/99"}: task.delete{task.id=99}: tower_http::trace::on_response: finished processing request latency=0 ms status=404
```

Even failed operations get spans. The `task.delete{task.id=99}` span tells you which task was targeted, and the `status=404` tells you it didn't exist. The span still records its duration — useful for detecting slow "not found" lookups that might indicate a performance issue (e.g., scanning a large list).

### The Complete Span Hierarchy Diagram

```text
┌─────────────────────────────────────────────────────────────┐
│  request{method=POST uri="/api/tasks"}     ← TraceLayer    │
│  Duration: 3ms (entire request lifecycle)                   │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  task.create{task.id=4}                ← #[instrument]│  │
│  │  Duration: 2ms (handler execution only)               │  │
│  │                                                       │  │
│  │  Events:                                              │  │
│  │    INFO "task created" task.id=4 client.name="admin"  │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
│  Events:                                                    │
│    DEBUG "started processing request"                       │
│    DEBUG "finished processing request" status=201 latency=3ms│
└─────────────────────────────────────────────────────────────┘
```

The outer span (3ms) includes routing, middleware, and serialization overhead. The inner span (2ms) is pure handler execution. The 1ms difference is framework overhead — useful for identifying whether slowness is in your code or in the middleware stack.

## Key Takeaways

1. **`#[tracing::instrument]` replaces manual timing code.** One attribute on a function gives you a named span with automatic duration recording. No `Instant::now()`, no `elapsed()`, no risk of missing early returns. The subscriber handles all timing automatically.

2. **`skip_all` + `fields(...)` is the right pattern for Axum handlers.** Skip all arguments (they include large state objects and extractors), then selectively add back the fields that matter — entity IDs, filter parameters, client names.

3. **`Span::current().record()` handles deferred field values.** For create operations where the entity ID isn't known until after insertion, declare an empty field in `fields(entity.id)` and fill it in later with `Span::current().record("entity.id", value)`.

4. **Operation spans nest inside request spans automatically.** When `#[instrument]` creates a span inside a `TraceLayer` request span, the tracing system automatically establishes a parent-child relationship. The formatted output shows the full span chain: `request{...}: task.create{...}: event message`.

5. **Dot-separated naming (`domain.operation`) is an observability convention.** It enables hierarchical filtering in tools like Jaeger (`task.*` shows all task operations) and keeps spans sorted by domain when listed alphabetically.

6. **Structured fields replace string interpolation.** Instead of `println!("[audit] Task {} created by client '{}'", id, name)`, use `tracing::info!(task.id = id, client.name = %name, "task created")`. The fields are machine-parseable, searchable, and automatically included in exported traces.

7. **Every handler gets a span — even for error paths.** A `task.delete{task.id=999}` span that results in a 404 is still valuable. It tells you someone tried to delete a non-existent task, how long the lookup took, and which task ID was targeted. Don't skip instrumentation for error cases.
