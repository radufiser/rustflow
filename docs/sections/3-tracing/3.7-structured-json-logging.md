# 3.7 — Structured JSON Logging

## Overview

Open the log file from the last lesson. What do you see?

```text
2026-01-15T10:30:01.456789Z DEBUG request{http.method=GET http.uri="/api/tasks" request_id=a1b2c3d4}: tower_http::trace::on_response: finished processing request latency=1 ms status=200
```

You can read that. A human can scan it, spot the `GET`, see the `200`, note the `1 ms` latency. It's designed for your eyes — and your eyes are good at this.

Now imagine you have 50 servers, each producing 10,000 log lines per minute. That's 500,000 lines per minute. You need to answer: "How many requests to `/api/tasks` returned a 500 in the last hour?" You're not reading half a million lines. You need a machine to do it.

The machine needs to *parse* each line. And here's the problem with human-readable logs: they're terrible to parse. Look at that line again:

```text
2026-01-15T10:30:01.456789Z DEBUG request{http.method=GET http.uri="/api/tasks" request_id=a1b2c3d4}: tower_http::trace::on_response: finished processing request latency=1 ms status=200
```

Where does the timestamp end? Where does the span context start? Is `latency=1 ms` one field or two? What's the delimiter between `request_id=a1b2c3d4` and the closing `}`? Every log aggregation tool would need a custom regex to parse this format — and that regex would break the moment `tracing-subscriber` changes its output format.

### The Solution: JSON

```json
{"timestamp":"2026-01-15T10:30:01.456789Z","level":"DEBUG","target":"tower_http::trace::on_response","fields":{"message":"finished processing request","latency":"1 ms","status":200},"span":{"name":"request","http.method":"GET","http.uri":"/api/tasks","request_id":"a1b2c3d4"},"spans":[{"name":"request","http.method":"GET","http.uri":"/api/tasks","request_id":"a1b2c3d4"}]}
```

One line. One JSON object. Every field is a named key with a typed value. Any JSON parser in any language can extract any field instantly. No regex. No guessing. No breakage when the format evolves.

This is what log aggregation systems expect:

| System | JSON Support |
|---|---|
| **Elasticsearch / ELK** | Native JSON ingestion — each key becomes a searchable field |
| **Datadog** | Auto-parses JSON logs, creates facets from keys |
| **Grafana Loki** | JSON parser pipeline stage extracts fields for filtering |
| **AWS CloudWatch** | JSON logs enable Metric Filters on specific fields |
| **Splunk** | Auto-extracts JSON fields as indexed fields |
| **Google Cloud Logging** | Structured JSON is the native format |

Every major log aggregation platform speaks JSON natively. When your logs are JSON, you get:

- **Searchable fields** — "Show me all requests where `status >= 500`" becomes a simple query, not a regex nightmare
- **Dashboards** — Plot `latency` over time, group by `http.method`, filter by `target`
- **Alerts** — "Alert me when `level=ERROR` and `target` contains `rustflow_server`"
- **Correlation** — Join logs from different services by `request_id` or `trace_id`

### The Development vs. Production Split

Here's the tension: JSON is great for machines but terrible for humans. Compare:

**Human-readable (development):**
```text
2026-01-15T10:30:01.456789Z  INFO rustflow_server::routes::tasks: task created task.id=4
```

**JSON (production):**
```json
{"timestamp":"2026-01-15T10:30:01.456789Z","level":"INFO","target":"rustflow_server::routes::tasks","fields":{"message":"task created","task.id":4}}
```

During development, you're staring at a terminal. You want colors, alignment, and scannable text. In production, nobody reads logs in a terminal — they go to Datadog or Kibana. You want structured data.

The solution: make the output format **toggleable**. Human-readable by default (development), JSON when configured (production). A single config flag or environment variable switches between them.

### The Type System Challenge

This sounds simple — just call `.json()` on the fmt layer, right?

```rust
// Human-readable:
let layer = tracing_subscriber::fmt::layer();

// JSON:
let layer = tracing_subscriber::fmt::layer().json();
```

The problem: `.json()` **changes the type** of the layer. These two layers have different Rust types:

```rust
// Human-readable layer type (simplified):
fmt::Layer<Registry, DefaultFields, Format<Full>>

// JSON layer type:
fmt::Layer<Registry, JsonFields, Format<Json>>
```

You can't do this:

```rust
// ❌ Won't compile — different types
let layer = if json_mode {
    tracing_subscriber::fmt::layer().json()    // type A
} else {
    tracing_subscriber::fmt::layer()           // type B
};
```

Rust's `if` expression requires both branches to return the same type. This is a fundamental constraint of Rust's type system — and it's actually a feature, not a bug. The compiler knows exactly what type each layer is, which enables zero-cost abstraction.

But we need to work around it. The solution uses the same `Option<Layer>` pattern from lesson 3.6: create **two** layers, wrap each in `Option`, and add both to the registry. Only one will be `Some` at a time.

## Step 1: Enable the `json` Feature on `tracing-subscriber`

The JSON formatter is behind a feature flag in `tracing-subscriber`. It's not included by default because it pulls in `serde` and `serde_json` as dependencies — which you don't need if you're only using human-readable output.

**Update** `Cargo.toml` (workspace root) — add the `json` feature:

```toml name=Cargo.toml
[workspace.dependencies]
# ... existing dependencies ...
tracing-subscriber = { version = "0.3", features = ["fmt", "env-filter", "json"] }
```

### Why a Feature Flag?

`tracing-subscriber` is modular by design:

| Feature | What It Enables | Dependencies Added |
|---|---|---|
| `fmt` | Human-readable formatting (`fmt::Layer`) | Minimal |
| `env-filter` | `EnvFilter` for `RUST_LOG` parsing | `regex`, `matchers` |
| `json` | JSON formatting (`.json()` method) | `serde`, `serde_json`, `tracing-serde` |
| `ansi` | ANSI color codes in terminal output | `ansi_term` |

We already had `fmt` and `env-filter` from lesson 3.1. Now we add `json`. The `serde` and `serde_json` dependencies are already in our workspace (we use them for request/response serialization), so the additional compile-time cost is minimal — `tracing-subscriber` just needs `tracing-serde` to bridge between tracing events and serde's serialization model.

Without the `json` feature, calling `.json()` on a fmt layer produces a compile error:

```text
error[E0599]: no method named `json` found for struct `Layer` in the current scope
  --> rustflow-common/src/tracing.rs:42:10
   |
42 |         .json()
   |          ^^^^ method not found
   |
   = note: the method exists but the following trait bounds were not satisfied:
           `tracing_subscriber::fmt::Layer<...>: ...`
   help: the following trait is implemented but not in scope; perhaps add a `use` for it:
           `use tracing_subscriber::fmt::format::json;`
```

The error message is misleading — it's not a missing `use`, it's a missing feature flag. This is a common gotcha.


## Step 2: Add `json_output` to `TracingConfig`

**Update** `crates/rustflow-common/src/tracing.rs` — extend the config struct:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;

/// Configuration for the tracing subsystem.
///
/// Controls which layers are active in the subscriber pipeline.
/// Passed to [`init_tracing()`] at application startup.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    ///
    /// - `Some(path)` — enable file logging to this directory
    /// - `None` — stdout only, no file logging
    pub log_directory: Option<PathBuf>,

    /// Use JSON formatting for stdout log output.
    ///
    /// - `true` — each event is a single-line JSON object (for log aggregation)
    /// - `false` — human-readable format with colors (for development)
    ///
    /// The file layer (if enabled) always uses human-readable format,
    /// since JSON output is typically consumed by log aggregation pipelines
    /// reading from stdout (e.g., Docker/Kubernetes log drivers).
    pub json_output: bool,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
            json_output: false,
        }
    }
}
```

### Why `json_output` Defaults to `false`

The default is human-readable because that's what developers want during local development. JSON mode is a production concern — you enable it when deploying to an environment with log aggregation.

This follows the principle of **sensible defaults**: `TracingConfig::default()` gives you a development-friendly setup. Production deployments explicitly opt into JSON.

### Why JSON on stdout, Not the File?

The `json_output` flag controls the **stdout** layer. The file layer (if enabled) stays human-readable. This might seem backwards — shouldn't the file be JSON for machine parsing?

In modern deployments, the answer is: **stdout is the machine-readable channel**. Here's why:

- **Docker** captures stdout/stderr from containers and forwards them to a logging driver (json-file, fluentd, awslogs)
- **Kubernetes** captures stdout from pods and makes it available via `kubectl logs` and log aggregation sidecars
- **12-Factor App methodology** says: "Treat logs as event streams" — write to stdout, let the platform handle routing

The file layer is a fallback for traditional deployments where you need persistent logs on disk. Those files are typically read by humans during debugging, so human-readable format makes sense.

If you need JSON in the file too, you could add a separate `json_file_output: bool` flag — but that's an exercise, not a requirement.


## Step 3: The Dual `Option<Layer>` Pattern

This is the key architectural insight of this lesson. Because `.json()` changes the layer's type, we can't conditionally call it. Instead, we create **two** layers and wrap each in `Option`:

```rust
// Conceptual pattern:
let (human_layer, json_layer) = if json_mode {
    (None, Some(fmt::layer().json()))       // JSON active, human inactive
} else {
    (Some(fmt::layer()), None)              // human active, JSON inactive
};

registry()
    .with(env_filter)
    .with(human_layer)   // Option<Layer<..., Format<Full>>>
    .with(json_layer)    // Option<Layer<..., Format<Json>>>
    .with(file_layer)    // Option<Layer<..., NonBlocking>>
    .init();
```

At any given time, exactly one of `human_layer` or `json_layer` is `Some`. The other is `None` (a no-op). The registry doesn't care — it processes whatever layers it's given.

### Why Not Use `Box<dyn Layer>`?

You might think: "Just box the layer and erase the type":

```rust
// Alternative approach — type erasure via Box
let stdout_layer: Box<dyn Layer<Registry> + Send + Sync> = if json_mode {
    Box::new(fmt::layer().json())
} else {
    Box::new(fmt::layer())
};
```

This works, but has downsides:

1. **Dynamic dispatch** — every event goes through a vtable call instead of being monomorphized. For a hot path like logging, this adds measurable overhead.
2. **Complexity** — `Box<dyn Layer<S> + Send + Sync>` requires careful trait bound management. The `Layer` trait has associated types that make boxing non-trivial.
3. **Composability** — boxed layers are harder to combine with per-layer filters (a pattern we might need later).

The dual `Option` pattern avoids all of this. Both layers are fully monomorphized — the compiler knows their exact types. The `None` branch is a compile-time no-op. Zero runtime cost.

### The Type Signatures

For the curious, here are the actual types (simplified):

```rust
// Human-readable stdout layer:
Option<fmt::Layer<Registry, DefaultFields, Format<Full>, Stdout>>

// JSON stdout layer:
Option<fmt::Layer<Registry, JsonFields, Format<Json>, Stdout>>

// File layer (human-readable, non-blocking writer):
Option<fmt::Layer<Registry, DefaultFields, Format<Full>, NonBlocking>>
```

These are three completely different types. The registry accepts all of them because `tracing-subscriber` implements `Layer` for `Option<L>` where `L: Layer`. Each `Option` is independently `Some` or `None`.

**Update** `crates/rustflow-common/src/tracing.rs` — the refactored `init_tracing()`:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::EnvFilter;
use tracing_subscriber::prelude::*;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
const DEFAULT_LOG_FILTER: &str =
    "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

// ... TracingConfig struct as shown in Step 2 ...

/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — either human-readable or JSON, depending on `config.json_output`
/// - **file layer** — human-readable output to a daily-rotated log file
///   (only when `config.log_directory` is `Some`)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime.
///
/// # Panics
///
/// Panics if called more than once.
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer — human-readable OR JSON (mutually exclusive) ──
    // When file logging is active, disable ANSI on the human layer —
    // span field formatting is shared across layers in the registry.
    let has_file_logging = config.log_directory.is_some();
    let (human_layer, json_layer) = if config.json_output {
        // JSON mode: structured output for log aggregation
        let json = tracing_subscriber::fmt::layer()
            .json()
            .with_target(true)
            .with_level(true)
            .with_span_list(true);

        (None, Some(json))
    } else {
        // Human-readable mode: scannable output for development
        let human = tracing_subscriber::fmt::layer()
            .with_target(true)
            .with_level(true)
            .with_ansi(!has_file_logging);

        (Some(human), None)
    };

    // ── file layer (optional, always human-readable) ────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_writer(dir) {
            Some((writer, guard)) => {
                let layer = tracing_subscriber::fmt::layer()
                    .with_target(true)
                    .with_level(true)
                    .with_ansi(false)
                    .with_writer(writer);
                (Some(layer), Some(guard))
            }
            None => (None, None),
        },
        None => (None, None),
    };

    // ── assemble the registry ───────────────────────────────
    tracing_subscriber::registry()
        .with(env_filter)
        .with(human_layer)
        .with(json_layer)
        .with(file_layer)
        .init();

    guard
}
```

### What Changed from 3.6

The diff is small but significant:

```rust
// 3.6: Single stdout layer
let has_file_logging = config.log_directory.is_some();
let stdout_layer = tracing_subscriber::fmt::layer()
    .with_target(true)
    .with_level(true)
    .with_ansi(!has_file_logging);

// 3.7: Two mutually exclusive stdout layers
let (human_layer, json_layer) = if config.json_output {
    (None, Some(fmt::layer().json().with_target(true).with_level(true).with_span_list(true)))
} else {
    (Some(fmt::layer().with_target(true).with_level(true).with_ansi(!has_file_logging)), None)
};
```

And the registry gains one more `.with()`:

```rust
// 3.6:
registry().with(env_filter).with(stdout_layer).with(file_layer).init();

// 3.7:
registry().with(env_filter).with(human_layer).with(json_layer).with(file_layer).init();
```

That's it. The file layer is unchanged. The `EnvFilter` is unchanged. The guard handling is unchanged. We just split the stdout layer into two mutually exclusive options.

### The `.json()` Method

```rust
tracing_subscriber::fmt::layer()
    .json()
    .with_target(true)
    .with_level(true)
    .with_span_list(true);
```

`.json()` transforms the layer from human-readable to JSON formatting. After calling `.json()`, the layer serializes each event as a single-line JSON object instead of the human-readable text format.

`.with_span_list(true)` includes the full span stack in each event. Without it, you only get the immediate parent span. With it, you get the entire chain — useful for seeing the full request context (HTTP span → operation span → nested span).

Note the method chain order: `.json()` must come before the `.with_*()` calls because it changes the layer's type. The methods available after `.json()` are slightly different from those on the non-JSON layer.


## Step 4: The JSON Event Structure

When JSON mode is enabled, every tracing event produces a single-line JSON object. Let's dissect the structure.

### A Simple Event

```rust
tracing::info!("server started");
```

Produces:

```json
{
  "timestamp": "2026-01-15T10:30:00.123456Z",
  "level": "INFO",
  "target": "rustflow_server",
  "fields": {
    "message": "server started"
  }
}
```

| Field | Type | Description |
|---|---|---|
| `timestamp` | string (ISO 8601) | When the event occurred, in UTC |
| `level` | string | Log level: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` |
| `target` | string | The Rust module path that emitted the event |
| `fields` | object | All structured fields attached to the event |
| `fields.message` | string | The human-readable message passed to the macro |

### An Event with Structured Fields

```rust
tracing::info!(task.id = 4, status = "created", "task created");
```

Produces:

```json
{
  "timestamp": "2026-01-15T10:30:01.456789Z",
  "level": "INFO",
  "target": "rustflow_server::routes::tasks",
  "fields": {
    "message": "task created",
    "task.id": 4,
    "status": "created"
  }
}
```

The structured fields (`task.id`, `status`) become top-level keys inside `fields`. This is the power of structured logging — the fields are typed and named, not embedded in a string that needs parsing.

In Elasticsearch, `fields.task.id` becomes a searchable numeric field. You can query `fields.task.id: 4` directly. In the human-readable format, `task.id=4` is just part of a text string — you'd need a regex to extract it.

### An Event Inside a Span

```rust
// Span created by TraceLayer or #[instrument]:
// request{http.method=GET http.uri="/api/tasks" request_id=a1b2c3d4}

tracing::info!("listing tasks");
```

Produces:

```json
{
  "timestamp": "2026-01-15T10:30:01.456789Z",
  "level": "INFO",
  "target": "rustflow_server::routes::tasks",
  "fields": {
    "message": "listing tasks"
  },
  "span": {
    "name": "request",
    "http.method": "GET",
    "http.uri": "/api/tasks",
    "request_id": "a1b2c3d4"
  },
  "spans": [
    {
      "name": "request",
      "http.method": "GET",
      "http.uri": "/api/tasks",
      "request_id": "a1b2c3d4"
    }
  ]
}
```

| Field | Type | Description |
|---|---|---|
| `span` | object | The **immediate parent** span — the innermost span the event is inside |
| `span.name` | string | The span's name (e.g., `"request"`, `"task.create"`) |
| `spans` | array | The **full span stack** — from outermost to innermost (enabled by `.with_span_list(true)`) |

### Nested Spans

When an event is inside multiple nested spans (e.g., a request span containing an operation span):

```rust
// Outer span: request{http.method=POST http.uri="/api/tasks" request_id=a1b2c3d4}
//   Inner span: task.create{task.id=4}
//     Event: tracing::info!("task created");
```

Produces:

```json
{
  "timestamp": "2026-01-15T10:30:01.456789Z",
  "level": "INFO",
  "target": "rustflow_server::routes::tasks",
  "fields": {
    "message": "task created"
  },
  "span": {
    "name": "task.create",
    "task.id": 4
  },
  "spans": [
    {
      "name": "request",
      "http.method": "POST",
      "http.uri": "/api/tasks",
      "request_id": "a1b2c3d4"
    },
    {
      "name": "task.create",
      "task.id": 4
    }
  ]
}
```

The `span` field is the innermost span (`task.create`). The `spans` array contains the full stack, outermost first (`request` → `task.create`). This lets you see the complete context chain for any event.

In a log aggregation system, you can:
- Filter by `spans[0].http.method = "POST"` to find all events from POST requests
- Filter by `span.name = "task.create"` to find all events from task creation operations
- Join events by `spans[0].request_id` to reconstruct the full request lifecycle

### One Line Per Event

Every JSON event is a **single line** — no pretty-printing, no newlines inside the JSON. This is critical for log ingestion:

```text
{"timestamp":"2026-01-15T10:30:00.123456Z","level":"INFO","target":"rustflow_server","fields":{"message":"server started"}}
{"timestamp":"2026-01-15T10:30:01.456789Z","level":"DEBUG","target":"tower_http::trace::on_request","fields":{"message":"started processing request"},"span":{"name":"request","http.method":"GET","http.uri":"/api/tasks"},"spans":[{"name":"request","http.method":"GET","http.uri":"/api/tasks"}]}
{"timestamp":"2026-01-15T10:30:01.457123Z","level":"DEBUG","target":"tower_http::trace::on_response","fields":{"message":"finished processing request","latency":"1 ms","status":200},"span":{"name":"request","http.method":"GET","http.uri":"/api/tasks"},"spans":[{"name":"request","http.method":"GET","http.uri":"/api/tasks"}]}
```

Each line is independently parseable. Log aggregation tools read line by line, parse each as JSON, and index the fields. If a line is corrupted (truncated write, partial flush), only that one event is lost — the rest are fine.

This is why `tracing-subscriber`'s JSON formatter doesn't pretty-print: newlines inside a JSON object would break line-based log ingestion.


## Step 5: Making JSON Mode Toggleable

The `json_output` field in `TracingConfig` is the primary toggle. But in production, you often want to control the log format without recompiling — via an environment variable.

**Update** `crates/rustflow-server/src/main.rs` — read `LOG_FORMAT` from the environment:

```rust name=crates/rustflow-server/src/main.rs
use rustflow_common::tracing::{TracingConfig, init_tracing};
use std::path::PathBuf;

#[tokio::main]
async fn main() {
    // ── Determine log format from environment ───────────────
    let json_output = std::env::var("LOG_FORMAT")
        .map(|v| v.eq_ignore_ascii_case("json"))
        .unwrap_or(false);

    // ── Initialize tracing ──────────────────────────────────
    let tracing_config = TracingConfig {
        log_directory: Some(PathBuf::from("logs")),
        json_output,
    };

    let _guard = init_tracing(tracing_config);

    let state: AppState = AppState::new();
    // ... rest of main unchanged ...
}
```

### How It Works

```rust
let json_output = std::env::var("LOG_FORMAT")
    .map(|v| v.eq_ignore_ascii_case("json"))
    .unwrap_or(false);
```

1. `std::env::var("LOG_FORMAT")` reads the `LOG_FORMAT` environment variable
2. `.map(|v| v.eq_ignore_ascii_case("json"))` checks if the value is `"json"` (case-insensitive)
3. `.unwrap_or(false)` defaults to `false` if the variable isn't set

This gives you three modes:

```bash
# Human-readable (default — LOG_FORMAT not set)
cargo run -p rustflow-server

# Human-readable (explicit)
LOG_FORMAT=text cargo run -p rustflow-server

# JSON
LOG_FORMAT=json cargo run -p rustflow-server
```

### Why `LOG_FORMAT` Instead of `LOG_JSON=true`?

A format selector (`LOG_FORMAT=json`) is more extensible than a boolean (`LOG_JSON=true`). If you later add support for `logfmt` (another structured format popular with Grafana), you'd set `LOG_FORMAT=logfmt`. With a boolean, you'd need a new variable.

The convention of `LOG_FORMAT` is common in the ecosystem. Some projects use `RUST_LOG_FORMAT` to namespace it under Rust-specific variables. Either works — the important thing is that it's documented and consistent.

### The `RUST_LOG` + `LOG_FORMAT` Interaction

These two environment variables are independent:

- `RUST_LOG` controls **what** gets logged (filter level per module)
- `LOG_FORMAT` controls **how** it's formatted (human-readable vs. JSON)

They compose naturally:

```bash
# Verbose JSON output (debug level, JSON format)
RUST_LOG=debug LOG_FORMAT=json cargo run -p rustflow-server

# Quiet human-readable output (warn level, text format)
```

## Step 6: JSON Output and the File Layer

An important design decision: when JSON mode is enabled, what format does the file layer use?

In our implementation, the file layer **always uses human-readable format**, regardless of the `json_output` setting. Here's the reasoning:

### stdout = Machine Channel, File = Human Channel

```text
┌─────────────────────────────────────────────────────────┐
│                    Registry                              │
│                                                          │
│  ┌──────────────┐                                        │
│  │  EnvFilter    │                                        │
│  └──────┬───────┘                                        │
│         │                                                │
│   ┌─────┴──────┐                                         │
│   │            │                                         │
│   ▼            ▼                                         │
│ ┌────────┐  ┌────────────┐  ┌────────────────────────┐   │
│ │ stdout │  │  stdout    │  │     file layer         │   │
│ │ human  │  │  JSON      │  │  (always human-        │   │
│ │ layer  │  │  layer     │  │   readable, no ANSI)   │   │
│ │ (dev)  │  │  (prod)    │  │                        │   │
│ └────┬───┘  └─────┬──────┘  └──────────┬─────────────┘   │
│      │            │                    │                  │
└──────┼────────────┼────────────────────┼──────────────────┘
       │            │                    │
       ▼            ▼                    ▼
    Terminal     Terminal          logs/rustflow.log
   (colors)    (JSON lines)      (plain text, no colors)

   Only ONE of these is active     Always active (if configured)
   at a time (based on json_output)
```

In production:
- **stdout** → captured by Docker/Kubernetes → forwarded to log aggregation → needs JSON
- **file** → read by humans during incident investigation → needs human-readable format

In development:
- **stdout** → your terminal → needs human-readable with colors
- **file** → optional, for reviewing past sessions → needs human-readable without colors

The file layer serves the same purpose in both environments: a human-readable fallback for direct inspection. JSON on stdout is for the machines.

### What If You Want JSON in the File Too?

If your use case requires JSON in the file (e.g., a log shipper reads from the file instead of stdout), you'd extend `TracingConfig` with a separate flag:

```rust
pub struct TracingConfig {
    pub log_directory: Option<PathBuf>,
    pub json_output: bool,
    pub json_file_output: bool,  // separate flag for file format
}
```

And apply the same dual `Option<Layer>` pattern to the file layer. But this adds complexity for a niche use case — most modern deployments use stdout for machine-readable output.


## Step 7: The Complete `tracing.rs` After 3.7

For reference, here's the full file with all changes:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::EnvFilter;
use tracing_subscriber::prelude::*;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
const DEFAULT_LOG_FILTER: &str =
    "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

/// Configuration for the tracing subsystem.
///
/// Controls which layers are active in the subscriber pipeline.
/// Passed to [`init_tracing()`] at application startup.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    ///
    /// - `Some(path)` — enable file logging to this directory
    /// - `None` — stdout only, no file logging
    pub log_directory: Option<PathBuf>,

    /// Use JSON formatting for stdout log output.
    ///
    /// - `true` — each event is a single-line JSON object (for log aggregation)
    /// - `false` — human-readable format with colors (for development)
    ///
    /// The file layer (if enabled) always uses human-readable format.
    pub json_output: bool,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
            json_output: false,
        }
    }
}

/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — human-readable OR JSON, depending on `config.json_output`
/// - **file layer** — human-readable output to a daily-rotated log file
///   (only when `config.log_directory` is `Some`)
///
/// The stdout format is controlled by `config.json_output`:
/// - `false` → human-readable format (ANSI colors when file logging is off)
/// - `true` → single-line JSON objects (production / log aggregation)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime. Dropping the guard stops the background file writer and may lose
/// buffered events.
///
/// # Panics
///
/// Panics if called more than once.
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer — human-readable OR JSON (mutually exclusive) ──
    //
    // These two layers have different types (Format<Full> vs Format<Json>),
    // so we can't use a single variable. Instead, we wrap each in Option
    // and add both to the registry. Only one will be Some at a time.
    //
    // When file logging is active, disable ANSI on the human layer —
    // span field formatting is shared across layers in the registry.
    let has_file_logging = config.log_directory.is_some();
    let (human_layer, json_layer) = if config.json_output {
        let json = tracing_subscriber::fmt::layer()
            .json()
            .with_target(true)
            .with_level(true)
            .with_span_list(true);

        (None, Some(json))
    } else {
        let human = tracing_subscriber::fmt::layer()
            .with_target(true)
            .with_level(true)
            .with_ansi(!has_file_logging);

        (Some(human), None)
    };

    // ── file layer (optional, always human-readable) ────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_writer(dir) {
            Some((writer, guard)) => {
                let layer = tracing_subscriber::fmt::layer()
                    .with_target(true)
                    .with_level(true)
                    .with_ansi(false)
                    .with_writer(writer);
                (Some(layer), Some(guard))
            }
            None => (None, None),
        },
        None => (None, None),
    };

    // ── assemble the registry ───────────────────────────────
    tracing_subscriber::registry()
        .with(env_filter)
        .with(human_layer)
        .with(json_layer)
        .with(file_layer)
        .init();

    guard
}

/// Attempts to create a non-blocking file writer with daily rotation.
///
/// Returns `None` if the directory can't be created or isn't writable.
/// Prints a warning to stderr (tracing isn't initialized yet).
fn try_build_file_writer(
    dir: &PathBuf,
) -> Option<(tracing_appender::non_blocking::NonBlocking, WorkerGuard)> {
    if let Err(e) = std::fs::create_dir_all(dir) {
        eprintln!(
            "WARNING: Cannot create log directory '{}': {}. File logging disabled.",
            dir.display(),
            e
        );
        return None;
    }

    let test_path = dir.join(".rustflow-log-test");
    match std::fs::write(&test_path, b"test") {
        Ok(_) => {
            let _ = std::fs::remove_file(&test_path);
        }
        Err(e) => {
            eprintln!(
                "WARNING: Log directory '{}' is not writable: {}. File logging disabled.",
                dir.display(),
                e
            );
            return None;
        }
    }

    let file_appender = tracing_appender::rolling::daily(dir, "rustflow.log");
    let (non_blocking, guard) = tracing_appender::non_blocking(file_appender);

    Some((non_blocking, guard))
}
```

### What Changed from 3.6 — Summary

| Change | 3.6 | 3.7 |
|---|---|---|
| `TracingConfig` fields | `log_directory` | `log_directory` + `json_output` |
| stdout layer | Single `fmt::layer()` | Two `Option` layers: human OR JSON |
| Registry `.with()` calls | `env_filter`, `stdout_layer`, `file_layer` | `env_filter`, `human_layer`, `json_layer`, `file_layer` |
| `try_build_file_writer()` | Unchanged | Unchanged |
| Guard handling | Unchanged | Unchanged |

The change is surgical: one new config field, one `if/else` to split the stdout layer, one extra `.with()` on the registry. Everything else — the file layer, the guard, the `EnvFilter`, graceful degradation — is identical.

### The Tradeoff Is Clear

| Aspect | Human-Readable | JSON |
|---|---|---|
| **Readability** | Excellent — scan, spot patterns | Terrible — wall of brackets and quotes |
| **Parseability** | Difficult — custom regex per format | Trivial — `serde_json::from_str()` |
| **Field extraction** | Manual — "find `status=` then read until space" | Direct — `event["fields"]["status"]` |
| **Size** | Compact | ~2x larger (key names repeated per event) |
| **Tooling** | `grep`, `awk`, human eyes | `jq`, Elasticsearch, Datadog, any JSON tool |
| **Schema evolution** | Breaks parsers when format changes | New fields are additive — old parsers ignore them |

The size difference is real — JSON events are roughly twice as large as human-readable ones because every field name is repeated in every event. For a high-volume service, this means more disk I/O and more network bandwidth for log shipping. But the parseability advantage far outweighs the size cost in production.

## Key Takeaways

1. **`.json()` changes the layer's type.** This is the core challenge. `fmt::layer()` and `fmt::layer().json()` produce different Rust types (`Format<Full>` vs `Format<Json>`). You can't conditionally call `.json()` in an `if` expression because both branches must return the same type.

2. **The dual `Option<Layer>` pattern solves the type mismatch.** Create two layers (human-readable and JSON), wrap each in `Option`, and add both to the registry. Only one is `Some` at a time. The `None` layer is a compile-time no-op — zero runtime cost.

3. **JSON events are single-line objects with structured fields.** Each event contains `timestamp`, `level`, `target`, `fields` (with `message` and any structured key-value pairs), and optionally `span` (immediate parent) and `spans` (full span stack). Every field is named and typed — no parsing required.

4. **`.with_span_list(true)` includes the full span stack.** Without it, you only get the immediate parent span. With it, you get the entire chain from outermost to innermost — essential for correlating events to their full request context in a log aggregation system.

5. **JSON mode is a production concern.** Human-readable output is for development (your terminal). JSON output is for production (log aggregation systems). The `LOG_FORMAT` environment variable lets you switch without recompiling — same binary, different behavior based on the deployment environment.

6. **stdout is the machine channel, files are the human channel.** In modern deployments (Docker, Kubernetes), stdout is captured by the platform and forwarded to log aggregation. The file layer is a fallback for direct human inspection. That's why JSON applies to stdout and the file stays human-readable.

7. **The `json` feature flag must be enabled on `tracing-subscriber`.** Without `features = ["json"]` in `Cargo.toml`, the `.json()` method doesn't exist. This is a common source of confusing compile errors.

8. **`TracingConfig` continues to grow without breaking changes.** Adding `json_output: bool` is a new field on the struct — the function signature (`init_tracing(config: TracingConfig)`) doesn't change. Callers that don't need JSON use `TracingConfig::default()` and get `json_output: false` automatically.
