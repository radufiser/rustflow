# 3.1 — Minimal Tracing Example

## Overview

Open `crates/rustflow-server/src/main.rs`. Find this line:

```rust
println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);
```

Now open `crates/rustflow-server/src/routes/middleware.rs`:

```rust
println!("{} {}", request.method(), uri);
```

And `crates/rustflow-server/src/routes/tasks.rs`:

```rust
println!("[audit] Task {} created by client '{}'", task.id, client.name);
```

Every log message in RustFlow is a `println!` call. It works — text appears in the terminal. But `println!` has serious limitations that become painful as a service grows:

- **No severity levels.** Is `"Draining... (10s timeout)"` informational or a warning? Is `"Request counter: 100"` debug noise or important? `println!` doesn't distinguish — everything is the same.
- **No filtering.** Want to silence the request counter but keep audit logs? You can't. It's all or nothing.
- **No structure.** Log aggregation systems (ELK, Datadog, Grafana Loki) need machine-parseable output — JSON with fields like `level`, `timestamp`, `target`. `println!` gives you a flat string.
- **No context propagation.** When 50 concurrent requests are in flight, which log line belongs to which request? `println!` doesn't know. You'd have to manually thread a request ID through every function call.
- **No spans.** How long did the task creation take? Which middleware was slow? `println!` can't measure durations or nest timing contexts.
- **Single output.** Logs go to stdout. Want to also write to a file? Send to a remote collector? You'd need to duplicate every `println!` call.

The Rust ecosystem's answer is the **`tracing`** crate — and its companion **`tracing-subscriber`**. Together, they provide structured, filterable, multi-destination observability that replaces `println!` entirely.

### The Tracing Ecosystem: Two Crates, Two Roles

The tracing ecosystem separates **instrumentation** (what you write in your code) from **collection** (how logs are processed and displayed):

| Crate | Role | What It Does |
|---|---|---|
| `tracing` | **Instrumentation** | Provides macros: `info!`, `debug!`, `warn!`, `error!`, `trace!`, `#[instrument]` |
| `tracing-subscriber` | **Collection** | Receives events from `tracing`, formats them, writes them somewhere (stdout, file, network) |

This separation is powerful. Your application code uses `tracing` macros everywhere — it doesn't know or care where the output goes. At startup, you configure a **subscriber** that decides:

- What format? (human-readable, JSON, compact)
- What destination? (stdout, file, OpenTelemetry collector)
- What verbosity? (show `debug` for your crates, `warn` for dependencies)

Change the subscriber configuration → change all log output. Zero changes to application code.

```text
Your Code                          Subscriber Pipeline
─────────                          ───────────────────
tracing::info!("listening")   ──►  fmt layer → stdout
tracing::debug!("task found") ──►  fmt layer → stdout
tracing::warn!("rate limited") ──► fmt layer → stdout
                                   (later: + file layer, + JSON, + OpenTelemetry)
```

### Log Levels: The Severity Hierarchy

`tracing` defines five severity levels, from most verbose to most critical:

| Level | Macro | When to Use | Example |
|---|---|---|---|
| `TRACE` | `tracing::trace!` | Ultra-verbose internals (rarely enabled) | `trace!("entering loop iteration {}", i)` |
| `DEBUG` | `tracing::debug!` | Development diagnostics | `debug!("task found: id={}", id)` |
| `INFO` | `tracing::info!` | Normal operational events | `info!("listening on {}", addr)` |
| `WARN` | `tracing::warn!` | Something unexpected but recoverable | `warn!("rate limit exceeded for client")` |
| `ERROR` | `tracing::error!` | Something failed | `error!("database connection lost")` |

Levels are hierarchical: setting the filter to `INFO` shows `INFO`, `WARN`, and `ERROR` — but hides `DEBUG` and `TRACE`. This is how you control verbosity without changing code.

### Events vs Spans (Preview)

In this lesson, we'll use **events** — single points in time, like log messages:

```rust
tracing::info!("server started");           // an event
tracing::warn!("connection refused");        // an event
```

In later lessons (3.3–3.5), we'll add **spans** — periods of time with a beginning and end:

```rust
let span = tracing::info_span!("handle_request", method = "GET", uri = "/api/tasks");
let _guard = span.enter();
// everything here is "inside" the span
// when _guard drops, the span ends and its duration is recorded
```

Spans are what make tracing more than just logging — they let you measure durations, nest contexts, and correlate events to specific operations. For now, events are enough to replace `println!`.

### What We'll Build in This Lesson

1. Add `tracing` and `tracing-subscriber` as workspace dependencies
2. Create `rustflow-common/src/tracing.rs` with an `init_tracing()` function
3. Re-export the module from `rustflow-common/src/lib.rs`
4. Call `init_tracing()` in `main.rs` before the TCP listener bind
5. Replace every `println!` call with the appropriate `tracing` macro

By the end, RustFlow's output will look like this instead of bare `println!` text:

```text
2026-01-15T10:30:00.123456Z  INFO rustflow_server: rustflow v0.1.0 listening on 0.0.0.0:3000
2026-01-15T10:30:01.456789Z  INFO rustflow_server::routes::middleware: GET /api/tasks
```

Every line now has a timestamp, a severity level, and a **target** (the module path). This is the foundation everything else in Section 3 builds on.

### Why Two New Crates?

| Crate | Version | Purpose |
|---|---|---|
| `tracing` | `0.1` | The instrumentation API — macros like `info!`, `debug!`, `warn!` that your code calls |
| `tracing-subscriber` | `0.3` | The subscriber implementation — collects events and writes them somewhere |

### Why These Features?

`tracing-subscriber` is modular — you enable only what you need:

| Feature | What It Provides |
|---|---|
| `fmt` | The `fmt::Layer` — formats events as human-readable text and writes to stdout/stderr |
| `env-filter` | The `EnvFilter` — controls log verbosity per module via the `RUST_LOG` environment variable |

Without `fmt`, you'd have a subscriber that collects events but can't display them. Without `env-filter`, you'd see *everything* — including verbose internal logs from `hyper`, `tokio`, and `tower` that would drown out your application output.

We'll use `env-filter` properly in lesson 3.2. For now, we include it so the dependency is ready.

### Workspace Dependency Pattern

Just like `tower` and `tower-http`, we declare the version once in the workspace root and reference it from crate-level `Cargo.toml` files with `{ workspace = true }`. This keeps all crates on the same version.

## Step 4: Create the Tracing Module

**Create** `crates/rustflow-common/src/tracing.rs`:

This is the heart of the change — a module that initializes the global tracing subscriber. For now, it's minimal: a `fmt` subscriber that writes human-readable output to stdout.

```rust name=crates/rustflow-common/src/tracing.rs
use tracing_subscriber::fmt;

/// Initialize the global tracing subscriber.
///
/// Sets up a `fmt` subscriber that writes human-readable log output to stdout.
/// Must be called exactly once, before any tracing macros fire — typically the
/// first line in `main()`.
///
/// # Panics
///
/// Panics if called more than once (the global subscriber can only be set once).
pub fn init_tracing() {
    fmt::init();
}
```

### What Does `fmt::init()` Do?

`tracing_subscriber::fmt::init()` is a convenience function that does three things in one call:

1. **Creates a `fmt` subscriber** — this is the component that receives tracing events and formats them as text
2. **Configures it with sensible defaults** — timestamps, log levels, module paths, ANSI colors (when writing to a terminal)
3. **Sets it as the global default** — all `tracing` macros (`info!`, `debug!`, etc.) in the entire process will route events to this subscriber

Under the hood, it's roughly equivalent to:

```rust
// What fmt::init() does internally (simplified):
tracing_subscriber::fmt()
    .with_target(true)          // show module path (e.g., rustflow_server::routes::tasks)
    .with_level(true)           // show level (INFO, DEBUG, WARN, etc.)
    .with_timer(SystemTime)     // show timestamp
    .with_ansi(true)            // colorize output in terminals
    .init();                    // set as global default subscriber
```

You don't need to write all that — `fmt::init()` picks good defaults. In lesson 3.2, we'll replace this with a more customized setup that includes `EnvFilter` for log level control.

### Why "Exactly Once"?

The tracing subscriber is a **global singleton**. Calling `fmt::init()` (or any `.init()` variant) sets the global default subscriber for the entire process. If you call it twice, the second call panics:

```text
thread 'main' panicked at 'a]global default trace dispatcher has already been set'
```

This is by design — having two subscribers fighting over events would be chaos. The rule is simple: call `init_tracing()` once, at the very start of `main()`, before anything else runs.

### Why a Wrapper Function?

We could call `fmt::init()` directly in `main.rs`. But wrapping it in `init_tracing()` gives us a stable API:

```rust
// Today (3.1):
pub fn init_tracing() {
    fmt::init();
}

// Tomorrow (3.2): add EnvFilter — main.rs doesn't change
pub fn init_tracing() {
    fmt()
        .with_env_filter(build_env_filter())
        .init();
}

// Later (3.6): add file logging — main.rs still doesn't change
pub fn init_tracing() -> Option<WorkerGuard> {
    // ... complex layered setup ...
}
```

The server always calls `rustflow_common::tracing::init_tracing()`. The implementation evolves behind that interface. This is the same pattern we used with `AppState` — a stable public API that hides internal complexity.

## Step 5: Re-Export the Module

**Update** `crates/rustflow-common/src/lib.rs` — add the module declaration:

```rust name=crates/rustflow-common/src/lib.rs
pub mod tracing;
```

Add this line near the top of `lib.rs`, alongside the existing `pub use` and `pub const` declarations. The `pub mod` makes the module accessible to other crates as `rustflow_common::tracing`.

### Module Naming: Shadowing the `tracing` Crate

You might notice that our module is named `tracing` — the same as the `tracing` crate. This is intentional and safe, but worth understanding:

- Inside `rustflow-common`, `crate::tracing` refers to **our module** (`src/tracing.rs`)
- Inside `rustflow-server`, `tracing` refers to **the crate** (from `Cargo.toml` dependencies)
- `rustflow_common::tracing` refers to **our module** (via the re-export)

There's no conflict because Rust's module system uses fully-qualified paths. The server imports the crate's macros with `tracing::info!` and calls our init function with `rustflow_common::tracing::init_tracing()`. Different paths, no ambiguity.

If the shadowing bothers you, you could name the module `tracing_setup` or `observability` instead. We use `tracing` because it clearly describes what the module is about, and the qualified paths prevent any confusion.

## Step 6: Call `init_tracing()` in the Server

**Update** `crates/rustflow-server/src/main.rs` — call `init_tracing()` as the first thing in `main()`:

```rust name=crates/rustflow-server/src/main.rs
#[tokio::main]
async fn main() {
    // Initialize tracing FIRST — before any other code runs.
    // All tracing macros (info!, debug!, warn!) are no-ops until this is called.
    rustflow_common::tracing::init_tracing();

    let state: AppState = AppState::new();
    // ... rest of main unchanged ...
}
```

### Why First?

Any `tracing::info!` call that fires *before* a subscriber is installed is silently dropped — the event has nowhere to go. By calling `init_tracing()` as the very first line, we ensure that every subsequent tracing macro has a subscriber ready to receive it.

This is especially important because `AppState::new()` reads `api_keys.json` and could panic — if we initialized tracing first, we'd see the panic message in our structured log output instead of a bare `thread 'main' panicked at ...` message.

### The Call Path

```text
main()
  └── rustflow_common::tracing::init_tracing()
        └── tracing_subscriber::fmt::init()
              ├── Creates fmt subscriber (formats events as text)
              ├── Configures defaults (timestamps, levels, colors)
              └── Sets as global default (all macros route here)
```

After this call, every `tracing::info!("...")` anywhere in the process — in `rustflow-server`, in `rustflow-common`, even in dependencies that use `tracing` — will produce formatted output on stdout.

## Step 7: Replace `println!` with Tracing Macros

Now the fun part. Go through every `println!` call in `rustflow-server` and replace it with the appropriate tracing macro. The choice of macro depends on the **severity** of the message.

### `main.rs` — Server Lifecycle Messages

These are operational messages about the server's state. Most are `info!` level (normal operations), with shutdown messages at appropriate levels:

```rust name=crates/rustflow-server/src/main.rs
// Before:
println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

// After:
tracing::info!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);
```

```rust
// Before:
println!("{} stopped", APP_NAME);

// After:
tracing::info!("{} stopped", APP_NAME);
```

```rust
// Before:
println!("Draining... (10s timeout)");

// After:
tracing::info!("Draining... (10s timeout)");
```

```rust
// Before:
println!("{} has shut down gracefully", APP_NAME);

// After:
tracing::info!("{} has shut down gracefully", APP_NAME);
```

```rust
// Before:
println!("Shutdown timeout exceeded, forcing exit");

// After:
tracing::warn!("Shutdown timeout exceeded, forcing exit");
```

Note the last one is `warn!`, not `info!` — a forced shutdown timeout is an abnormal condition worth highlighting. The signal handlers in `shutdown_signal()` also use `info!`:

```rust
// Before:
println!("\nReceived SIGINT (Ctrl+C), starting graceful shutdown...");

// After:
tracing::info!("Received SIGINT (Ctrl+C), starting graceful shutdown...");
```

```rust
// Before:
println!("\nReceived SIGTERM, starting graceful shutdown...");

// After:
tracing::info!("Received SIGTERM, starting graceful shutdown...");
```

Notice we drop the `\n` prefix — `println!` needed it to move past the `^C` on the terminal line. The tracing subscriber starts each event on a new line automatically.

### `middleware.rs` — Request Logging

The `log_request` middleware currently prints the HTTP method and URI:

```rust
// Before:
println!("{} {}", request.method(), uri);

// After:
tracing::info!("{} {}", request.method(), uri);
```

The `log_elapsed_time` middleware prints request duration:

```rust
// Before:
println!("Took {} mu", Instant::now().duration_since(start).as_micros() as f64);

// After:
tracing::debug!("Took {}μs", start.elapsed().as_micros());
```

This one becomes `debug!` — request timing is diagnostic detail that's useful during development but noisy in production. With tracing, you can filter it out by setting the log level to `info` without touching the code.

The `request_counter` middleware:

```rust
// Before:
println!("Request counter: {}", new);

// After:
tracing::debug!("Request counter: {}", new);
```

Also `debug!` — the counter is a diagnostic metric, not an operational event.

### `tasks.rs` — Audit Logs

Task operations have audit-style messages that record who did what:

```rust
// Before:
println!("Listing tasks for authenticated client {}", client.name);

// After:
tracing::debug!("Listing tasks for authenticated client {}", client.name);
```

Read operations are `debug!` — they're frequent and not security-critical.

```rust
// Before:
println!("[audit] Task {} created by client '{}'", task.id, client.name);

// After:
tracing::info!("[audit] Task {} created by client '{}'", task.id, client.name);
```

Write operations (create, update, delete) stay at `info!` — these are important audit events:

```rust
// Before:
println!("[audit] Task {id} deleted by client '{}'", client.name);

// After:
tracing::info!("[audit] Task {id} deleted by client '{}'", client.name);
```

```rust
// Before:
println!("[audit] Task {id} updated by client '{}'", client.name);

// After:
tracing::info!("[audit] Task {id} updated by client '{}'", client.name);
```

```rust
// Before:
println!("[audit] Task {id} status changed by client '{}'", client.name);

// After:
tracing::info!("[audit] Task {id} status changed by client '{}'", client.name);
```

### `projects.rs` — Audit Logs

Same pattern as tasks:

```rust
// Before:
println!("[audit] Project {} created by client '{}'", project.id, client.name);

// After:
tracing::info!("[audit] Project {} created by client '{}'", project.id, client.name);
```

```rust
// Before:
println!("[audit] Project {} deleted by client '{}'", id, client.name);

// After:
tracing::info!("[audit] Project {} deleted by client '{}'", id, client.name);
```

### Choosing the Right Level: A Decision Framework

When replacing `println!`, ask yourself:

| Question | If Yes → Level |
|---|---|
| Is this a normal operational event that operators should see? | `info!` |
| Is this a security-relevant action (create, delete, auth)? | `info!` |
| Is this diagnostic detail useful only during development? | `debug!` |
| Is this something unexpected but recoverable? | `warn!` |
| Is this a failure that needs immediate attention? | `error!` |
| Is this ultra-verbose internal state (loop iterations, byte counts)? | `trace!` |

For RustFlow:
- **Server lifecycle** (start, stop, shutdown) → `info!`
- **Audit events** (create, update, delete with client identity) → `info!`
- **Request logging** (method + URI) → `info!` (will be replaced by `TraceLayer` in 3.3)
- **Timing and counters** → `debug!`
- **Read operations by authenticated clients** → `debug!`
- **Forced shutdown timeout** → `warn!`


## Step 8: Understanding the Output Format

After replacing all `println!` calls, run the server and send a request. The output format changes dramatically.

### Before (println!)

```text
rustflow v0.1.0 listening on 0.0.0.0:3000
GET /api/tasks
Took 42 mu
POST /api/tasks
[audit] Task 4 created by client 'admin'
Took 156 mu
```

Flat text. No timestamps. No levels. No way to tell which module produced which line. No way to filter.

### After (tracing)

```text
2026-01-15T10:30:00.123456Z  INFO rustflow_server: rustflow v0.1.0 listening on 0.0.0.0:3000
2026-01-15T10:30:01.456789Z  INFO rustflow_server::routes::middleware: GET /api/tasks
2026-01-15T10:30:01.457123Z DEBUG rustflow_server::routes::middleware: Took 42μs
2026-01-15T10:30:05.100000Z  INFO rustflow_server::routes::middleware: POST /api/tasks
2026-01-15T10:30:05.100234Z  INFO rustflow_server::routes::tasks: [audit] Task 4 created by client 'admin'
2026-01-15T10:30:05.100345Z DEBUG rustflow_server::routes::middleware: Took 156μs
```

Every line now has four parts:

```text
2026-01-15T10:30:00.123456Z  INFO rustflow_server::routes::tasks: [audit] Task 4 created
│                            │    │                                │
│                            │    │                                └── message (your text)
│                            │    └── target (module path — automatic)
│                            └── level (INFO, DEBUG, WARN, ERROR, TRACE)
└── timestamp (ISO 8601 with microsecond precision)
```

### The Target Field

The **target** is the Rust module path where the macro was called. `tracing` captures this automatically — you don't need to include it in your message. This is incredibly useful:

- `rustflow_server` → event from `main.rs`
- `rustflow_server::routes::middleware` → event from `middleware.rs`
- `rustflow_server::routes::tasks` → event from `tasks.rs`

In lesson 3.2, we'll use the target to filter by module: "show me only events from `rustflow_server::routes::tasks`" or "silence everything from `hyper`."

### ANSI Colors

When writing to a terminal (TTY), the `fmt` subscriber colorizes output:

- `INFO` → green
- `DEBUG` → blue
- `WARN` → yellow
- `ERROR` → red

When writing to a file or pipe (non-TTY), colors are automatically disabled. You don't need to configure this — the subscriber detects the output type.

The only `println!` that should remain is inside doc comments (the `/// ``` ignore` block in `middleware.rs`). All actual runtime output should now use `tracing` macros.

### What If You See No Output?

If tracing macros produce no output, check:

1. **Did you call `init_tracing()`?** Without it, all macros are no-ops.
2. **Is it called before the macros?** Events fired before `init_tracing()` are silently dropped.
3. **Is the level filtered out?** The default `fmt::init()` shows everything at `TRACE` and above — so this shouldn't be an issue yet. In 3.2, when we add `EnvFilter`, incorrect filter strings can hide output.

## How Tracing Macros Work Under the Hood

When you write:

```rust
tracing::info!("listening on {}", addr);
```

The macro expands to roughly:

```rust
// Simplified — actual expansion is more complex
if tracing::level_enabled!(tracing::Level::INFO) {
    tracing::Event::dispatch(
        tracing::Metadata {
            level: Level::INFO,
            target: module_path!(),  // "rustflow_server" — automatic
            file: file!(),           // "src/main.rs" — automatic
            line: line!(),           // 42 — automatic
        },
        &[("message", &format_args!("listening on {}", addr))],
    );
}
```

Key points:

1. **Level check first** — if the subscriber's filter would reject this level, the formatting code never runs. This means `debug!` calls in production (where the level is set to `info`) have near-zero cost — not even the `format_args!` is evaluated.

2. **Metadata is compile-time** — the module path, file, and line number are captured by Rust's built-in macros (`module_path!()`, `file!()`, `line!()`). No runtime reflection.

3. **Dispatch to subscriber** — the event is sent to whatever subscriber was installed by `init_tracing()`. The subscriber decides what to do with it (format and print, write to file, send to a collector, or discard).

This is why tracing is essentially free when disabled — the level check short-circuits before any work happens.

## Key Takeaways

1. **`tracing` replaces `println!` with structured, leveled events.** Every event automatically gets a timestamp, severity level, and module path — no manual formatting needed.

2. **The ecosystem splits instrumentation from collection.** `tracing` (macros) is what your code uses. `tracing-subscriber` (subscriber) is what processes the output. Change the subscriber → change all output. Zero code changes.

3. **Log levels let you control verbosity without code changes.** `debug!` for diagnostics, `info!` for operations, `warn!` for anomalies. In production, set the level to `info` and all `debug!` calls become zero-cost no-ops.

4. **`init_tracing()` must be called once, before anything else.** It sets the global subscriber. Events fired before initialization are silently dropped. Events after a second initialization call cause a panic.

5. **Centralizing tracing setup in `rustflow-common` is forward-thinking.** Today it's one line (`fmt::init()`). By the end of Section 3, it'll be a layered pipeline with filtering, file output, JSON formatting, and OpenTelemetry export — all behind the same `init_tracing()` interface.

6. **Tracing macros are near-zero cost when disabled.** The level check happens before any formatting. A `debug!` call in production (with `info` level filter) doesn't even allocate the format string.

7. **The target field is automatic and invaluable.** `tracing` captures `module_path!()` at compile time. You get per-module filtering for free — no need to manually tag messages with their origin.
