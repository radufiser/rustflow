# 3.8 — OpenTelemetry

## Overview

You have structured logs. You have spans with timing. You have JSON output for log aggregation. You can answer "what happened?" by searching log lines. But can you answer this:

*"A request to `POST /api/tasks` took 1.2 seconds. Where did the time go?"*

You'd search the logs for that request ID, find the spans, mentally reconstruct the timeline:

```text
request{http.method=POST http.uri="/api/tasks" request_id=a1b2c3d4}
  → task.create{} — 1.1s
    → enrichment call — 900ms
    → store write — 200ms
  → response sent — 1.2s total
```

You can piece this together from log lines. But it's manual, error-prone, and doesn't scale. What if the request called three external services? What if one of those services called two more? What if you have 50 services and need to trace a request across all of them?

This is where **distributed tracing** tools come in — and the industry standard for getting trace data into those tools is **OpenTelemetry**.

### What Is OpenTelemetry?

OpenTelemetry (OTel) is a vendor-neutral observability framework. It defines:

1. **A data model** — what a trace, span, and event look like
2. **An API** — how your code creates spans and attaches metadata
3. **An SDK** — how spans are collected, batched, and exported
4. **A protocol (OTLP)** — how trace data is sent over the wire to a collector

The key word is **vendor-neutral**. OpenTelemetry doesn't care where your traces end up:

| Backend | What It Does |
|---|---|
| **Jaeger** | Open-source distributed tracing UI (we'll use this) |
| **Zipkin** | Another open-source tracing backend |
| **Datadog APM** | Commercial APM with tracing |
| **Grafana Tempo** | Trace storage backend for Grafana |
| **AWS X-Ray** | AWS-native distributed tracing |
| **Honeycomb** | Observability platform built around traces |

You instrument your code once with OpenTelemetry. Then you point the exporter at whatever backend your organization uses. Switch from Jaeger to Datadog? Change one configuration line. Your application code doesn't change.

### The Rust OTel Ecosystem

OpenTelemetry in Rust involves four crates, each with a distinct role:

| Crate | Role | Analogy |
|---|---|---|
| `opentelemetry` | **API** — defines the `Tracer`, `Span`, and `TracerProvider` traits | The interface contract |
| `opentelemetry-sdk` | **SDK** — implements the API with span processing, batching, and export pipelines | The engine |
| `opentelemetry-otlp` | **Exporter** — sends spans over gRPC/HTTP to an OTLP-compatible collector | The network driver |
| `tracing-opentelemetry` | **Bridge** — converts `tracing` spans into OpenTelemetry spans | The adapter |

The last one is the crucial piece. We've been using the `tracing` crate since lesson 3.1 — all our spans and events use `tracing` macros (`tracing::info!`, `#[instrument]`). We don't want to rewrite everything to use the OpenTelemetry API directly. Instead, `tracing-opentelemetry` acts as a **bridge layer**: it sits in the subscriber registry alongside the `fmt` layer and the file layer, and it converts every `tracing` span into an OpenTelemetry span that gets exported via OTLP.

```text
tracing::info!("task created")
    │
    ▼
┌──────────────────────────────────────────────────────────┐
│                       Registry                            │
│                                                           │
│  ┌──────────────┐                                         │
│  │  EnvFilter    │                                         │
│  └──────┬───────┘                                         │
│         │                                                 │
│   ┌─────┼──────────────┬──────────────┐                   │
│   │     │              │              │                   │
│   ▼     ▼              ▼              ▼                   │
│ ┌─────────┐  ┌──────────────┐  ┌──────────────────────┐   │
│ │ stdout  │  │  file layer  │  │  OpenTelemetry layer │   │
│ │ layer   │  │  (optional)  │  │  (optional)          │   │
│ └────┬────┘  └──────┬───────┘  └──────────┬───────────┘   │
│      │              │                     │               │
└──────┼──────────────┼─────────────────────┼───────────────┘
       │              │                     │
       ▼              ▼                     ▼
    Terminal     logs/rustflow.log    OTLP Collector
                                     (Jaeger, Tempo, etc.)
```

This is the beauty of the layered subscriber pattern we've been building since lesson 3.6. Adding OpenTelemetry is just one more `.with()` call on the registry. The existing stdout and file layers are completely unaffected.

### Why Feature-Gate OpenTelemetry?

The four OTel crates pull in significant dependencies:

- `opentelemetry-otlp` brings in `tonic` (a gRPC framework) or `reqwest` for HTTP transport
- `opentelemetry-sdk` brings in async runtime integration
- Together, they add dozens of transitive dependencies and increase compile time noticeably

For local development, you rarely need trace export — the terminal output is sufficient. For CI builds, pulling OTel dependencies slows down compilation for no benefit. Only production deployments (or local testing with Jaeger) need the exporter.

Cargo **features** solve this perfectly. We'll gate all OTel dependencies behind an `otel` feature flag:

```toml
# Without the feature — no OTel deps compiled
cargo build -p rustflow-common

# With the feature — OTel deps included
cargo build -p rustflow-common --features otel
```

When the `otel` feature is disabled, the OTel crates aren't even downloaded. The `init_tracing()` function skips the OTel layer entirely. Zero cost when you don't need it.

### What We'll Build in This Lesson

1. Add the four OTel crates as **optional** dependencies behind an `otel` feature flag
2. Add `otlp_endpoint: Option<String>` to `TracingConfig`
3. Build an OTLP exporter pipeline with a `TracerProvider` and service name resource
4. Add the `tracing-opentelemetry` layer to the subscriber registry
5. Handle non-blocking export — if the collector is unreachable, the server continues
6. Add graceful shutdown for the tracer provider (flush pending spans on exit)
7. Run Jaeger locally with Docker and view traces in the Jaeger UI


### What Each Crate Does

| Crate | Version | Purpose |
|---|---|---|
| `opentelemetry` | `0.28` | Core API — defines `Tracer`, `Span`, `TracerProvider` traits. Lightweight, no implementation. |
| `opentelemetry-sdk` | `0.28` | SDK implementation — span processing, batching, resource attributes. The `rt-tokio` feature integrates with Tokio's async runtime for background export. |
| `opentelemetry-otlp` | `0.28` | OTLP exporter — sends spans to a collector over gRPC (via `tonic`) or HTTP. The `grpc-tonic` feature uses gRPC transport, which is what Jaeger's OTLP receiver expects on port 4317. |
| `tracing-opentelemetry` | `0.29` | Bridge layer — implements `tracing_subscriber::Layer` and converts `tracing` spans into OpenTelemetry spans. This is the glue between the `tracing` ecosystem and the OTel ecosystem. |

### Version Compatibility

The OpenTelemetry Rust crates are versioned together — `opentelemetry`, `opentelemetry-sdk`, and `opentelemetry-otlp` must be the same minor version (all `0.28.x`). `tracing-opentelemetry` tracks one version ahead (`0.29`) because it bridges two ecosystems and has its own release cadence.

If you mix versions (e.g., `opentelemetry` 0.27 with `opentelemetry-sdk` 0.28), you'll get confusing trait mismatch errors:

```text
error[E0277]: the trait bound `opentelemetry::trace::Tracer` is not satisfied
```

Always keep the three `opentelemetry-*` crates at the same version.

### The `rt-tokio` Feature

`opentelemetry-sdk` needs an async runtime to batch and export spans in the background. The `rt-tokio` feature tells it to use Tokio — which we're already running. Without this feature, you'd need to manually drive the export pipeline, which defeats the purpose of non-blocking export.

### The `grpc-tonic` Feature

`opentelemetry-otlp` supports two transport protocols:

- **gRPC** (via `tonic`) — the standard OTLP transport. Jaeger, Grafana Tempo, and most collectors listen on port 4317 for gRPC OTLP.
- **HTTP/protobuf** — an alternative for environments where gRPC is blocked. Uses port 4318.

We use gRPC because it's the default for Jaeger and most production collectors. The `grpc-tonic` feature pulls in the `tonic` gRPC framework — this is the heaviest dependency in the OTel stack, which is why we feature-gate everything.


## Step 2: Feature-Gate the OTel Dependencies

This is the key architectural decision of this lesson. We don't want every `cargo build` to compile `tonic`, `prost`, and the entire gRPC stack. Cargo features let us make these dependencies **optional** — only compiled when explicitly requested.

**Update** `crates/rustflow-common/Cargo.toml`:

```toml name=crates/rustflow-common/Cargo.toml
[package]
name = "rustflow-common"
version = "0.1.0"
edition = "2024"

[features]
otel = [
    "dep:opentelemetry",
    "dep:opentelemetry-sdk",
    "dep:opentelemetry-otlp",
    "dep:tracing-opentelemetry",
]

[dependencies]
chrono = "0.4"
serde = { workspace = true }
serde_json = { workspace = true }
validator = { workspace = true }
tracing = { workspace = true }
tracing-subscriber = { workspace = true }
tracing-appender = { workspace = true }

# OpenTelemetry — optional, behind the "otel" feature
opentelemetry = { workspace = true, optional = true }
opentelemetry-sdk = { workspace = true, optional = true }
opentelemetry-otlp = { workspace = true, optional = true }
tracing-opentelemetry = { workspace = true, optional = true }
```

### How Cargo Features Work

The `[features]` section defines named feature flags. Each feature lists the dependencies it activates:

```toml
[features]
otel = [
    "dep:opentelemetry",
    "dep:opentelemetry-sdk",
    "dep:opentelemetry-otlp",
    "dep:tracing-opentelemetry",
]
```

The `dep:` prefix means "enable this optional dependency." When you build without the feature:

```bash
cargo build -p rustflow-common
# opentelemetry, opentelemetry-sdk, opentelemetry-otlp, tracing-opentelemetry
# are NOT compiled — they don't even appear in the dependency graph
```

When you build with the feature:

```bash
cargo build -p rustflow-common --features otel
# All four crates are compiled and linked
```

The `optional = true` marker on each dependency means it's not included by default. Only when the `otel` feature activates them (via `dep:`) do they become part of the build.

### Conditional Compilation with `#[cfg(feature = "otel")]`

In Rust code, you use `#[cfg(feature = "otel")]` to conditionally compile blocks:

```rust
// This code only exists when the "otel" feature is enabled
#[cfg(feature = "otel")]
fn build_otel_layer(endpoint: &str) -> impl Layer<Registry> {
    // ... OpenTelemetry setup ...
}

// This import only exists when "otel" is enabled
#[cfg(feature = "otel")]
use opentelemetry_sdk::trace::TracerProvider;
```

When the feature is disabled, the compiler completely ignores these blocks — they don't exist in the binary. No dead code, no unused imports, no runtime cost.

This is the same pattern as `#[cfg(unix)]` from lesson 2.21 (graceful shutdown). Cargo features and platform targets both use Rust's conditional compilation system.

### Forwarding Features from the Server Crate

The server crate depends on `rustflow-common`. To enable the `otel` feature on the common crate, the server needs to forward it:

**Update** `crates/rustflow-server/Cargo.toml`:

```toml name=crates/rustflow-server/Cargo.toml
[features]
otel = ["rustflow-common/otel"]

[dependencies]
rustflow-common = { path = "../rustflow-common" }
# ... other dependencies unchanged ...
```

Now you can enable OTel from the server crate:

```bash
# Build the server with OTel support
cargo build -p rustflow-server --features otel

# Run the server with OTel support
cargo run -p rustflow-server --features otel
```

The feature propagates: `rustflow-server/otel` → `rustflow-common/otel` → enables all four OTel dependencies.


## Step 3: Add `otlp_endpoint` to `TracingConfig`

**Update** `crates/rustflow-common/src/tracing.rs` — extend the config struct:

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;

/// Configuration for the tracing subsystem.
///
/// Controls which layers are active in the subscriber pipeline.
/// Passed to [`init_tracing()`] at application startup.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    pub log_directory: Option<PathBuf>,

    /// Use JSON formatting for stdout log output.
    pub json_output: bool,

    /// Optional OTLP collector endpoint for OpenTelemetry trace export.
    ///
    /// - `Some("http://localhost:4317")` — export spans via gRPC to this endpoint
    /// - `None` — no OpenTelemetry export (default)
    ///
    /// Requires the `otel` feature to be enabled. If the feature is disabled
    /// but an endpoint is provided, the endpoint is silently ignored.
    ///
    /// If the collector is unreachable, the server continues operating —
    /// export failures are non-blocking and logged as warnings.
    pub otlp_endpoint: Option<String>,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
            json_output: false,
            otlp_endpoint: None,
        }
    }
}
```

### The `Option<String>` Pattern

`otlp_endpoint` follows the same pattern as `log_directory` — `None` means "disabled," `Some(url)` means "enabled with this configuration." This keeps the default behavior unchanged: `TracingConfig::default()` produces no OTel export, no file logging, human-readable stdout. Every feature is opt-in.

The endpoint is a URL string like `"http://localhost:4317"`. Port 4317 is the standard OTLP gRPC port. In production, this would point to your collector:

```rust
TracingConfig {
    otlp_endpoint: Some("http://otel-collector.monitoring.svc:4317".to_string()),
    ..Default::default()
}
```

### Feature Gate + Config: Defense in Depth

There are two independent guards:

1. **Compile-time**: The `otel` feature must be enabled, or the OTel code doesn't exist in the binary
2. **Runtime**: `otlp_endpoint` must be `Some`, or the OTel layer isn't added to the registry

This means you can compile with `--features otel` but still run without a collector — just don't set the endpoint. The OTel code is in the binary but dormant. This is useful for container images that might or might not be deployed with a collector sidecar.


## Step 4: Build the OpenTelemetry Pipeline

This is the core of the lesson. We need to:

1. Create an OTLP exporter that knows where to send spans
2. Create a `TracerProvider` that batches spans and feeds them to the exporter
3. Set the service name so Jaeger knows which service the traces belong to
4. Create a `tracing-opentelemetry` layer that bridges `tracing` spans to OTel spans
5. Add the layer to the registry

All of this is behind `#[cfg(feature = "otel")]`.

**Add to** `crates/rustflow-common/src/tracing.rs`:

```rust name=crates/rustflow-common/src/tracing.rs
#[cfg(feature = "otel")]
use opentelemetry::trace::TracerProvider as _;
#[cfg(feature = "otel")]
use opentelemetry_sdk::trace::TracerProvider;
#[cfg(feature = "otel")]
use opentelemetry_sdk::Resource;
#[cfg(feature = "otel")]
use opentelemetry::KeyValue;

use crate::APP_NAME;

/// Builds the OpenTelemetry tracing layer.
///
/// Creates an OTLP exporter → TracerProvider → tracing-opentelemetry layer.
/// The layer converts `tracing` spans into OpenTelemetry spans and exports
/// them to the configured collector endpoint.
///
/// Returns `None` if the pipeline fails to initialize (e.g., invalid endpoint).
/// In that case, a warning is printed and the server continues without OTel.
#[cfg(feature = "otel")]
fn build_otel_layer(
    endpoint: &str,
) -> Option<tracing_opentelemetry::OpenTelemetryLayer<
    tracing_subscriber::Registry,
    opentelemetry_sdk::trace::Tracer,
>> {
    // ── Step A: Create the OTLP exporter ────────────────────
    let exporter = match opentelemetry_otlp::SpanExporter::builder()
        .with_tonic()
        .with_endpoint(endpoint)
        .build()
    {
        Ok(exporter) => exporter,
        Err(e) => {
            eprintln!(
                "WARNING: Failed to create OTLP exporter for '{}': {}. \
                 OpenTelemetry disabled.",
                endpoint, e
            );
            return None;
        }
    };

    // ── Step B: Create the TracerProvider ────────────────────
    let provider = TracerProvider::builder()
        .with_batch_exporter(exporter)
        .with_resource(
            Resource::builder()
                .with_attribute(KeyValue::new(
                    "service.name",
                    APP_NAME.to_string(),
                ))
                .build(),
        )
        .build();

    // ── Step C: Get a tracer from the provider ──────────────
    let tracer = provider.tracer(APP_NAME);

    // ── Step D: Install the provider globally ───────────────
    opentelemetry::global::set_tracer_provider(provider);

    // ── Step E: Create the tracing-opentelemetry layer ──────
    let otel_layer = tracing_opentelemetry::layer().with_tracer(tracer);

    Some(otel_layer)
}
```

### Anatomy of the Pipeline

Let's walk through each step.

#### Step A: The OTLP Exporter

```rust
let exporter = opentelemetry_otlp::SpanExporter::builder()
    .with_tonic()
    .with_endpoint(endpoint)
    .build()?;
```

The exporter is the network component — it serializes spans into the OTLP protobuf format and sends them over gRPC to the collector. `.with_tonic()` selects the gRPC transport (using the `tonic` crate). `.with_endpoint(endpoint)` sets the collector URL.

If the endpoint is malformed or the exporter can't be created, we catch the error and return `None`. The server continues without OTel — no panic, no crash.

#### Step B: The TracerProvider

```rust
let provider = TracerProvider::builder()
    .with_batch_exporter(exporter)
    .with_resource(
        Resource::builder()
            .with_attribute(KeyValue::new("service.name", APP_NAME.to_string()))
            .build(),
    )
    .build();
```

The `TracerProvider` is the central OTel component. It:

1. **Manages span processing** — when a span ends, the provider processes it
2. **Batches spans** — instead of sending each span individually, it batches them for efficiency
3. **Feeds the exporter** — the batch processor periodically flushes batches to the OTLP exporter

`.with_batch_exporter(exporter)` configures batch processing. The SDK spawns a background task (on the Tokio runtime, thanks to `rt-tokio`) that collects completed spans and exports them in batches. Default batch settings:

| Setting | Default | Description |
|---|---|---|
| Max queue size | 2048 | Maximum spans buffered before dropping |
| Scheduled delay | 5 seconds | How often batches are exported |
| Max export batch size | 512 | Maximum spans per export call |
| Export timeout | 30 seconds | How long to wait for an export to complete |

These defaults are fine for development. In production, you might tune them for higher throughput.

#### The Service Name Resource

```rust
.with_resource(
    Resource::builder()
        .with_attribute(KeyValue::new("service.name", APP_NAME.to_string()))
        .build(),
)
```

A `Resource` describes the entity producing telemetry. The most important attribute is `service.name` — this is how Jaeger identifies your service in its UI. Without it, your traces show up as "unknown_service" — not helpful when you have multiple services.

We use `APP_NAME` from `rustflow-common` (the constant `"rustflow"` defined in `lib.rs`). In Jaeger, you'll search for traces by this service name.

#### Step C: Getting a Tracer

```rust
let tracer = provider.tracer(APP_NAME);
```

A `Tracer` is a named span factory. The name (`APP_NAME`) is used for instrumentation library identification — it tells the collector which library produced the spans. This is metadata, not the service name (that's in the `Resource`).

#### Step D: Installing the Provider Globally

```rust
opentelemetry::global::set_tracer_provider(provider);
```

This installs the `TracerProvider` as the global default. The `tracing-opentelemetry` layer uses the global provider to export spans. This is similar to how `tracing_subscriber::registry().init()` installs the global subscriber — there's one provider per process.

#### Step E: The Bridge Layer

```rust
let otel_layer = tracing_opentelemetry::layer().with_tracer(tracer);
```

This creates the bridge layer. It implements `tracing_subscriber::Layer` and does the following for every `tracing` span:

1. **On span creation** — creates a corresponding OpenTelemetry span with the same name and fields
2. **On span enter/exit** — tracks the span's active duration
3. **On span close** — ends the OpenTelemetry span and sends it to the `TracerProvider` for export
4. **On event** — attaches the event as an OTel span event (log entry within a span)

The bridge is transparent — your existing `#[instrument]` annotations and `tracing::info!()` calls work exactly as before. They still produce output on stdout and in the log file. But now they *also* produce OpenTelemetry spans that get exported to Jaeger.


## Step 5: Wire the OTel Layer into `init_tracing()`

Now we integrate the OTel layer into the existing subscriber pipeline.

**Update** `crates/rustflow-common/src/tracing.rs` — the `init_tracing()` function:

```rust name=crates/rustflow-common/src/tracing.rs
/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — either human-readable or JSON
/// - **file layer** — daily-rotated log file (optional)
/// - **OpenTelemetry layer** — OTLP export to a collector (optional, requires `otel` feature)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime.
///
/// # Panics
///
/// Panics if called more than once.
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer — human-readable OR JSON ───────────────
    let (human_layer, json_layer) = if config.json_output {
        let json = tracing_subscriber::fmt::layer()
            .json()
            .with_target(true)
            .with_level(true)
            .with_span_list(true);
        (None, Some(json))
    } else {
        let human = tracing_subscriber::fmt::layer()
            .with_target(true)
            .with_level(true);
        (Some(human), None)
    };

    // ── file layer (optional) ───────────────────────────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_layer(dir) {
            Some((layer, guard)) => (Some(layer), Some(guard)),
            None => (None, None),
        },
        None => (None, None),
    };

    // ── OpenTelemetry layer (optional, feature-gated) ───────
    #[cfg(feature = "otel")]
    let otel_layer = config
        .otlp_endpoint
        .as_deref()
        .and_then(build_otel_layer);

    #[cfg(not(feature = "otel"))]
    let otel_layer: Option<tracing_opentelemetry::OpenTelemetryLayer<_, _>> = None;

    // ── assemble the registry ───────────────────────────────
    tracing_subscriber::registry()
        .with(env_filter)
        .with(human_layer)
        .with(json_layer)
        .with(file_layer)
        .with(otel_layer)
        .init();

    guard
}
```

```rust
    .init();
```

One more `.with()` call. The existing layers are completely untouched. This is the payoff of the layered architecture — each lesson adds capability without disturbing what came before.

### The `#[cfg]` Dance

```rust
#[cfg(feature = "otel")]
let otel_layer = config
    .otlp_endpoint
    .as_deref()
    .and_then(build_otel_layer);

#[cfg(not(feature = "otel"))]
let otel_layer: Option<tracing_opentelemetry::OpenTelemetryLayer<_, _>> = None;
```

Wait — there's a problem here. When the `otel` feature is disabled, `tracing-opentelemetry` isn't available, so we can't reference its types. We need a different approach for the `#[cfg(not(feature = "otel"))]` branch.

The solution is to use a type-erased `Option`:

```rust
#[cfg(not(feature = "otel"))]
let otel_layer = None::<tracing_opentelemetry::OpenTelemetryLayer<_, _>>;
```

But this still references `tracing_opentelemetry`. The cleanest approach is to restructure the registry assembly itself:

```rust
// ── assemble the registry ───────────────────────────────
let registry = tracing_subscriber::registry()
    .with(env_filter)
    .with(human_layer)
    .with(json_layer)
    .with(file_layer);

#[cfg(feature = "otel")]
{
    let otel_layer = config
        .otlp_endpoint
        .as_deref()
        .and_then(build_otel_layer);
    registry.with(otel_layer).init();
}

#[cfg(not(feature = "otel"))]
{
    registry.init();
}
```

This way, the `tracing-opentelemetry` type is only referenced inside the `#[cfg(feature = "otel")]` block. When the feature is disabled, the registry is initialized without the OTel layer — no type references to missing crates.

### The `.as_deref().and_then()` Pattern

```rust
config.otlp_endpoint
    .as_deref()           // Option<String> → Option<&str>
    .and_then(build_otel_layer)  // Option<&str> → Option<Layer>
```

This is a common Rust idiom for chaining optional operations:

1. `.as_deref()` converts `Option<String>` to `Option<&str>` — avoids moving the `String` out of the config
2. `.and_then(build_otel_layer)` calls the builder function only if the endpoint is `Some`. If the endpoint is `None`, the result is `None` (no OTel layer). If the builder returns `None` (initialization failed), the result is also `None`.

The end result: `otel_layer` is `Some(layer)` only when both the endpoint is configured *and* the pipeline initialized successfully. Otherwise it's `None`, and the `Option<Layer>` no-op kicks in.


## Step 6: Non-Blocking Export and Resilience

One of the most important properties of the OTel integration: **if the collector is unreachable, the server keeps running.**

This happens automatically because of how the batch exporter works:

```text
Request → Handler → tracing span created
                         │
                         ▼
                  tracing-opentelemetry layer
                         │
                         ▼
                  TracerProvider (batch processor)
                         │
                    ┌─────┴─────┐
                    │  Span     │
                    │  Queue    │  ← spans buffered here
                    │  (2048)   │
                    └─────┬─────┘
                          │
                    Background task (every 5s)
                          │
                          ▼
                    OTLP Exporter
                          │
                    ┌─────┴─────┐
                    │ Collector │  ← might be unreachable
                    │ (Jaeger)  │
                    └───────────┘
```

The handler never waits for the export. It creates a span, the span is queued, and the handler returns immediately. The background task periodically drains the queue and attempts to export. If the export fails:

1. The batch is dropped (not retried indefinitely — that would cause unbounded memory growth)
2. A warning is logged via `tracing` (which goes to stdout/file, not to the broken OTel pipeline)
3. The next batch is attempted on the next cycle

The server's request handling is completely decoupled from the export pipeline. A dead collector means you lose trace data — but you never lose request-handling capacity.

### What Happens at Startup with No Collector?

If you start the server with `OTLP_ENDPOINT=http://localhost:4317` but no Jaeger is running:

1. The OTLP exporter is created successfully (it doesn't connect at creation time)
2. The `TracerProvider` is installed
3. The server starts and handles requests normally
4. The background exporter attempts to send spans and fails
5. You see warnings in the server logs:

```text
2026-01-15T10:30:05.123Z  WARN opentelemetry_otlp: OTLP exporter failed: transport error
```

6. The server continues operating. Start Jaeger later, and traces begin flowing automatically — no restart needed.

This is the correct behavior for a production service. Observability infrastructure should never be a hard dependency. If your monitoring system goes down, your application should keep serving users.


## Step 7: Graceful Shutdown for the Tracer Provider

When the server shuts down (SIGTERM/SIGINT from lesson 2.21), there may be spans still in the batch queue that haven't been exported yet. If the process exits without flushing, those spans are lost.

The `opentelemetry::global::shutdown_tracer_provider()` function signals the `TracerProvider` to:

1. Stop accepting new spans
2. Flush all remaining spans in the batch queue to the exporter
3. Wait for the export to complete (with a timeout)
4. Shut down the background export task

**Update** `crates/rustflow-server/src/main.rs` — add OTel shutdown after the server drains:

```rust name=crates/rustflow-server/src/main.rs
use rustflow_common::tracing::{TracingConfig, init_tracing};
use std::path::PathBuf;

#[tokio::main]
async fn main() {
    // ── Determine configuration from environment ────────────
    let json_output = std::env::var("LOG_FORMAT")
        .map(|v| v.eq_ignore_ascii_case("json"))
        .unwrap_or(false);

    let otlp_endpoint = std::env::var("OTLP_ENDPOINT").ok();

    // ── Initialize tracing ──────────────────────────────────
    let tracing_config = TracingConfig {
        log_directory: Some(PathBuf::from("logs")),
        json_output,
        otlp_endpoint,
    };

    let _guard = init_tracing(tracing_config);

    let state: AppState = AppState::new();

    // ... router setup unchanged ...

    tracing::info!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

    // ── Serve with graceful shutdown ────────────────────────
    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal())
        .await
        .expect("Server error");

    // ── Post-shutdown cleanup ───────────────────────────────
    // Flush any pending OpenTelemetry spans before exiting.
    // This must happen AFTER the server drains (no new spans created)
    // but BEFORE the process exits (so the exporter can send them).
    #[cfg(feature = "otel")]
    {
        tracing::info!("Flushing OpenTelemetry spans...");
        opentelemetry::global::shutdown_tracer_provider();
        tracing::info!("OpenTelemetry shutdown complete");
    }

    tracing::info!("{} has shut down gracefully", APP_NAME);
}
```

### The Shutdown Order Matters

```text
1. SIGTERM received
2. Server stops accepting new connections
3. In-flight requests complete (spans still being created)
4. Server fully drained (no more spans)
5. ← shutdown_tracer_provider() HERE — flush pending spans
6. ← _guard dropped HERE — flush pending file log events
7. Process exits
```

The OTel shutdown must happen:
- **After** the server drains — otherwise you'd miss spans from the final requests
- **Before** the `_guard` is dropped — because the OTel shutdown might log messages (via `tracing::info!`), and those messages need the file writer to still be alive

The `#[cfg(feature = "otel")]` guard ensures this code only compiles when the feature is enabled. Without it, `opentelemetry::global::shutdown_tracer_provider()` would be a compile error (the crate doesn't exist).

### The `OTLP_ENDPOINT` Environment Variable

```rust
let otlp_endpoint = std::env::var("OTLP_ENDPOINT").ok();
```

`.ok()` converts `Result<String, VarError>` to `Option<String>`:
- Variable set → `Some("http://localhost:4317")`
- Variable not set → `None`

This gives you three deployment modes:

```bash
# No OTel (development default)
cargo run -p rustflow-server

# OTel enabled, pointing to local Jaeger
OTLP_ENDPOINT=http://localhost:4317 cargo run -p rustflow-server --features otel

# OTel enabled, pointing to production collector
OTLP_ENDPOINT=http://otel-collector.monitoring:4317 cargo run -p rustflow-server --features otel
```

Note: you need both `--features otel` (compile-time) and `OTLP_ENDPOINT` (runtime) for traces to export. If you compile with the feature but don't set the endpoint, the OTel layer is skipped. If you set the endpoint but didn't compile with the feature, the endpoint is ignored.

```rust name=crates/rustflow-common/src/tracing.rs
use std::path::PathBuf;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::EnvFilter;
use tracing_subscriber::prelude::*;

#[cfg(feature = "otel")]
use opentelemetry::trace::TracerProvider as _;
#[cfg(feature = "otel")]
use opentelemetry::KeyValue;
#[cfg(feature = "otel")]
use opentelemetry_sdk::trace::TracerProvider;
#[cfg(feature = "otel")]
use opentelemetry_sdk::Resource;

use crate::APP_NAME;

/// The compiled-in default filter applied when `RUST_LOG` is not set.
const DEFAULT_LOG_FILTER: &str =
    "rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn";

/// Configuration for the tracing subsystem.
pub struct TracingConfig {
    /// Optional directory for daily-rotated log files.
    pub log_directory: Option<PathBuf>,

    /// Use JSON formatting for stdout log output.
    pub json_output: bool,

    /// Optional OTLP collector endpoint for OpenTelemetry trace export.
    pub otlp_endpoint: Option<String>,
}

impl Default for TracingConfig {
    fn default() -> Self {
        Self {
            log_directory: None,
            json_output: false,
            otlp_endpoint: None,
        }
    }
}

/// Initialize the global tracing subscriber.
///
/// Assembles a layered subscriber pipeline:
/// - **EnvFilter** — reads `RUST_LOG` or falls back to [`DEFAULT_LOG_FILTER`]
/// - **stdout layer** — either human-readable or JSON
/// - **file layer** — daily-rotated log file (optional)
/// - **OpenTelemetry layer** — OTLP export to a collector (optional, requires `otel` feature)
///
/// Returns an `Option<WorkerGuard>` that **must** be held for the application
/// lifetime.
pub fn init_tracing(config: TracingConfig) -> Option<WorkerGuard> {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(DEFAULT_LOG_FILTER));

    // ── stdout layer — human-readable OR JSON ───────────────
    let (human_layer, json_layer) = if config.json_output {
        let json = tracing_subscriber::fmt::layer()
            .json()
            .with_target(true)
            .with_level(true)
            .with_span_list(true);
        (None, Some(json))
    } else {
        let human = tracing_subscriber::fmt::layer()
            .with_target(true)
            .with_level(true);
        (Some(human), None)
    };

    // ── file layer (optional) ───────────────────────────────
    let (file_layer, guard) = match config.log_directory {
        Some(ref dir) => match try_build_file_layer(dir) {
            Some((layer, guard)) => (Some(layer), Some(guard)),
            None => (None, None),
        },
        None => (None, None),
    };

    // ── assemble the registry ───────────────────────────────
    let registry = tracing_subscriber::registry()
        .with(env_filter)
        .with(human_layer)
        .with(json_layer)
        .with(file_layer);

    #[cfg(feature = "otel")]
    {
        let otel_layer = config
            .otlp_endpoint
            .as_deref()
            .and_then(build_otel_layer);
        registry.with(otel_layer).init();
    }

    #[cfg(not(feature = "otel"))]
    {
        registry.init();
    }

    guard
}

// ... try_build_file_layer() unchanged from 3.6 ...

/// Builds the OpenTelemetry tracing layer.
///
/// Creates an OTLP exporter → TracerProvider → tracing-opentelemetry layer.
/// Returns `None` if the pipeline fails to initialize.
#[cfg(feature = "otel")]
fn build_otel_layer(
    endpoint: &str,
) -> Option<tracing_opentelemetry::OpenTelemetryLayer<
    tracing_subscriber::Registry,
    opentelemetry_sdk::trace::Tracer,
>> {
    let exporter = match opentelemetry_otlp::SpanExporter::builder()
        .with_tonic()
        .with_endpoint(endpoint)
        .build()
    {
        Ok(exporter) => exporter,
        Err(e) => {
            eprintln!(
                "WARNING: Failed to create OTLP exporter for '{}': {}. \
                 OpenTelemetry disabled.",
                endpoint, e
            );
            return None;
        }
    };

    let provider = TracerProvider::builder()
        .with_batch_exporter(exporter)
        .with_resource(
            Resource::builder()
                .with_attribute(KeyValue::new(
                    "service.name",
                    APP_NAME.to_string(),
                ))
                .build(),
        )
        .build();

    let tracer = provider.tracer(APP_NAME);
    opentelemetry::global::set_tracer_provider(provider);

    let otel_layer = tracing_opentelemetry::layer().with_tracer(tracer);
    Some(otel_layer)
}
```

## Key Takeaways

1. **OpenTelemetry is vendor-neutral.** You instrument once with OTel, then point the exporter at any backend — Jaeger, Datadog, Grafana Tempo, AWS X-Ray. Switching backends is a configuration change, not a code change.

2. **Four crates, four roles.** `opentelemetry` (API), `opentelemetry-sdk` (implementation), `opentelemetry-otlp` (network exporter), `tracing-opentelemetry` (bridge to the `tracing` ecosystem). Each has a distinct responsibility. The bridge layer is the key — it lets you keep using `tracing` macros while exporting to OTel.

3. **Feature-gate heavy dependencies.** The OTel crates pull in gRPC (`tonic`), protobuf (`prost`), and HTTP/2 (`h2`). Gating them behind `--features otel` means local development builds stay fast. Only production builds (or local Jaeger testing) pay the compile-time cost.

4. **The layered subscriber pattern scales.** Adding OTel was one more `.with()` call on the registry. The existing stdout, JSON, and file layers were untouched. This is the payoff of the architecture we built in lessons 3.6 and 3.7.

5. **Non-blocking export is essential.** The batch exporter runs in a background task. If the collector is unreachable, spans are dropped — not retried forever. The server never blocks on trace export. Observability infrastructure must never be a hard dependency for request handling.

6. **`service.name` is the most important resource attribute.** Without it, your traces show up as "unknown_service" in Jaeger. Set it to your application name so you can find your traces in a multi-service environment.

7. **Flush on shutdown.** `opentelemetry::global::shutdown_tracer_provider()` flushes pending spans before the process exits. Without it, the last few seconds of traces are lost. Call it after the server drains but before the process exits.

8. **Two guards: compile-time and runtime.** The `otel` feature flag (compile-time) controls whether OTel code exists in the binary. The `otlp_endpoint` config (runtime) controls whether the OTel layer is active. You can compile with the feature but run without a collector — the OTel code is dormant until an endpoint is configured.

9. **Jaeger `all-in-one` is perfect for local development.** One Docker command gives you a collector, storage, and UI. Port 4317 for OTLP gRPC, port 16686 for the web UI. Traces are stored in memory — lost on container restart, which is fine for development.

10. **`#[cfg(feature = "...")]` is conditional compilation.** Code inside `#[cfg(feature = "otel")]` blocks only exists when the feature is enabled. This is the same mechanism as `#[cfg(unix)]` from lesson 2.21 — Rust's compile-time feature system ensures zero cost for disabled features.
