# 3.3 — Logging Axum & Tower HTTP Requests

## Overview

Open `crates/rustflow-server/src/routes/middleware.rs` and look at these two functions:

```rust
pub async fn log_request(request: Request, next: Next) -> Response {
    let uri = request
        .extensions()
        .get::<OriginalUri>()
        .map(|original| original.0.to_string())
        .unwrap_or_else(|| request.uri().to_string());
    tracing::info!("{} {}", request.method(), uri);
    next.run(request).await
}

pub async fn log_elapsed_time(request: Request, next: Next) -> Response {
    let start = Instant::now();
    let response = next.run(request).await;
    tracing::debug!("Took {}μs", start.elapsed().as_micros());
    response
}
```

We wrote these by hand in Section 2 and upgraded them from `println!` to `tracing` macros in 3.1. They work — but they have real limitations:

- **Two separate middleware for one concern.** Request logging and response timing are split across `log_request` and `log_elapsed_time`. They run independently — there's no connection between "this request" and "this timing."
- **No response information.** `log_request` fires *before* the handler runs. It logs the method and URI, but it has no idea what status code the response will have. Did the request succeed? Return a 404? Panic? You can't tell from the logs.
- **No span lifecycle.** `log_request` emits a single event. It doesn't create a *span* — a named context that wraps the entire request lifecycle. Without a span, you can't correlate the request log with the timing log, or with any events emitted by the handler itself.
- **Manual `OriginalUri` handling.** We had to manually extract `OriginalUri` from extensions to get the full path after `nest()` strips the prefix. This is boilerplate that every request-logging middleware has to repeat.
- **Applied inconsistently.** Look at `main.rs` — `log_request` and `log_elapsed_time` are applied to both the infra router and the API router, but with slightly different stacking. If you add a new router group, you have to remember to add both middleware.

Now look at what we *want* from HTTP request logging:

1. A single log line per request that includes method, URI, status code, *and* latency
2. A span that wraps the entire request lifecycle — so handler events appear "inside" the request context
3. Automatic integration with the tracing subscriber pipeline (EnvFilter, fmt layer)
4. Zero custom middleware code to maintain

This is exactly what `tower-http`'s `TraceLayer` provides.

### What Is `TraceLayer`?

`TraceLayer` is a Tower middleware from the `tower-http` crate that automatically instruments HTTP request/response cycles with `tracing` spans and events. When a request arrives:

1. **Creates a span** — a named tracing context containing the HTTP method and URI. This span wraps the entire request lifecycle.
2. **Forwards the request** — the inner service (your handler + other middleware) runs inside this span.
3. **Emits a response event** — when the response comes back, `TraceLayer` logs the status code and how long the request took (latency).

All of this happens in one middleware, with zero custom code. The output flows through the same subscriber pipeline we built in 3.1 and 3.2 — `EnvFilter` filters it, the `fmt` layer formats it, and it appears on stdout.

```text
Request arrives
    │
    ▼
┌──────────────────────────────────────────────┐
│  TraceLayer                                  │
│                                              │
│  1. Create span: "HTTP request"              │
│     Fields: method=GET, uri=/api/tasks       │
│                                              │
│  2. Enter span → forward to handler          │
│     ┌──────────────────────────────────┐     │
│     │  Handler runs (inside the span)  │     │
│     │  Any tracing events here are     │     │
│     │  associated with this request    │     │
│     └──────────────────────────────────┘     │
│                                              │
│  3. Emit response event:                     │
│     status=200, latency=1.2ms                │
│                                              │
│  4. Exit span (duration recorded)            │
└──────────────────────────────────────────────┘
    │
    ▼
Response sent to client
```

Compare this to our two-middleware approach:

| Feature | `log_request` + `log_elapsed_time` | `TraceLayer` |
|---|---|---|
| Request method + URI | ✅ (manual) | ✅ (automatic) |
| Response status code | ❌ | ✅ (automatic) |
| Request latency | ✅ (separate middleware) | ✅ (same middleware) |
| Span wrapping request | ❌ | ✅ (automatic) |
| Handler events correlated | ❌ | ✅ (inside span) |
| Custom code to maintain | ~20 lines | 0 lines |

### The `trace` Feature

`TraceLayer` is behind a **feature flag** on `tower-http`. The `tower-http` crate is large — it includes middleware for compression, CORS, static files, request decompression, and more. Feature flags let you pull in only what you need.

We already have `tower-http` in our workspace with features for static files (`fs`), CORS (`cors`), and compression (`compression-full`). To use `TraceLayer`, we need to add the `trace` feature.

Without the `trace` feature enabled, `tower_http::trace::TraceLayer` simply doesn't exist — the module isn't compiled. You'll get a "module not found" error if you try to import it.

### Why `tower_http=debug` Was Already in Our Filter

Back in lesson 3.2, we set this as the default `EnvFilter`:

```text
rustflow_server=debug,rustflow_common=debug,tower_http=debug,warn
```

We included `tower_http=debug` even though we weren't using `TraceLayer` yet. This was deliberate — `TraceLayer` emits its spans and events under the `tower_http` target. Because we already have `tower_http` at `debug` level in our filter, the `TraceLayer` output will appear immediately when we add it. No filter changes needed.

If `tower_http` were at `warn` (like other dependencies), `TraceLayer`'s `DEBUG`-level request/response events would be silently filtered out — you'd add the layer, see nothing, and wonder what went wrong.

### What the `trace` Feature Pulls In

The `trace` feature on `tower-http` adds a dependency on the `tracing` crate (which we already have). It doesn't add any new external crates — it just enables the `trace` module within `tower-http` itself. The module provides:

| Type | Purpose |
|---|---|
| `TraceLayer` | The middleware layer — wraps a service with request/response tracing |
| `DefaultMakeSpan` | Creates the per-request span (method + URI) |
| `DefaultOnRequest` | Emits an event when a request is received |
| `DefaultOnResponse` | Emits an event when a response is sent (status + latency) |
| `DefaultOnFailure` | Emits an event when the service returns an error |

`TraceLayer::new_for_http()` uses all the `Default*` implementations out of the box. In lesson 3.5, we'll replace `DefaultMakeSpan` with a custom implementation that adds request IDs and client names. For now, the defaults are exactly what we need.

```rust name=crates/rustflow-server/src/main.rs
fn build_app(state: &AppState) -> Router {
    // ...

    // Infrastructure router — no per-group logging needed anymore
    let infra_router: Router<AppState> = routes::health::router();

    let api_router: Router<AppState> = Router::new()
        .nest("/tasks", routes::tasks::router(state.clone()))
        .nest("/projects", routes::projects::router(state.clone()))
        .nest("/users", routes::users::router(state.clone()))
        .nest(
            "/enrichment",
            rate_limited(routes::enrichment::router(), 10, Duration::from_secs(10)),
        )
        .layer(
            ServiceBuilder::new()
                .layer(
                    CompressionLayer::new()
                        .compress_when(DefaultPredicate::new().and(SizeAbove::new(512))),
                )
                .layer(middleware::from_fn_with_state(
                    state.clone(),
                    request_counter,
                )),
        );

    let app: Router = Router::new()
        .merge(static_router)
        .merge(infra_router)
        .nest("/api", api_router)
        .with_state(state.clone())
        // TraceLayer is global — every request gets a span and response event
        .layer(TraceLayer::new_for_http())
        .layer(cors);

    app
}
```

### What Changed

Three things happened:

1. **`TraceLayer::new_for_http()` added as a global layer.** It sits between CORS and the router — every request passes through it, regardless of which router group handles it. This replaces the per-group `log_request` and `log_elapsed_time` layers.

2. **`log_request` and `log_elapsed_time` removed from both router groups.** The infra router is now bare — no middleware at all. The API router keeps compression and `request_counter`, but logging is handled globally by `TraceLayer`.

3. **Import updated.** `log_elapsed_time` and `log_request` are no longer imported from `middleware`. Only `rate_limited` and `request_counter` remain.

### Why Global Instead of Per-Group?

In the previous setup, we applied logging middleware to each router group individually. This was necessary because `log_request` and `log_elapsed_time` were simple middleware functions — they had to be explicitly added wherever we wanted logging.

`TraceLayer` works differently. As a global layer (applied after `.with_state()`), it wraps the entire application. Every request — static files, health checks, API calls — gets a span and response event. This is the right default: you want visibility into *all* traffic, not just API routes.

If you later need to *exclude* certain routes from tracing (e.g., high-frequency health checks from a load balancer), you can customize `TraceLayer`'s `make_span` function to skip them — but that's a lesson 3.5 concern. For now, trace everything.

### Layer Ordering

The layer stack after this change:

```text
Request arrives
    │
    ▼
┌─────────────┐
│    CORS      │  ← outermost: handles OPTIONS preflight
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  TraceLayer  │  ← creates span, times request, logs response
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   Router     │  ← routes to static / infra / API
└──────┬──────┘
       │
       ▼
  (handler)
```

CORS is outermost because OPTIONS preflight requests should be handled before any other processing. `TraceLayer` is next — it wraps everything inside the router, so the span covers the full request lifecycle including routing, middleware, and handler execution.

### `new_for_http()` vs `new()`

`TraceLayer` has two constructors:

```rust
// For HTTP services (what we use):
TraceLayer::new_for_http()

// For generic Tower services:
TraceLayer::new(classify::SharedClassifier::new(StatusInRangeAsFailures::new(400..=599)))
```

`new_for_http()` is a convenience that pre-configures the layer for HTTP semantics:
- Classifies responses by HTTP status code (5xx = failure, everything else = success)
- Uses `DefaultMakeSpan` which extracts method and URI
- Uses `DefaultOnResponse` which logs status code and latency

For Axum services, `new_for_http()` is always the right choice.


## Step 3: Remove Custom Logging Middleware

**Update** `crates/rustflow-server/src/routes/middleware.rs` — remove the `log_request` and `log_elapsed_time` functions.

### Before (3.2)

```rust name=crates/rustflow-server/src/routes/middleware.rs
pub async fn log_request(request: Request, next: Next) -> Response {
    let uri = request
        .extensions()
        .get::<OriginalUri>()
        .map(|original| original.0.to_string())
        .unwrap_or_else(|| request.uri().to_string());
    tracing::info!("{} {}", request.method(), uri);
    next.run(request).await
}

pub async fn log_elapsed_time(request: Request, next: Next) -> Response {
    let start = Instant::now();
    let response = next.run(request).await;
    tracing::debug!("Took {}μs", start.elapsed().as_micros());
    response
}
```

### After (3.3)

Delete both functions entirely. They're no longer called from anywhere — `TraceLayer` handles their responsibilities.

You can also clean up any imports that were only used by these two functions. After removing them, check whether `OriginalUri`, `Instant`, and `Duration` are still needed by other functions in the file. If `log_request` was the only user of `OriginalUri`, remove that import. If `log_elapsed_time` was the only user of `Instant` and `Duration`, remove those too.

The remaining functions in `middleware.rs` should be:
- `require_api_key` — authentication middleware (still needed)
- `rate_limited` — rate limiting wrapper (still needed)
- `request_counter` — request counting middleware (still needed)

### Why Remove Instead of Keep?

You might think: "Why not keep `log_request` and `log_elapsed_time` alongside `TraceLayer`? More logging is better, right?"

No — it's worse. If you keep both:

1. **Duplicate output.** Every request produces *two* log lines for the method/URI — one from `log_request`, one from `TraceLayer`'s span. The timing appears twice too.
2. **Confusing correlation.** `log_request`'s event is *outside* `TraceLayer`'s span (depending on layer order), so it won't be associated with the request context. You'd see orphaned log lines mixed with properly-spanned ones.
3. **Maintenance burden.** Two systems doing the same thing means two things to update, debug, and reason about.

`TraceLayer` is strictly superior — it does everything our custom middleware did, plus status codes, plus span lifecycle. The custom middleware has no remaining purpose.


## Step 4: Understanding `TraceLayer` Output

With the changes in place, let's understand exactly what `TraceLayer` produces and how it flows through the subscriber pipeline.

### The Span: Per-Request Context

When a request arrives, `TraceLayer`'s `DefaultMakeSpan` creates a span like this:

```text
HTTP request{method=GET uri=/api/tasks}
```

This span is **entered** before the request is forwarded to the handler, and **exited** after the response is produced. Everything that happens inside — handler execution, database queries, other middleware — runs "inside" this span.

In the formatted output, the span appears as context on every event emitted during the request:

```text
2026-01-15T10:30:01.456789Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_request: started processing request
```

The `request{method=GET uri="/api/tasks"}:` prefix is the span context. Any `tracing::info!` or `tracing::debug!` call inside a handler will also show this prefix — that's how you correlate handler events to specific requests.

### The Response Event

When the handler returns a response, `TraceLayer`'s `DefaultOnResponse` emits an event:

```text
2026-01-15T10:30:01.457123Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=0 ms status=200
```

This single line tells you:
- **Which request** — `method=GET uri="/api/tasks"` (from the span)
- **What happened** — `finished processing request`
- **How long** — `latency=0 ms` (sub-millisecond in this case)
- **The result** — `status=200`

Compare this to our old two-middleware approach:

```text
# Old (3.2) — two separate lines, no status code, no correlation
2026-01-15T10:30:01.456789Z  INFO rustflow_server::routes::middleware: GET /api/tasks
2026-01-15T10:30:01.457123Z DEBUG rustflow_server::routes::middleware: Took 42μs

# New (3.3) — one span + one response event, with status code
2026-01-15T10:30:01.456789Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.457123Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=0 ms status=200
```

The new output is richer: you get the status code (200), the latency, and the span context that ties everything together.

### How It Flows Through the Subscriber Pipeline

`TraceLayer` doesn't write to stdout directly. It emits tracing spans and events — just like `tracing::info!` does. Those events flow through the subscriber pipeline we built in 3.1 and 3.2:

```text
TraceLayer creates span: "HTTP request" (method=GET, uri=/api/tasks)
    │
    ▼
TraceLayer emits event: "finished processing request" (status=200, latency=1ms)
    │
    ▼
┌─────────────────────┐
│     EnvFilter        │  target: tower_http::trace::on_response
│                      │  level:  DEBUG
│                      │
│  Check: tower_http=debug → DEBUG ≥ DEBUG? Yes ✓
│  Result: PASS        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│     fmt Layer        │  Format and write to stdout
│                      │
│  2026-01-15T10:30:01.457123Z DEBUG request{method=GET uri="/api/tasks"}:
│    tower_http::trace::on_response: finished processing request latency=0 ms status=200
└─────────────────────┘
```

This is why the `tower_http=debug` directive in our default filter matters. `TraceLayer` emits events at `DEBUG` level under the `tower_http` target. If our filter had `tower_http=warn`, these events would be silently rejected by `EnvFilter` and never reach the `fmt` layer.

### The `tower_http` Target

Notice the target in the output: `tower_http::trace::on_response`. This is the module path inside the `tower-http` crate where the event is emitted. It's not `rustflow_server` — it's the library code doing the logging.

This means you can control `TraceLayer` output independently:

```bash
# Show TraceLayer output at debug level, silence everything else
RUST_LOG=tower_http=debug,error cargo run -p rustflow-server

# Hide TraceLayer output, show only your application events
RUST_LOG=rustflow_server=debug,tower_http=warn,warn cargo run -p rustflow-server

# Show TraceLayer at trace level (very verbose — shows headers, body sizes)
RUST_LOG=tower_http=trace,rustflow_server=info,warn cargo run -p rustflow-server
```

The `EnvFilter` from lesson 3.2 gives you fine-grained control over `TraceLayer`'s verbosity without touching any code.

5. **Global layer**: `.layer(TraceLayer::new_for_http())` added after `.with_state()`, before `.layer(cors)`

The `main()` function and `shutdown_signal()` function are completely unchanged from 3.2.


## Step 6: How `TraceLayer` Creates Spans and Events

Let's trace through exactly what happens when a request hits the server, step by step.

### Request: `GET /api/tasks`

```text
1. Client sends: GET /api/tasks HTTP/1.1

2. CORS layer: not an OPTIONS request → pass through

3. TraceLayer::on_request():
   - DefaultMakeSpan creates span:
     tracing::debug_span!("request", method = %request.method(), uri = %request.uri())
   - Span entered (all subsequent events are "inside" this span)
   - DefaultOnRequest emits: tracing::debug!("started processing request")

4. Router matches /api/tasks → tasks::list handler

5. Handler runs (inside the TraceLayer span):
   - Any tracing::info!() or tracing::debug!() calls here
     appear with the span context in the output

6. Handler returns Response (status 200, JSON body)

7. TraceLayer::on_response():
   - DefaultOnResponse emits:
     tracing::debug!(
       status = %response.status().as_u16(),
       latency = ?elapsed,
       "finished processing request"
     )
   - Span exited and dropped (duration recorded by subscriber)

8. Response sent to client
```

### What the Output Looks Like

For a simple `GET /api/tasks`:

```text
2026-01-15T10:30:01.456789Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:01.457000Z  INFO request{method=GET uri="/api/tasks"}: rustflow_server::routes::tasks: [audit] Listing tasks
2026-01-15T10:30:01.457123Z DEBUG request{method=GET uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=0 ms status=200
```

Three lines:
1. **Request started** — `TraceLayer` announces the request
2. **Handler event** — your `tracing::info!` inside the handler, with the request span as context
3. **Response sent** — `TraceLayer` announces completion with status and latency

The `request{method=GET uri="/api/tasks"}:` prefix on every line is the span context. This is how you know all three events belong to the same request — even when 50 concurrent requests are interleaved in the output.

### For a Failed Request: `GET /api/tasks/999`

```text
2026-01-15T10:30:02.100000Z DEBUG request{method=GET uri="/api/tasks/999"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:02.100234Z DEBUG request{method=GET uri="/api/tasks/999"}: tower_http::trace::on_response: finished processing request latency=0 ms status=404
```

The status code is `404` — immediately visible in the response event. With our old `log_request` middleware, you'd see `GET /api/tasks/999` but have no idea it returned a 404 unless you also checked the client output.

### For a POST with Authentication

```text
2026-01-15T10:30:03.200000Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:03.200234Z  INFO request{method=POST uri="/api/tasks"}: rustflow_server::routes::tasks: [audit] Task 4 created by client 'admin'
2026-01-15T10:30:03.200345Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=0 ms status=201
```

The audit event from the handler (`Task 4 created by client 'admin'`) appears inside the request span. You can see it was a `POST /api/tasks` that resulted in a `201 Created`.

### For an Unauthorized Request

```text
2026-01-15T10:30:04.300000Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_request: started processing request
2026-01-15T10:30:04.300123Z DEBUG request{method=POST uri="/api/tasks"}: tower_http::trace::on_response: finished processing request latency=0 ms status=401
```

No handler events — the `require_api_key` middleware rejected the request before the handler ran. The `status=401` tells the whole story.

## Key Takeaways

1. **`TraceLayer` replaces custom request-logging middleware entirely.** One line — `TraceLayer::new_for_http()` — gives you per-request spans with method, URI, status code, and latency. No custom middleware to write or maintain.

2. **Spans are more powerful than events.** Our old `log_request` emitted a single event (method + URI). `TraceLayer` creates a *span* that wraps the entire request lifecycle. Events emitted by handlers appear inside this span, giving you automatic correlation between "what request" and "what happened."

3. **Status codes are now visible in logs.** This was the biggest gap in our custom middleware. `log_request` fired before the handler ran — it couldn't know the response status. `TraceLayer`'s `on_response` callback fires after the response is produced, so it includes the status code.

4. **Feature flags control what's compiled.** The `trace` feature on `tower-http` is a Cargo feature flag. Without it, `TraceLayer` doesn't exist. This is a common pattern in the Rust ecosystem — large crates use features to let you opt into only what you need.

5. **`TraceLayer` integrates with the subscriber pipeline.** It doesn't write to stdout directly — it emits tracing spans and events that flow through `EnvFilter` and the `fmt` layer. This means `RUST_LOG` controls `TraceLayer` output just like it controls your application's `tracing::info!` calls.

6. **The `tower_http=debug` filter directive is what makes `TraceLayer` output visible.** Without it, `TraceLayer`'s `DEBUG`-level events would be silently filtered out. We set this up in lesson 3.2 specifically for this moment.

7. **Global layers simplify the middleware stack.** Instead of applying logging middleware to each router group individually, `TraceLayer` as a global layer covers everything — API routes, infrastructure, static files. Less duplication, more consistent coverage.

## What's Next

`TraceLayer` gives us automatic request/response logging, but the spans it creates are generic — just method and URI. In lesson 3.4, we'll add `#[tracing::instrument]` to our handler functions to create **operation-level spans** (like `task.create`, `project.list`) that nest inside the request span. Then in lesson 3.5, we'll customize `TraceLayer`'s span creation to include domain-specific fields like request IDs, authenticated client names, and entity IDs.
