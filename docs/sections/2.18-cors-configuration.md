# 2.18 - CORS Configuration

## Overview

Open `http://localhost:3000/` — the RustFlow dashboard loads and displays tasks. Now open a second terminal and start any other HTTP server on port `8080` (e.g., `python3 -m http.server 8080`). Create a small HTML page that fetches `http://localhost:3000/api/tasks` from that server. Open it in a browser. Nothing works — the browser console shows:

```
Access to fetch at 'http://localhost:3000/api/tasks' from origin 'http://localhost:8080'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
on the requested resource.
```

This is **Cross-Origin Resource Sharing (CORS)** — a browser security mechanism that prevents JavaScript running on one origin from making requests to a different origin. Our dashboard works because it's served from `localhost:3000` and calls `localhost:3000/api/tasks` — same origin. An external frontend on a different port or domain is a different origin, and the browser blocks it by default.

In this lesson we configure CORS headers so that external frontends, partner applications, and development tools can call the RustFlow API without being blocked.

### Why This Matters in Enterprise Services

In real-world deployments, your API and frontend are almost never on the same origin:

- **Separate frontend deployment** — React/Vue/Angular apps on `app.company.com` calling APIs on `api.company.com`
- **Development workflows** — Frontend devs running `localhost:5173` (Vite) calling `localhost:3000` (RustFlow)
- **Partner integrations** — Third-party dashboards embedding your API data
- **Mobile web views** — Native apps loading web components that call your API

Without CORS configuration, all of these are blocked by the browser. The API itself is fine — `curl` and server-to-server calls ignore CORS entirely. It's purely a browser enforcement mechanism.

## What Is CORS?

CORS is a protocol between the browser and the server. The browser asks "is this cross-origin request allowed?" and the server answers by including (or not including) specific response headers.

### Same-Origin Policy

Browsers enforce a **same-origin policy**: JavaScript can only make HTTP requests to the same origin that served the page. An origin is defined by the tuple `(scheme, host, port)`:

```text
http://localhost:3000/dashboard    ← origin: (http, localhost, 3000)
http://localhost:3000/api/tasks    ← same origin ✅ (scheme, host, port all match)
http://localhost:8080/             ← different origin ❌ (port differs)
https://localhost:3000/            ← different origin ❌ (scheme differs)
http://api.rustflow.dev/           ← different origin ❌ (host differs)
```

### How CORS Relaxes the Policy

The server opts in to cross-origin access by returning CORS headers:

```text
Access-Control-Allow-Origin: http://localhost:8080     ← "I allow this origin"
Access-Control-Allow-Methods: GET, POST, PUT, DELETE   ← "I allow these methods"
Access-Control-Allow-Headers: Content-Type, x-api-key  ← "I allow these headers"
```

Without these headers, the browser silently discards the response — the request might succeed on the server side, but JavaScript never sees the result.

### Simple vs Preflight Requests

Not all cross-origin requests are treated the same. The browser classifies every cross-origin request as either **simple** or **non-simple**, and handles them very differently.

#### Simple Requests — No Preflight

A request is "simple" only if it meets **all** of these conditions:

| Condition | Allowed values |
|---|---|
| **Method** | `GET`, `HEAD`, or `POST` only |
| **Headers** | Only "CORS-safelisted" headers: `Accept`, `Accept-Language`, `Content-Language`, `Content-Type` (with restrictions) |
| **Content-Type** (if POST) | Only `text/plain`, `multipart/form-data`, or `application/x-www-form-urlencoded` |

If a request is simple, the browser sends it **directly** to the server — no prior permission check. It adds an `Origin` header so the server knows the request is cross-origin. After the response arrives, the browser checks for `Access-Control-Allow-Origin` in the response headers. If present and matching, JavaScript gets the response. If absent, the browser discards the response silently.

```text
Simple request flow (e.g., GET /api/tasks):

  Browser                              Server
    │                                    │
    ├── GET /api/tasks ─────────────────►│
    │   Origin: http://localhost:8080    │
    │                                    ├── handler runs, builds response
    │◄── 200 OK ─────────────────────────┤
    │   Access-Control-Allow-Origin: ... │
    │                                    │
    ├── Header present? ─► JS gets data  │
    └── Header absent?  ─► JS gets error │
```

Example: a plain `GET` with no custom headers. Your dashboard's `fetch('/api/tasks')` is simple (same origin so CORS doesn't apply at all, but a cross-origin `GET` would be simple too).

#### Preflight Requests — The Permission Check

If **any** condition for a simple request is violated, the browser sends a **preflight** first. A preflight is an automatic `OPTIONS` request — the browser sends it on its own before your actual request. Your JavaScript code never sees it; `fetch()` doesn't send it manually. The browser does it behind the scenes.

**Why does the preflight exist?** It's a safety mechanism. Before CORS existed, servers could assume that cross-origin requests with custom headers or non-standard methods were impossible from a browser. Adding CORS couldn't retroactively make those servers accept such requests — that would break security. So the spec requires the browser to _ask first_. If the server doesn't explicitly opt in (by responding correctly to the `OPTIONS`), the browser never sends the real request.

Think of it like this: a `GET` can't cause damage — it's read-only. But a `DELETE` with a custom auth header could destroy data. The preflight ensures the server has intentionally opted in to receiving that kind of request from that origin.

#### The Preflight Lifecycle

Here's the full timeline for a cross-origin `POST /api/tasks` with `Content-Type: application/json` and `x-api-key`:

```text
Step 1 — Preflight (automatic, invisible to your JS code):

  Browser                                      Server
    │                                            │
    ├── OPTIONS /api/tasks ─────────────────────►│
    │   Origin: http://localhost:8080            │
    │   Access-Control-Request-Method: POST      │
    │   Access-Control-Request-Headers:          │
    │     content-type, x-api-key                │
    │                                            │
    │   (No body. No auth header. Just          │
    │    "would you accept this kind of         │
    │    request from this origin?")             │
    │                                            │
    │◄── 200 OK ─────────────────────────────────┤
    │   Access-Control-Allow-Origin:             │
    │     http://localhost:8080                   │
    │   Access-Control-Allow-Methods:            │
    │     GET,POST,PUT,PATCH,DELETE               │
    │   Access-Control-Allow-Headers:            │
    │     content-type,x-api-key                  │
    │   Access-Control-Max-Age: 3600             │
    │   Content-Length: 0                         │
    │                                            │
    ├── Preflight passed ✅                       │
    │                                            │

Step 2 — Actual request (your fetch() runs):

    │                                            │
    ├── POST /api/tasks ────────────────────────►│
    │   Origin: http://localhost:8080            │
    │   Content-Type: application/json           │
    │   x-api-key: rustflow-api-key-2026         │
    │   {"title": "New task"}                    │
    │                                            ├── auth middleware checks key
    │                                            ├── handler creates task
    │◄── 201 Created ───────────────────────────┤
    │   Access-Control-Allow-Origin:             │
    │     http://localhost:8080                   │
    │   {"id": 4, "title": "New task", ...}     │
    │                                            │
    └── JS receives the response ✅               │
```

Notice the preflight `OPTIONS` request has:
- **No body** — it's just asking a question
- **No `x-api-key`** — the browser hasn't been told it's allowed to send it yet
- **No `Content-Type: application/json`** — same reason
- `Access-Control-Request-Method` — tells the server "I want to send a POST"
- `Access-Control-Request-Headers` — tells the server "I want to send these headers"

The server's response to the `OPTIONS` is the permission slip. Only after receiving it does the browser send the real `POST`.

#### What If the Preflight Fails?

If the server doesn't return the right CORS headers on the `OPTIONS` response, the browser **never sends the actual request**:

```text
Failed preflight:

  Browser                                 Server
    │                                       │
    ├── OPTIONS /api/tasks ────────────────►│
    │   Origin: http://evil.example.com    │
    │                                       │
    │◄── 200 OK ────────────────────────────┤
    │   (no Access-Control-Allow-Origin)    │
    │                                       │
    ├── Preflight FAILED ❌                  │
    │   The actual POST is never sent.      │
    │   JavaScript gets a network error.    │
    │                                       │
    └── console: "CORS policy blocked..."   │
```

Your server never sees the `POST`. The `OPTIONS` arrived and was answered (even a bare `200 OK` without CORS headers counts as "answered"), but the permission wasn't granted, so the browser stops.

#### What Triggers a Preflight? (Complete List)

The browser sends a preflight if **any** of these are true:

| Trigger | Example | Why it's "non-simple" |
|---|---|---|
| Method is not GET/HEAD/POST | `PUT /api/tasks/1` | PUT/DELETE/PATCH didn't exist in early HTTP forms |
| Custom headers | `x-api-key: abc123` | Only standard headers existed before CORS |
| `Content-Type` is not a form type | `Content-Type: application/json` | Browsers only sent form-encoded data before CORS |
| Request includes `ReadableStream` | Streaming request body | Modern feature, needs explicit opt-in |

For RustFlow, nearly every write request triggers a preflight because we use:
- `Content-Type: application/json` (non-simple content type)
- `x-api-key` header (custom header)
- `PUT`, `DELETE`, `PATCH` methods (non-simple methods)

Even our `POST` with `Content-Type: application/json` triggers a preflight — if it were `Content-Type: application/x-www-form-urlencoded`, it wouldn't. But JSON is the right format for an API, so we accept the preflight cost.

#### Preflight Caching with `Max-Age`

The `Access-Control-Max-Age` header tells the browser to cache the preflight result — so it doesn't send an `OPTIONS` request for every single API call:

```text
Without max_age:
  OPTIONS /api/tasks → 200    (preflight)
  POST /api/tasks    → 201    (actual)
  OPTIONS /api/tasks → 200    (preflight again!)
  POST /api/tasks    → 201    (actual)
  OPTIONS /api/tasks → 200    (preflight again!)
  POST /api/tasks    → 201    (actual)
  
  = 6 HTTP roundtrips for 3 API calls

With max_age: 3600:
  OPTIONS /api/tasks → 200    (preflight — cached for 1 hour)
  POST /api/tasks    → 201    (actual)
  POST /api/tasks    → 201    (actual — cached preflight reused)
  POST /api/tasks    → 201    (actual — cached preflight reused)
  
  = 4 HTTP roundtrips for 3 API calls (and only 1 preflight per hour)
```

In production, you want `max_age` to be at least `3600` (1 hour). Some APIs set it to `86400` (24 hours). The browser may cap it — Chrome caps at 2 hours, Firefox at 24 hours — but setting a high value is still correct.

### Why Our API Triggers Preflights

RustFlow's protected endpoints require the `x-api-key` custom header. Custom headers _always_ trigger preflight requests. Even `Content-Type: application/json` on POST requests triggers a preflight (only `text/plain`, `multipart/form-data`, and `application/x-www-form-urlencoded` are considered "simple").

So every write request from an external frontend will be:
1. `OPTIONS /api/tasks` (preflight) — browser asks permission
2. `POST /api/tasks` (actual) — browser sends the real request

Our server needs to handle both. `CorsLayer` handles both automatically — it intercepts `OPTIONS` and responds with the correct headers, and it adds CORS headers to normal responses.

## `tower-http`'s `CorsLayer`

We've used `tower-http` since 2.13 for static file serving. Now we enable its `cors` feature for the `CorsLayer` — a Tower layer that automatically handles CORS preflight requests and adds the correct response headers.

```rust
use tower_http::cors::{CorsLayer, Any};

let cors = CorsLayer::new()
    .allow_origin(Any)                          // any origin can call us
    .allow_methods(Any)                         // GET, POST, PUT, DELETE, etc.
    .allow_headers(Any);                        // Content-Type, x-api-key, etc.

let app = Router::new()
    .route("/api/tasks", get(list).post(create))
    .layer(cors);                               // ← one line, entire API is CORS-enabled
```

`CorsLayer` intercepts every request:
- For `OPTIONS` preflight requests: responds immediately with the CORS headers (the request never reaches your handlers)
- For actual requests: passes through to the handler, then adds CORS headers to the response

### Permissive vs Restrictive

`CorsLayer` offers two starting points:

```rust
// Permissive — allow everything (good for development)
let cors = CorsLayer::permissive();

// Very permissive — same as permissive but also allows credentials
let cors = CorsLayer::very_permissive();

// Restrictive (default) — allow nothing, you opt in to each thing
let cors = CorsLayer::new()
    .allow_origin("https://app.rustflow.dev".parse::<HeaderValue>().unwrap())
    .allow_methods([Method::GET, Method::POST, Method::PUT, Method::DELETE])
    .allow_headers([CONTENT_TYPE, HeaderName::from_static("x-api-key")])
    .max_age(Duration::from_secs(3600));
```

For development we'll use a configured layer that allows everything explicitly — so you understand each setting. In the exercises, you'll lock it down for production.

### Layer Ordering Matters

CORS must be the **outermost** middleware layer (applied last in code, runs first on incoming requests). If auth middleware runs before CORS, it will reject the `OPTIONS` preflight request (which has no `x-api-key` header) with `401 Unauthorized`, and the browser will never make the actual request.

```text
❌ Wrong order:
  Request → [Auth] → [CORS] → Handler
  OPTIONS /api/tasks → Auth says "no x-api-key!" → 401 → browser gives up

✅ Correct order:
  Request → [CORS] → [Auth] → Handler
  OPTIONS /api/tasks → CORS responds 200 with headers → browser sends real request
  POST /api/tasks → CORS passes through → Auth checks key → Handler runs
```

In Axum, layers are applied in **reverse order** — the last `.layer()` call is the outermost middleware:

```rust
Router::new()
    .route("/", post(create))
    .layer(auth_middleware)     // ← inner: runs second
    .layer(cors)               // ← outer: runs first (CORS must be here)
```

Our auth middleware is already scoped to protected sub-routers (from 2.17), so in practice there's no conflict — but it's still correct to apply CORS outermost on the whole app.

## Step 2: Add CORS to the Application

**Update** `crates/rustflow-server/src/main.rs` — import `CorsLayer` and apply it as the outermost layer:

```rust name=crates/rustflow-server/src/main.rs
mod extractors;
mod routes;
mod state;
mod errors;

use crate::state::AppState;
use axum::Router;
use axum::http::{HeaderName, HeaderValue, Method};
use rustflow_common::{APP_NAME, APP_VERSION};
use std::time::Duration;
use tokio::net::TcpListener;
use tower_http::cors::CorsLayer;
use tower_http::services::{ServeDir, ServeFile};

#[tokio::main]
async fn main() {
    let state: AppState = AppState::new();

    // ── CORS configuration ──────────────────────────────────
    //
    // Allow any origin, any method, and specific headers.
    // In production, lock this down to known origins.
    let cors = CorsLayer::new()
        .allow_origin("http://localhost:3000".parse::<HeaderValue>().unwrap())
        .allow_methods([
            Method::GET,
            Method::POST,
            Method::PUT,
            Method::PATCH,
            Method::DELETE,
        ])
        .allow_headers([
            HeaderName::from_static("content-type"),
            HeaderName::from_static("x-api-key"),
        ])
        .max_age(Duration::from_secs(3600));

    // Build the application router
    let app = Router::new()
        // Serve the dashboard at root
        .route_service("/", ServeFile::new("crates/rustflow-server/static/index.html"))
        // Serve static files from /static/*
        .nest_service(
            "/static",
            ServeDir::new("crates/rustflow-server/static")
                .append_index_html_on_directories(true)
        )
        .route_service("/favicon.ico", ServeFile::new("crates/rustflow-server/static/favicon.ico"))
        // Health & config — merged at root level (no prefix)
        .merge(routes::health::router())
        // Domain routes — nested under /api/*
        .nest("/api/tasks", routes::tasks::router(state.clone()))
        .nest("/api/projects", routes::projects::router(state.clone()))
        .nest("/api/users", routes::users::router(state.clone()))
        // Enrichment — combines local data with external API calls
        .nest("/api/enrichment", routes::enrichment::router())
        // Provide state to ALL routes (merged and nested)
        .with_state(state)
        // CORS — outermost layer, runs first on every request
        .layer(cors);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr)
        .await
        .expect("Failed to bind to address");

    println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

    axum::serve(listener, app).await.expect("Server error");
}
```

### Anatomy of the CORS Configuration

Let's walk through each setting:

**`allow_origin`** — Which origins are allowed to make cross-origin requests.

```rust
// Single specific origin (what we use — our dashboard)
.allow_origin("http://localhost:3000".parse::<HeaderValue>().unwrap())

// Multiple origins
.allow_origin([
    "http://localhost:3000".parse::<HeaderValue>().unwrap(),
    "https://app.rustflow.dev".parse::<HeaderValue>().unwrap(),
])

// Any origin (development convenience — insecure for production)
.allow_origin(tower_http::cors::Any)
```

We use a specific origin for now. In the exercises you'll switch to `Any` for development and discuss production strategies.

**`allow_methods`** — Which HTTP methods are permitted in cross-origin requests.

```rust
.allow_methods([Method::GET, Method::POST, Method::PUT, Method::PATCH, Method::DELETE])
```

We list exactly the methods our API uses. `OPTIONS` is handled automatically by `CorsLayer` and doesn't need to be listed.

**`allow_headers`** — Which request headers the client can send.

```rust
.allow_headers([
    HeaderName::from_static("content-type"),
    HeaderName::from_static("x-api-key"),
])
```

`content-type` is needed for JSON requests. `x-api-key` is our authentication header. If we forget to list `x-api-key`, the browser will block any authenticated request — the preflight will fail because the server doesn't declare it allows that header.

**`max_age`** — How long the browser caches preflight results.

```rust
.max_age(Duration::from_secs(3600))  // 1 hour
```

Without this, the browser sends a preflight `OPTIONS` request before _every_ non-simple request. With `max_age(3600)`, it sends one preflight per hour per endpoint. This is a significant performance optimization for chatty frontends.

### The `Vary` Header — Automatic Cache Safety

When you test with `curl`, you'll notice `CorsLayer` adds a header you didn't configure:

```text
vary: origin, access-control-request-method, access-control-request-headers
```

`Vary` is a **caching instruction**. It tells any intermediate cache (CDN, reverse proxy, browser HTTP cache) that this response depends on certain request headers. A cache must not serve a stored response unless the listed headers match exactly.

**Why CORS needs it:** Without `Vary`, a cache could serve the wrong CORS response:

```text
❌ Without Vary — cache poisoning:

  1. Request from http://localhost:3000 (allowed origin)
     → Response cached with: Access-Control-Allow-Origin: http://localhost:3000

  2. Request from http://evil.example.com (not allowed)
     → Cache says "I have a cached 200 for /api/tasks!"
     → Serves the cached response WITH Allow-Origin: http://localhost:3000
     → Origin doesn't match the request, but the damage depends on the setup

✅ With Vary: origin — cache-safe:

  1. Request with Origin: http://localhost:3000
     → Cached under key: (/api/tasks, origin=http://localhost:3000)

  2. Request with Origin: http://evil.example.com
     → Different Origin header → cache miss → server generates fresh response
     → Server doesn't include Allow-Origin → browser blocks ✅
```

The three values explained:

| Vary value | Why it's listed |
|---|---|
| `origin` | The `Access-Control-Allow-Origin` response header depends on which origin made the request |
| `access-control-request-method` | Preflight responses depend on which method was requested |
| `access-control-request-headers` | Preflight responses depend on which custom headers were requested |

`CorsLayer` sets `Vary` automatically on **every** response — not just preflights — because even normal responses carry `Access-Control-Allow-Origin`, which varies by origin. This is required by the [CORS specification](https://fetch.spec.whatwg.org/#http-responses). You don't need to configure it.

### Why `.layer(cors)` Is After `.with_state()`

In Axum, `.with_state()` finalizes the router by binding state, converting `Router<AppState>` to `Router<()>`. Layers applied after `.with_state()` are **outermost** — they run first on incoming requests and last on outgoing responses. CORS must be outermost so it handles `OPTIONS` preflight requests before any auth middleware runs.

```text
Request flow:
  → [CORS layer]                          ← runs first (handles OPTIONS, adds headers)
    → [Axum router with state]
      → [per-route middleware: auth, logging]
        → [handler]
      ← response flows back
    ← CORS adds response headers
  ← response to client
```

### Simulate a Preflight Request

```bash
# Simulate what the browser sends before a POST with custom headers
curl -s -D - -o /dev/null -X OPTIONS \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type, x-api-key" \
  http://localhost:3000/api/tasks
```

Expected response:
```text
HTTP/1.1 200 OK
access-control-allow-origin: http://localhost:3000
access-control-allow-methods: GET,POST,PUT,PATCH,DELETE
access-control-allow-headers: content-type,x-api-key
access-control-max-age: 3600
content-length: 0
```

The `200 OK` with `content-length: 0` means the preflight succeeded — the browser would proceed with the actual `POST` request.

## How CorsLayer Works Internally

`CorsLayer` is a Tower layer — it wraps the entire router in a Service that intercepts requests:

```text
┌─────────────────────────────────────────────┐
│  CorsService (created by CorsLayer)         │
│                                             │
│  1. Is this an OPTIONS preflight?           │
│     YES → respond 200 with CORS headers     │
│            (never reaches inner service)     │
│     NO  → continue to step 2               │
│                                             │
│  2. Does the Origin header match?           │
│     YES → call inner service, add headers   │
│     NO  → call inner service, no headers    │
│            (browser blocks the response)    │
│                                             │
│  ┌────────────────────────────────────────┐ │
│  │  Inner Service (your Axum Router)      │ │
│  └────────────────────────────────────────┘ │
└─────────────────────────────────────────────┘
```

Key insight: the CORS layer doesn't _block_ non-matching origins — it just doesn't add the `Access-Control-Allow-Origin` header. The browser is the one that blocks. Server-to-server calls (curl, reqwest, gRPC) ignore CORS entirely because they're not browsers.

## CORS in Production

The configuration we've built is for development. Production CORS requires more thought:

### Specific Origins Only

```rust
// Production: explicit origin list
.allow_origin([
    "https://app.rustflow.dev".parse::<HeaderValue>().unwrap(),
    "https://staging.rustflow.dev".parse::<HeaderValue>().unwrap(),
])
```

Never use `Any` in production — it allows any website to make API calls to your service on behalf of your users.

### Credentials (Cookies, Auth Headers)

If your frontend sends cookies or `Authorization` headers, you need:

```rust
.allow_credentials(true)
```

But there's a catch: `allow_credentials(true)` is **incompatible** with `allow_origin(Any)`. You must list specific origins. This is a browser security requirement — if any origin could send credentialed requests, it would defeat the purpose.

### Expose Response Headers

By default, browsers only expose "simple" response headers (Cache-Control, Content-Language, Content-Type, Expires, Last-Modified, Pragma) to JavaScript. To expose custom headers:

```rust
.expose_headers([
    HeaderName::from_static("x-request-id"),
    HeaderName::from_static("x-authenticated-as"),
])
```

Without this, your frontend's JavaScript can't read custom response headers — even though they're in the HTTP response.

## Key Takeaways

1. **CORS is a browser concern, not a server concern.** `curl` and server-to-server calls ignore CORS entirely. The server's job is to include the right headers so browsers allow JavaScript to read the response.

2. **Preflight requests are automatic.** Any cross-origin request with custom headers (`x-api-key`) or non-simple methods (PUT, DELETE, PATCH) triggers an `OPTIONS` preflight. `CorsLayer` handles this transparently.

3. **CORS must be the outermost layer.** If auth middleware runs first, it rejects `OPTIONS` preflight requests (which have no API key), and the browser never makes the real request.

4. **`max_age` is a performance optimization.** Without it, every non-simple cross-origin request incurs a double HTTP roundtrip (preflight + actual). Caching preflights for an hour (`3600s`) eliminates this overhead.

5. **`Any` origin in production is a security risk.** It allows any website to make API calls to your service on behalf of users. Always use explicit origin lists in production.

6. **`tower-http` features are additive.** We enabled `cors` alongside `fs`. Each feature brings in only the code it needs — no bloat from unused middleware.
