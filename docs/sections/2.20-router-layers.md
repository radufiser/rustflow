# 2.20 - Router Layers

## Overview

After implementing the 2.19 exercises, our `main.rs` has per-domain rate limiting with a reusable `rate_limited()` helper:

```rust
/// Wraps a router with the full rate-limiting layer stack:
/// 429 conversion → HandleError → Buffer → LoadShed → RateLimit → router
fn rate_limited<S: Clone + Send + Sync + 'static>(
    router: Router<S>,
    num: u64,
    per: Duration,
) -> Router<S> {
    let retry_after = per.as_secs().to_string();
    router.layer(
        ServiceBuilder::new()
            .layer(middleware::from_fn(move |request: Request, next: Next| {
                let retry_after = retry_after.clone();
                async move {
                    let mut response = next.run(request).await;
                    if response.status() == StatusCode::SERVICE_UNAVAILABLE {
                        *response.status_mut() = StatusCode::TOO_MANY_REQUESTS;
                        if let Ok(val) = HeaderValue::from_str(&retry_after) {
                            response.headers_mut().insert("Retry-After", val);
                        }
                    }
                    response
                }
            }))
            .layer(HandleErrorLayer::new(|err: BoxError| async move {
                (StatusCode::SERVICE_UNAVAILABLE, format!("Service overloaded: {}", err))
            }))
            .layer(BufferLayer::new(100))
            .layer(LoadShedLayer::new())
            .layer(RateLimitLayer::new(num, per)),
    )
}
```

And the router composition applies per-domain limits with CORS on the API group:

```rust
let api = Router::new()
    .nest("/tasks", rate_limited(routes::tasks::router(state.clone()), 50, Duration::from_secs(10)))
    .nest("/projects", rate_limited(routes::projects::router(state.clone()), 30, Duration::from_secs(10)))
    .nest("/users", rate_limited(routes::users::router(state.clone()), 20, Duration::from_secs(10)))
    .nest("/enrichment", rate_limited(routes::enrichment::router(), 10, Duration::from_secs(10)))
    .layer(cors);

let app = Router::new()
    .route_service("/", ServeFile::new(...))
    .nest_service("/static", ServeDir::new(...))
    .route_service("/favicon.ico", ServeFile::new(...))
    .merge(routes::health::router())
    .nest("/api", api)
    .with_state(state);
```

Meanwhile, each route module still has its own logging middleware:

```rust
// tasks.rs
public.merge(protected)
    .layer(middleware::from_fn(log_request))
    .layer(middleware::from_fn(log_elapsed_time))

// projects.rs — same two lines
// users.rs — same two lines
```

This works well — health checks and static files are exempt from rate limiting, and each domain has its own rate limit bucket. But there are remaining problems:

1. **Middleware duplication** — `log_request` and `log_elapsed_time` are applied identically in three files. Add a fourth domain (e.g., `comments`) and you must remember to add them again. Forget one, and you have invisible requests.

2. **No centralized middleware view** — Rate limiting is configured in `main.rs`, logging is in three route modules, auth is in each route module. To answer "what middleware runs on `POST /api/tasks`?", you must read four files.

3. **CORS is too narrow** — CORS is applied only to the API router. If a browser fetches `/health` or a static file from a different origin, there are no CORS headers. This breaks browser-based monitoring dashboards and cross-origin `<link>` or `fetch()` calls to static resources. CORS is cheap — it should cover everything.

4. **Health checks have no logging** — Monitoring traffic is invisible. If a Kubernetes liveness probe starts failing, you have no log trail showing when `/health` requests stopped arriving.

In this lesson we **reorganize the middleware stack** into a clean, composable architecture. Middleware is applied at the right scope — per-route-group — and the entire stack is visible in one place.

### The Target Architecture

```text
Root Router
├── CORS (global — applied to everything)
│
├── Static files: /, /static/*, /favicon.ico     ← NO other middleware
├── Health / Config: /health, /config             ← logging only
└── API Router (/api/*)                           ← logging + per-domain rate limiting
    ├── Tasks (rate_limited: 50/10s, auth on writes)
    ├── Projects (rate_limited: 30/10s, auth on writes)
    ├── Users (rate_limited: 20/10s, auth on writes)
    └── Enrichment (rate_limited: 10/10s)
```

- **Static files** are served raw — no logging, no rate limiting overhead
- **Health checks** are logged but not rate-limited — monitoring can poll freely, and you can see the traffic in logs
- **API endpoints** get the full middleware stack: logging, per-domain rate limiting, and auth (on writes)
- **CORS** applies to everything (it's cheap and needed for browser requests to any endpoint)

### `ServiceBuilder` — Composing Layers

So far we've used both chained `.layer()` calls and `ServiceBuilder`. The `rate_limited()` helper already uses `ServiceBuilder` internally. Let's formalize when to use each and how they differ.

Tower provides `ServiceBuilder` for composing multiple layers into a single unit:

```rust
use tower::ServiceBuilder;

// Individual layers — verbose, order-dependent
Router::new()
    .layer(layer_a)
    .layer(layer_b)
    .layer(layer_c)

// ServiceBuilder — declares intent, same result
Router::new()
    .layer(
        ServiceBuilder::new()
            .layer(layer_c)     // outermost
            .layer(layer_b)
            .layer(layer_a)     // innermost
    )
```

Important: `ServiceBuilder` applies layers in **top-to-bottom order** (the first layer listed is outermost), while chained `.layer()` calls apply **bottom-to-top** (the last call is outermost). `ServiceBuilder` reads more naturally — the request flows top to bottom through the list.

```text
ServiceBuilder::new()
    .layer(C)     ← request hits this first
    .layer(B)     ← then this
    .layer(A)     ← then this → handler
```

vs.

```text
router
    .layer(A)     ← request hits this LAST
    .layer(B)     ← then this
    .layer(C)     ← request hits this FIRST
```

`ServiceBuilder` reduces confusion, especially when the order matters (which it always does for middleware).

Your `rate_limited()` helper already demonstrates this well — the `ServiceBuilder` inside it lists layers in request order: 429 conversion (outermost) → `HandleError` → `Buffer` → `LoadShed` → `RateLimit` (innermost). In this lesson, we'll use `ServiceBuilder` at the API router level too.

pub fn router(state: AppState) -> Router<AppState> {
    // Public routes — no authentication required
    let public = Router::new()
        .route("/", get(list))

### What Stays in Route Modules vs What Moves to `main.rs`

| Middleware | Scope | Where It Lives |
|---|---|---|
| **Auth** (`require_api_key`) | Per-domain (only writes) | Route modules — it's domain-specific |
| **Logging** (`log_request`, `log_elapsed_time`) | All API routes | `main.rs` — applied once to the API router |
| **Rate limiting** (`rate_limited()`) | Per-domain (different limits) | `main.rs` — applied per-domain via the helper |
| **CORS** (`CorsLayer`) | Everything | `main.rs` — applied to the root router |

The rule of thumb: **domain-specific middleware stays in route modules; cross-cutting middleware moves to `main.rs`.**

Auth is domain-specific — only write routes need it, and different domains might have different auth rules in the future. Logging and rate limiting are cross-cutting — they apply uniformly to all API endpoints, so they belong in one place.

## Step 2: Reorganize `main.rs`

**Update** `crates/rustflow-server/src/main.rs`:

```rust name=crates/rustflow-server/src/main.rs
mod errors;
mod extractors;
mod routes;
mod state;

use crate::routes::middleware::{log_elapsed_time, log_request};
use crate::state::AppState;
use axum::extract::Request;
use axum::http::{HeaderName, HeaderValue, Method, StatusCode};
use axum::middleware::{self, Next};
use axum::Router;
use axum::error_handling::HandleErrorLayer;
use rustflow_common::{APP_NAME, APP_VERSION};
use std::time::Duration;
use tokio::net::TcpListener;
use tower::{BoxError, ServiceBuilder, buffer::BufferLayer, limit::RateLimitLayer, load_shed::LoadShedLayer};
use tower_http::cors::CorsLayer;
use tower_http::services::{ServeDir, ServeFile};

/// Wraps a router with the full rate-limiting layer stack:
/// 429 conversion → HandleError → Buffer → LoadShed → RateLimit → router
fn rate_limited<S: Clone + Send + Sync + 'static>(
    router: Router<S>,
    num: u64,
    per: Duration,
) -> Router<S> {
    let retry_after = per.as_secs().to_string();
    router.layer(
        ServiceBuilder::new()
            .layer(middleware::from_fn(move |request: Request, next: Next| {
                let retry_after = retry_after.clone();
                async move {
                    let mut response = next.run(request).await;
                    if response.status() == StatusCode::SERVICE_UNAVAILABLE {
                        *response.status_mut() = StatusCode::TOO_MANY_REQUESTS;
                        if let Ok(val) = HeaderValue::from_str(&retry_after) {
                            response.headers_mut().insert("Retry-After", val);
                        }
                    }
                    response
                }
            }))
            .layer(HandleErrorLayer::new(|err: BoxError| async move {
                (
                    StatusCode::SERVICE_UNAVAILABLE,
                    format!("Service overloaded: {}", err),
                )
            }))
            .layer(BufferLayer::new(100))
            .layer(LoadShedLayer::new())
            .layer(RateLimitLayer::new(num, per)),
    )
}

#[tokio::main]
async fn main() {
    let state: AppState = AppState::new();

    // ── CORS (global) ───────────────────────────────────────
    // Moved to the root router — browsers need CORS headers
    // for any endpoint, not just API routes
    let cors = CorsLayer::new()
        .allow_origin(
            state.config.cors_origins.iter()
                .filter_map(|o| o.parse::<HeaderValue>().ok())
                .collect::<Vec<_>>()
        )
        .allow_methods([
            Method::GET,
            Method::POST,
            Method::PUT,
            Method::DELETE,
            Method::PATCH,
        ])
        .allow_headers([
            HeaderName::from_static("content-type"),
            HeaderName::from_static("x-api-key"),
        ])
        .expose_headers([HeaderName::from_static("x-authenticated-as")])
        .max_age(Duration::from_secs(3600));

    // ── Static files ────────────────────────────────────────
    // No middleware — served as fast as possible
    let static_router = Router::new()
        .route_service("/", ServeFile::new("crates/rustflow-server/static/index.html"))
        .nest_service(
            "/static",
            ServeDir::new("crates/rustflow-server/static")
                .append_index_html_on_directories(true),
        )
        .route_service(
            "/favicon.ico",
            ServeFile::new("crates/rustflow-server/static/favicon.ico"),
        );

    // ── Infrastructure ──────────────────────────────────────
    // Logging only — no rate limiting (monitoring can poll freely)
    let infra_router = routes::health::router()
        .layer(middleware::from_fn(log_request));

    // ── API routes ──────────────────────────────────────────
    // Per-domain rate limiting (via rate_limited helper) + centralized logging
    // Auth is applied per-domain inside each route module
    let api_router = Router::new()
        .nest("/tasks", rate_limited(routes::tasks::router(state.clone()), 50, Duration::from_secs(10)))
        .nest("/projects", rate_limited(routes::projects::router(state.clone()), 30, Duration::from_secs(10)))
        .nest("/users", rate_limited(routes::users::router(state.clone()), 20, Duration::from_secs(10)))
        .nest("/enrichment", rate_limited(routes::enrichment::router(), 10, Duration::from_secs(10)))
        .layer(
            ServiceBuilder::new()
                // Outermost → innermost (top to bottom = request order)
                .layer(middleware::from_fn(log_request))
                .layer(middleware::from_fn(log_elapsed_time))
        );

    // ── Compose everything ──────────────────────────────────
    let app = Router::new()
        .merge(static_router)
        .merge(infra_router)
        .nest("/api", api_router)
        .with_state(state)
        // CORS is the only global layer — needed for all browser requests
        .layer(cors);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr)
        .await
        .expect("Failed to bind to address");

    println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

    axum::serve(listener, app).await.expect("Server error");
}
```

### What Changed and Why

**Three router groups** instead of one flat list:

1. **`static_router`** — Dashboard, CSS, favicon. No middleware overhead. These are just files being read from disk.

2. **`infra_router`** — Health check and config. Only `log_request` middleware — so you can see monitoring activity in the logs. No rate limiting — a Kubernetes liveness probe hitting `/health` every 5 seconds should never be rate-limited.

3. **`api_router`** — All domain endpoints. Per-domain rate limiting (already in place via `rate_limited()`) plus centralized logging:

```rust
.layer(
    ServiceBuilder::new()
        .layer(middleware::from_fn(log_request))       // outermost — logs path and method
        .layer(middleware::from_fn(log_elapsed_time))  // innermost — times everything including rate limiting
)
```

Request flow through the API router:

```text
Request → log_request → log_elapsed_time → rate_limited(per-domain) → auth (on writes) → handler
```

So `log_request` runs first (logs the request path and method), then `log_elapsed_time` starts timing. The timer includes rate-limiting overhead — if a request is delayed or rejected by the rate limiter, you see that in the timing. This is intentional: you want to know when rate limiting is affecting response times.

**CORS moved to global scope:**

```rust
let app = Router::new()
    .merge(static_router)
    .merge(infra_router)
    .nest("/api", api_router)
    .with_state(state)
    .layer(cors);   // ← now covers everything, not just API
```

Previously CORS only covered `/api/*`. Now it covers health checks and static files too. A monitoring dashboard running on a different origin can fetch `/health` without CORS errors. The overhead is minimal — CORS just adds response headers.

**`ServiceBuilder` at the API router level:**

The API router uses `ServiceBuilder` for its logging layers. Compare the two approaches:

```rust
// Chained — read bottom to top (confusing):
.layer(middleware::from_fn(log_request))        // runs 1st (outermost)
.layer(middleware::from_fn(log_elapsed_time))   // runs 2nd

// ServiceBuilder — read top to bottom (natural):
ServiceBuilder::new()
    .layer(middleware::from_fn(log_request))        // runs 1st (outermost)
    .layer(middleware::from_fn(log_elapsed_time))   // runs 2nd
```

With only two layers the difference is small, but `ServiceBuilder` pays off as stacks grow — and your `rate_limited()` helper already proves this: its five-layer `ServiceBuilder` reads naturally top-to-bottom.

### The Composition Pattern

The final assembly is clean and self-documenting:

```rust
let app = Router::new()
    .merge(static_router)           // GET /, /static/*, /favicon.ico
    .merge(infra_router)            // GET /health, /config
    .nest("/api", api_router)       // /api/tasks, /api/projects, etc.
    .with_state(state)
    .layer(cors);                   // CORS on everything
```

Each router group carries its own middleware stack. When merged/nested, the stacks remain independent. Adding a new infrastructure endpoint means adding it to `infra_router` — it automatically gets logging but not rate limiting. Adding a new domain means nesting it inside `api_router` with `rate_limited()` — it automatically gets the full API middleware stack.

## The Design Principle: Layers at the Right Scope

The key insight is that **not all routes need the same middleware**. Applying everything globally is simple but wasteful (static files don't need logging) and sometimes harmful (rate-limiting health checks breaks monitoring).

The pattern:

```rust
// Global: applies to all routes
let app = Router::new()
    .merge(group_a)
    .merge(group_b)
    .layer(global_layer);          // ← everything

// Per-group: applies to specific routes
let group_a = Router::new()
    .route("/x", get(x))
    .layer(group_a_layers);        // ← only /x

let group_b = Router::new()
    .route("/y", get(y))
    .layer(group_b_layers);        // ← only /y
```

Each router group is an independent unit with its own middleware stack. When composed into the parent router, the stacks don't interfere with each other.

Our architecture goes one level deeper — the API router has group-level logging, and **within** that group each domain has its own rate-limiting stack via `rate_limited()`. This is middleware composition at two levels:

```text
Root (CORS)
└── API group (logging)
    ├── /tasks (rate limiting 50/10s)
    │   └── protected (auth)
    ├── /projects (rate limiting 30/10s)
    │   └── protected (auth)
    └── ...
```

## Key Takeaways

1. **Group routes by middleware requirements.** Static files need nothing. Infrastructure needs logging. API endpoints need the full stack. Don't apply middleware where it's not needed.

2. **`ServiceBuilder` makes layer ordering readable.** The request flows top-to-bottom through the layer list — no more mental reverse-order gymnastics. Your `rate_limited()` helper and the API router's logging stack both benefit from this.

3. **Domain-specific middleware stays in route modules.** Auth middleware is domain-specific (only writes need it, and different domains may have different auth rules in the future). Cross-cutting concerns (logging, rate limiting) belong in `main.rs`.

4. **Each router group is independent.** When you merge or nest routers, their middleware stacks don't interfere. Rate limiting on the API router doesn't affect the health router — they're separate units with separate layer stacks. Per-domain rate limits within the API router are also independent — exhausting the tasks bucket doesn't affect projects.

5. **The composition reads like documentation.** Looking at `main.rs`, you can immediately see: "static files → no middleware, health → logging, API → logging + per-domain rate limiting." This is self-documenting architecture.

6. **CORS belongs at global scope.** Browser requests to any endpoint need CORS headers — health checks, API endpoints, even static files if loaded cross-origin. It's cheap and prevents subtle cross-origin failures in monitoring dashboards or browser-based tools.

## Exercises

1. **Add request timing to health** — Add `log_elapsed_time` to the infrastructure router (in addition to `log_request`). Compare: do health check response times differ from API response times? Why?

2. **Separate read and write rate limits** — Within each domain, apply different rate limits for reads vs writes. For example, tasks reads at 100/10s but task writes at 10/10s. You'll need to split the `rate_limited()` calls — wrap the public and protected sub-routers separately with different limits before merging them. This is common in production APIs: reads are cheap, writes are expensive.

3. **Add a request counter layer** — Write a custom middleware that increments an `AtomicU64` counter on every request and prints the total count every 100 requests. Apply it only to the API router. This is the foundation for metrics (Section 3).

4. **Extract router construction** — Move `static_router`, `infra_router`, and `api_router` construction into a `fn build_app(state: AppState) -> Router` function. This makes `main()` clean and prepares for integration testing (Section 9) where tests need to construct the router without starting a server.

5. **Add compression** — Enable `tower-http`'s `compression` feature and add `CompressionLayer` to the API router. Measure the response size before and after with `curl -s --compressed -D -`. Is compression worth it for JSON responses? When would you skip it?

6. **Conditional middleware** — Use the `AppConfig` to control rate limiting. Add a `rate_limit_enabled: bool` field, and only apply the rate limiter when it's `true`. This previews Section 5 (Configuration) — different environments have different middleware needs.
