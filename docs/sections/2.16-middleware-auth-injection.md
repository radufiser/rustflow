# 2.16 - Middleware Auth with Injection

## Overview

Our middleware from 2.15 acts as a gatekeeper — it checks if the API key is valid and either lets the request through or
rejects it. But the handlers on the other side have no idea _who_ was authenticated. They just know _someone_ passed the
gate.

In enterprise services, this isn't enough. You need to know _which_ client is making the request so you can:

- **Audit** — log who created, modified, or deleted a resource
- **Authorize** — enforce per-client resource limits ("client X can only create 10 tasks")
- **Scope** — filter results by ownership ("show me _my_ tasks")

In this lesson we evolve the auth middleware to **extract an identity** from the request and **inject it into request
extensions** so any downstream handler can read it. The middleware still gates access, but now it also _annotates_ the
request with who the caller is.

### The Pattern: Request Extensions

HTTP requests carry metadata beyond headers and body. Axum (via the underlying `http` crate) provides an **extensions
map** — a type-safe, heterogeneous store attached to every request. Middleware can insert data into extensions, and
handlers can extract it:

```text
Request arrives
  │
  ├── Middleware runs:
  │     1. Validates x-api-key header
  │     2. Looks up who this key belongs to
  │     3. Inserts AuthenticatedClient into request.extensions()
  │
  ├── Handler runs:
  │     1. Extracts AuthenticatedClient from extensions (via Extension<T>)
  │     2. Uses it for logging, auditing, authorization
  │
  └── Response
```

Extensions are type-indexed: you insert and retrieve by Rust type, not by string key. Inserting an `AuthenticatedClient`
doesn't conflict with inserting a `RequestId` or `TraceContext` — each type has its own slot.

```rust
// Middleware inserts:
request.extensions_mut().insert(AuthenticatedClient { name: "ci-bot".into() });

// Handler extracts:
async fn create(Extension(client): Extension<AuthenticatedClient>, ...) {
    println!("Created by: {}", client.name);
}
```

This is the standard pattern for passing context from middleware to handlers in Tower-based services. You'll see it used
for request IDs, trace contexts, authenticated users, and feature flags.

### What Changes from 2.15

```text
2.15:  Middleware checks key → allows/denies
2.16:  Middleware checks key → resolves identity → injects into extensions → allows/denies
       Handler optionally reads identity from extensions
```

The middleware function signature changes to accept state (via `from_fn_with_state`) so it can look up the
key-to-identity mapping. In a real system this mapping would come from a database or identity service; for now we'll use
a simple in-memory map.

## How `from_fn` vs `from_fn_with_state` Differ

In 2.15, our middleware was a plain function with no access to application state:

```rust
// 2.15 — no state access
async fn require_api_key(request: Request, next: Next) -> Response { ... }

// Applied with:
.layer(middleware::from_fn(require_api_key))
```

To look up identities, the middleware needs to access state. `from_fn_with_state` adds the state as the first parameter:

```rust
// 2.16 — with state access
async fn require_api_key(
    State(state): State<AppState>,    // ← state is available
    request: Request,
    next: Next,
) -> Response { ... }

// Applied with:
.layer(middleware::from_fn_with_state(state.clone(), require_api_key))
```

Note: when using `from_fn_with_state`, the state is cloned into the middleware. Since `AppState` is cheap to clone (it's
all `Arc` inside), this is fine. The middleware shares the same underlying data as the handlers.

### Wait — Why Does Middleware Need State for a Key Lookup?

In 2.15, the middleware compared the header against a single constant (`API_KEY`). One key, one identity — no lookup
needed.

Now we want to map keys to identities:

```text
"rustflow-api-key-2026"  →  AuthenticatedClient { name: "default" }
"ci-bot-key-2026"        →  AuthenticatedClient { name: "ci-bot" }
"admin-key-2026"         →  AuthenticatedClient { name: "admin" }
```

This mapping lives in `AppState` so it can be configured at startup (and later loaded from a database). The middleware
needs state to perform the lookup.

## Step 1: Update Common Types

**Update** `crates/rustflow-common/src/lib.rs` — remove the hardcoded `API_KEY` constant and add the
`AuthenticatedClient` type.

Remove:

```rust
pub const API_KEY: &str = "rustflow-api-key-2026";
```

Add, near the other types:

```rust
/// The authenticated identity of the API caller.
///
/// Injected into request extensions by auth middleware.
/// Handlers extract it via `Extension<AuthenticatedClient>`.
#[derive(Debug, Clone, serde::Serialize)]
pub struct AuthenticatedClient {
    /// Human-readable name of the client (e.g., "ci-bot", "admin", "default")
    pub name: String,
}
```

### Why Move This to `rustflow-common`?

`AuthenticatedClient` is a **shared type** — it's used by both the middleware (in `rustflow-server`) and potentially by
other crates in the workspace (e.g., a future `rustflow-notifications` service that also needs to know who triggered an
action). Shared types live in `rustflow-common` per our workspace convention.

### Why Remove `API_KEY`?

We no longer have a single key. The key-to-identity mapping lives in `AppState`, configured at startup. The constant
would be misleading — it suggests there's one key, when now there are many.

### What Changed

1. Added `use std::collections::HashMap;`
2. Added `pub api_keys: HashMap<String, String>` to `AppState`
3. Populated with three keys in `AppState::new()`

The `HashMap<String, String>` maps API key → client name. This is deliberately simple. In production you'd use a struct
with roles, permissions, rate limits, etc. — but the pattern is the same.

### Why Not `Arc<RwLock<HashMap>>>`?

The key map is **immutable after startup** — no handler modifies it at runtime. It lives directly in `AppState` (which
is already cloned via `Arc` internally by Axum). No lock needed for read-only data. This is the same reasoning that
makes `AppConfig` a plain field.

## Step 3: Update the Auth Middleware

**Update** `crates/rustflow-server/src/routes/middleware.rs` — accept state, look up the key, and inject identity into
extensions.

```rust name=crates/rustflow-server/src/routes/middleware.rs
use axum::{
    extract::{Request, State},
    middleware::Next,
    response::Response,
};
use crate::errors::RustFlowError;
use crate::state::AppState;
use axum::response::IntoResponse;
use rustflow_common::AuthenticatedClient;

/// Middleware that validates the `x-api-key` header and injects the
/// authenticated client identity into request extensions.
///
/// Applied to a router with:
/// ```ignore
/// Router::new()
///     .route("/", post(create))
///     .layer(middleware::from_fn_with_state(state.clone(), require_api_key))
/// ```
///
/// After this middleware runs, handlers can extract the identity:
/// ```ignore
/// async fn create(
///     Extension(client): Extension<AuthenticatedClient>,
///     ...
/// ) {
///     println!("Created by: {}", client.name);
/// }
/// ```
pub async fn require_api_key(
    State(state): State<AppState>,
    mut request: Request,
    next: Next,
) -> Response {
    let api_key = request
        .headers()
        .get("x-api-key")
        .and_then(|value| value.to_str().ok());

    match api_key {
        Some(key) => {
            // Look up the key in the state's key map
            if let Some(client_name) = state.api_keys.get(key) {
                // Key is valid — inject the authenticated identity
                request.extensions_mut().insert(AuthenticatedClient {
                    name: client_name.clone(),
                });
                next.run(request).await
            } else {
                // Key provided but not recognized
                RustFlowError::Forbidden("Invalid API key".into()).into_response()
            }
        }
        None => {
            RustFlowError::Unauthorized("Missing x-api-key header".into()).into_response()
        }
    }
}
```

### What Changed from 2.15

**Signature:**

```text
// 2.15
pub async fn require_api_key(request: Request, next: Next) -> Response

// 2.16
pub async fn require_api_key(
    State(state): State<AppState>,   // ← NEW: access to state
    mut request: Request,             // ← NEW: `mut` so we can modify extensions
    next: Next,
) -> Response
```

Three changes:

1. **`State(state): State<AppState>`** — the middleware now receives application state via `from_fn_with_state`
2. **`mut request`** — we need mutability to call `request.extensions_mut().insert(...)`
3. **Identity injection** — on success, we insert `AuthenticatedClient` into extensions before calling `next.run()`

**Validation logic:**

```text
// 2.15: compare against a constant
Some(key) if key == API_KEY => next.run(request).await

// 2.16: look up in the key map, inject identity on match
Some(key) => {
    if let Some(client_name) = state.api_keys.get(key) {
        request.extensions_mut().insert(AuthenticatedClient { ... });
        next.run(request).await
    } else {
        RustFlowError::Forbidden(...)
    }
}
```

### How `extensions_mut().insert()` Works

`request.extensions_mut()` returns a mutable reference to the request's extension map. `.insert(value)` stores the value
indexed by its Rust type. There's no string key — the type _is_ the key:

```rust
// Insert: the key is the type AuthenticatedClient
request.extensions_mut().insert(AuthenticatedClient { name: "admin".into() });

// Extract (in a handler): Axum's Extension<T> reads by type
async fn handler(Extension(client): Extension<AuthenticatedClient>) { ... }
```

If you insert two values of the same type, the second overwrites the first. If you insert values of _different_ types,
they coexist:

```rust
request.extensions_mut().insert(AuthenticatedClient { name: "admin".into() });
request.extensions_mut().insert(RequestId("abc-123".into()));
// Both are stored — different types, different slots
```

This is possible because the extensions map uses `TypeId` as the key internally — Rust's type system becomes the key
space.

## Step 4: Update Route Modules

All three route modules need the same change: switch from `middleware::from_fn` to `middleware::from_fn_with_state`.

### Why Does the Router Need to Pass State?

In 2.15, `from_fn(require_api_key)` created middleware from a plain function — no state needed. Now
`from_fn_with_state(state, require_api_key)` needs an `AppState` value at layer construction time.

But our router factory functions don't have state — they return `Router<AppState>`, which means the state is provided
later via `.with_state()` in `main.rs`. How do we pass state to `from_fn_with_state` inside a router factory?

The answer: **the router factory now receives state as a parameter.**

```text
// 2.15: no state needed
pub fn router() -> Router<AppState> {
    Router::new()
        .route(...)
        .layer(middleware::from_fn(require_api_key))
}

// 2.16: state needed for middleware
pub fn router(state: AppState) -> Router<AppState> {
    Router::new()
        .route(...)
        .layer(middleware::from_fn_with_state(state, require_api_key))
}
```

And in `main.rs`:

```text
// 2.15:
.nest("/api/tasks", routes::tasks::router())

// 2.16:
.nest("/api/tasks", routes::tasks::router(state.clone()))
```

**Update** `crates/rustflow-server/src/routes/tasks.rs`:

```rust name=crates/rustflow-server/src/routes/tasks.rs
use crate::errors::RustFlowError;
use crate::extractors::{ValidatedJson, ValidatedQuery};
use crate::routes::middleware::require_api_key;
use crate::state::AppState;
use axum::extract::{Path, State};
use axum::http::StatusCode;
use axum::routing::{get, patch};
use axum::{middleware, Extension, Json, Router};
use rustflow_common::{AuthenticatedClient, CreateTask, Task, TaskFilter, TaskStatus};

/// GET /tasks?status=pending&priority=high
async fn list(
    State(state): State<AppState>,
    ValidatedQuery(filter): ValidatedQuery<TaskFilter>,
) -> Json<Vec<Task>> {
    let state = state.tasks.0.read().await;

    let filtered: Vec<Task> = state
        .tasks
        .iter()
        .filter(|task| filter.status.as_ref().map_or(true, |s| &task.status == s))
        .filter(|task| filter.priority.as_ref().map_or(true, |p| &task.priority == p))
        .filter(|task| {
            filter.search.as_ref().map_or(true, |s| {
                task.title.contains(s)
                    || task.description.as_ref().map_or(false, |d| d.contains(s))
            })
        })
        .cloned()
        .collect();

    Json(filtered)
}

/// GET /tasks/:id
async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<Json<Task>, RustFlowError> {
    let store = state.tasks.0.read().await;

    store
        .tasks
        .iter()
        .find(|task| task.id == id)
        .cloned()
        .map(Json)
        .ok_or(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
}

/// POST /tasks
///
/// The `Extension(client)` extractor reads the `AuthenticatedClient`
/// that the auth middleware injected into request extensions.
/// We use it here for demonstration — printing who created the task.
async fn create(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<(StatusCode, Json<Task>), RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if store.tasks.iter().any(|x| payload.title == x.title) {
        return Err(RustFlowError::Conflict(format!(
            "Task with title {} already exists",
            payload.title
        )));
    }

    let task = Task {
        id: store.next_id,
        title: payload.title,
        description: payload.description,
        priority: payload.priority,
        status: TaskStatus::Pending,
    };

    store.next_id += 1;
    store.tasks.push(task.clone());

    println!("[audit] Task {} created by client '{}'", task.id, client.name);

    Ok((StatusCode::CREATED, Json(task)))
}

/// DELETE /tasks/:id
async fn delete(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, RustFlowError> {
    let mut store = state.tasks.0.write().await;
    let len_before = store.tasks.len();

    store.tasks.retain(|task| task.id != id);

    if store.tasks.len() < len_before {
        println!("[audit] Task {id} deleted by client '{}'", client.name);
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {id} does not exist"
        )))
    }
}

/// PUT /tasks/:id
async fn update(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    ValidatedJson(payload): ValidatedJson<CreateTask>,
) -> Result<Json<Task>, RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if let Some(task) = store.tasks.iter_mut().find(|task| task.id == id) {
        task.title = payload.title;
        task.description = payload.description;
        task.priority = payload.priority;
        println!("[audit] Task {id} updated by client '{}'", client.name);
        Ok(Json(task.clone()))
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
    }
}

/// PATCH /tasks/:id/status
async fn change_status(
    Extension(client): Extension<AuthenticatedClient>,
    State(state): State<AppState>,
    Path(id): Path<u64>,
    Json(payload): Json<TaskStatus>,
) -> Result<Json<Task>, RustFlowError> {
    let mut store = state.tasks.0.write().await;

    if let Some(task) = store.tasks.iter_mut().find(|task| task.id == id) {
        task.status = payload;
        println!("[audit] Task {id} status changed by client '{}'", client.name);
        Ok(Json(task.clone()))
    } else {
        Err(RustFlowError::NotFound(format!(
            "Task with id {} does not exist",
            id
        )))
    }
}

pub fn router(state: AppState) -> Router<AppState> {
    Router::new()
        .route("/", get(list).post(create))
        .route("/{id}", get(get_one).put(update).delete(delete))
        .route("/{id}/status", patch(change_status))
        .layer(middleware::from_fn_with_state(state, require_api_key))
}
```

### What Changed from 2.15

1. **Imports**: Added `Extension` from axum and `AuthenticatedClient` from `rustflow_common`
2. **Mutation handlers**: Added `Extension(client): Extension<AuthenticatedClient>` as first parameter
3. **Audit logging**: Added `println!("[audit] ...")` lines using `client.name`
4. **Router factory**: Takes `state: AppState` parameter, uses `from_fn_with_state`

The `Extension<T>` extractor is Axum's way to read values from the request extensions map. It implements
`FromRequestParts`, so it's checked before body-consuming extractors. If the extension isn't present (middleware didn't
run), it returns `500 Internal Server Error` — a strong signal that something is misconfigured.

> **Note:** The `list` and `get_one` handlers don't use `Extension(client)` — they could, since the middleware runs for
> all routes. We'll make this cleaner in 2.17 when reads bypass the middleware entirely.

}

async fn create(
    State(state): State<AppState>,
    Json(payload): Json<CreateUser>,
) -> (StatusCode, Json<User>) {
    let mut store = state.users.0.write().await;

    let user = User {
        id: store.next_id,
        email: payload.email,
        first_name: payload.first_name,
        last_name: payload.last_name,
    };

    store.next_id += 1;
    store.users.push(user.clone());
    (StatusCode::CREATED, Json(user))
}

async fn delete(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<StatusCode, RustFlowError> {
    let mut store = state.users.0.write().await;
    let len_before = store.users.len();
    store.users.retain(|user| user.id != id);

    if store.users.len() < len_before {
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(RustFlowError::NotFound(format!(
            "User with id {} not found",
            id
        )))
    }
}

async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<u64>,
) -> Result<(StatusCode, Json<User>), RustFlowError> {
    let store = state.users.0.read().await;
    let found_user = store.users.iter().find(|user| user.id == id);

    if let Some(user) = found_user {
        Ok((StatusCode::OK, Json(user.clone())))
    } else {
        Err(RustFlowError::NotFound(format!(
            "User with id {} not found",
            id
        )))
    }
}

pub fn router(state: AppState) -> Router<AppState> {
    Router::new()
        .route("/users", get(list).post(create))
        .route("/users/{id}", get(get_one).delete(delete))
        .layer(middleware::from_fn_with_state(state, require_api_key))
}
```

## The Extension Pattern in Detail

### What Happens if the Extension Is Missing?

If a handler extracts `Extension<AuthenticatedClient>` but the middleware didn't insert it (e.g., the route isn't behind
the auth layer), Axum returns:

```text
500 Internal Server Error
"Missing request extension: Extension of type `...AuthenticatedClient` was not found."
```

This is a **programming error**, not a client error. It means you forgot to apply the middleware to a route. The loud
500 is intentional — it forces you to fix the misconfiguration.

### Optional Extraction

If you want a handler that _works_ with or without authentication (e.g., showing extra info to authenticated callers),
use `Option<Extension<AuthenticatedClient>>`:

```rust
async fn list(
    auth: Option<Extension<AuthenticatedClient>>,
    State(state): State<AppState>,
) -> Json<Vec<Task>> {
    if let Some(Extension(client)) = auth {
        println!("Listing tasks for authenticated client: {}", client.name);
    }
    // ... return tasks either way
}
```

We don't use this pattern yet (all routes in a given router either have the middleware or don't), but it's useful to
know for mixed-access endpoints.

## Key Takeaways

1. **`from_fn_with_state` gives middleware access to application state.** The state is cloned into the middleware at
   construction time. Since `AppState` is cheap to clone (all `Arc` internals), this adds no meaningful overhead.

2. **Request extensions are the standard way to pass data from middleware to handlers.** They're type-indexed (no string
   keys), type-safe (compiler catches mismatches), and composable (multiple middleware can inject different types
   without conflicts).

3. **`Extension<T>` fails loudly if the middleware didn't run.** A missing extension returns 500 — a programming error,
   not a client error. This is a safety net: you can't accidentally access identity data on an unprotected route without
   getting an immediate, obvious failure.

4. **Identity and authentication are separate concerns.** The middleware does both (validate key + resolve identity),
   but they're conceptually distinct. Authentication asks "is this request allowed?" Identity asks "who is making this
   request?" Separating them enables patterns like "allow anonymous reads but track identity for authenticated callers."

5. **Router factories now accept state.** When middleware needs state, the router that applies it must have state at
   construction time. This is a minor API change (`router()` → `router(state)`) that keeps the middleware composition
   self-contained within each domain module.

6. **Audit logging is trivial once identity is available.** A single `println!` in each handler creates an audit trail.
   In production, you'd use structured logging (Section 3) and write to a dedicated audit store, but the pattern is
   identical.

## Exercises

1. **Add identity to projects and users** — Add `Extension<AuthenticatedClient>` to the mutation handlers in
   `projects.rs` and `users.rs`. Add audit log lines like `[audit] Project {id} created by client '{name}'`.

2. **Add a `role` field** — Extend `AuthenticatedClient` with a `role: String` field (e.g., `"admin"`, `"reader"`,
   `"ci"`). Update the `api_keys` map to include roles. In the `delete` handler, reject non-admin clients with
   `403 Forbidden`.

3. **Return identity in response headers** — Modify the middleware to also set a `x-authenticated-as` response header
   after `next.run()` returns. This helps clients confirm which identity was used. (Hint: modify the response after
   `let response = next.run(request).await`.)

4. **Handle missing extensions gracefully** — What happens if you add `Extension<AuthenticatedClient>` to a handler on a
   route that doesn't have the auth middleware? Try it and observe the error. Then wrap the extraction in
   `Option<Extension<AuthenticatedClient>>` and handle the `None` case gracefully.

5. **Load keys from a JSON file** — Instead of hardcoding the `api_keys` map in `AppState::new()`, read it from a JSON
   file at startup (e.g., `config/api_keys.json`). Parse it with `serde_json::from_str`. This is a stepping stone toward
   Section 5 (Configuration).
