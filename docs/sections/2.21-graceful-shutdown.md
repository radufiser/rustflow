# 2.21 - Graceful Shutdown

## Overview

Stop the RustFlow server right now. What happens?

```bash
# Start the server
cargo run -p rustflow-server &
# Send a request
curl http://localhost:3000/api/tasks &
# Kill the server immediately
kill -9 $!
```

The request in flight is dropped. The TCP connection is reset. The client sees `curl: (52) Empty reply from server` or a connection error. If the client was in the middle of creating a task, the operation may or may not have completed — there's no way to know.

In a development environment, this is fine — just restart. In production, it's catastrophic:

- **In-flight requests are lost** — clients get errors, data may be partially written
- **WebSocket connections are severed** — users lose real-time updates with no explanation
- **Database connections are not cleaned up** — connection pools may leak, locks may be held
- **Load balancers don't know the server is gone** — they keep sending traffic to a dead instance
- **Rolling deployments break** — Kubernetes replaces pods one by one; if old pods die instantly, there's a gap

**Graceful shutdown** is the solution: when the server receives a stop signal, it:
1. Stops accepting **new** connections
2. Waits for **in-flight** requests to complete (up to a timeout)
3. Closes cleanly — connections drained, resources freed, exit code 0

This is not optional in production. Kubernetes sends `SIGTERM` before killing a pod, load balancers drain connections before removing a target, and CI/CD pipelines expect clean exits. Your server must cooperate.

### Signals: SIGTERM and SIGINT

Unix processes receive **signals** — asynchronous notifications from the OS or other processes:

| Signal | Source | Default Behavior |
|---|---|---|
| `SIGTERM` | `kill <pid>`, Kubernetes, Docker | Terminate (polite — "please stop") |
| `SIGINT` | Ctrl+C in terminal | Terminate (user interrupted) |
| `SIGKILL` | `kill -9 <pid>`, OOM killer | Forced termination (cannot be caught) |

`SIGTERM` is the standard "please stop" signal. Well-behaved services catch it, drain in-flight work, and exit cleanly. Kubernetes sends `SIGTERM` first, waits 30 seconds (configurable), then sends `SIGKILL` if the pod is still running.

`SIGINT` is Ctrl+C — what you use during development. We handle both identically.

`SIGKILL` cannot be caught — the OS kills the process immediately. This is the nuclear option that happens when graceful shutdown takes too long.

### The Graceful Shutdown Timeline

```text
Time 0s:   SIGTERM received
            Server stops accepting NEW connections
            In-flight requests continue processing

Time 0-5s: Existing requests complete and return responses
            Idle connections are closed

Time 5s:   All connections drained
            Server exits with code 0 ← ideal case

--- If shutdown takes too long ---

Time 30s:  Kubernetes sends SIGKILL
            Process dies immediately ← avoid this
```

The goal is to always reach "exits with code 0" before the SIGKILL deadline.

## Axum's Graceful Shutdown Support

Axum's `serve` function returns a `Serve` struct with a `.with_graceful_shutdown()` method that accepts a `Future`. When the future completes (signal received), the server begins draining:

```rust
let server = axum::serve(listener, app);

server
    .with_graceful_shutdown(shutdown_signal())
    .await
    .expect("Server error");
```

The `shutdown_signal()` function returns a `Future` that completes when a SIGTERM or SIGINT is received:

```rust
async fn shutdown_signal() {
    // Wait for Ctrl+C or SIGTERM
    // When either arrives, this function returns, and graceful shutdown begins
}
```

Under the hood, `.with_graceful_shutdown()` does:
1. Runs the server and the shutdown future concurrently
2. When the shutdown future completes:
   - Stops the listener (no new connections)
   - Signals all active connections to finish
   - Waits until all responses are sent
   - Returns

### Tokio's Signal Handling

Tokio provides platform-specific signal handling:

```rust
use tokio::signal;

// Wait for Ctrl+C (cross-platform — works on Linux, macOS, Windows)
signal::ctrl_c().await.expect("Failed to listen for Ctrl+C");

// Wait for SIGTERM (Unix-only — doesn't exist on Windows)
#[cfg(unix)]
{
    let mut sigterm = signal::unix::signal(signal::unix::SignalKind::terminate())
        .expect("Failed to listen for SIGTERM");
    sigterm.recv().await;
}
```

We want to respond to **either** signal — whichever comes first. Tokio's `select!` macro races multiple futures:

```rust
tokio::select! {
    _ = signal::ctrl_c() => {
        println!("Received SIGINT (Ctrl+C)");
    }
    _ = sigterm_future => {
        println!("Received SIGTERM");
    }
}
```

`select!` returns as soon as the first future completes. The other future is dropped (cancelled).

## Step 1: Add Graceful Shutdown

**Update** `crates/rustflow-server/src/main.rs`:

```rust name=crates/rustflow-server/src/main.rs
mod extractors;
mod routes;
mod state;
mod errors;

use crate::routes::middleware::{log_elapsed_time, log_request};
use crate::state::AppState;
use axum::middleware;
use axum::Router;
use axum::http::{HeaderName, HeaderValue, Method};
use rustflow_common::{APP_NAME, APP_VERSION};
use std::time::Duration;
use tokio::net::TcpListener;
use tower::ServiceBuilder;
use tower::limit::RateLimitLayer;
use tower::load_shed::LoadShedLayer;
use tower_http::cors::CorsLayer;
use tower_http::services::{ServeDir, ServeFile};

#[tokio::main]
async fn main() {
    let state: AppState = AppState::new();

    // ── CORS ────────────────────────────────────────────────
    let cors = CorsLayer::new()
        .allow_origin("http://localhost:3000".parse::<HeaderValue>().unwrap())
        .allow_methods([
            Method::GET,
            Method::POST,
            Method::PUT,
            Method::PATCH,
            Method::DELETE,
        ])
        .allow_headers([
            HeaderName::from_static("content-type"),
            HeaderName::from_static("x-api-key"),
        ])
        .max_age(Duration::from_secs(3600));

    // ── Static files ────────────────────────────────────────
    let static_router = Router::new()
        .route_service("/", ServeFile::new("crates/rustflow-server/static/index.html"))
        .nest_service(
            "/static",
            ServeDir::new("crates/rustflow-server/static")
                .append_index_html_on_directories(true),
        )
        .route_service(
            "/favicon.ico",
            ServeFile::new("crates/rustflow-server/static/favicon.ico"),
        );

    // ── Infrastructure ──────────────────────────────────────
    let infra_router = routes::health::router()
        .layer(middleware::from_fn(log_request));

    // ── API routes ──────────────────────────────────────────
    let api_router = Router::new()
        .nest("/tasks", routes::tasks::router(state.clone()))
        .nest("/projects", routes::projects::router(state.clone()))
        .nest("/users", routes::users::router(state.clone()))
        .nest("/enrichment", routes::enrichment::router())
        .layer(
            ServiceBuilder::new()
                .layer(LoadShedLayer::new())
                .layer(RateLimitLayer::new(50, Duration::from_secs(10)))
                .layer(middleware::from_fn(log_elapsed_time))
                .layer(middleware::from_fn(log_request))
        );

    // ── Compose everything ──────────────────────────────────
    let app = Router::new()
        .merge(static_router)
        .merge(infra_router)
        .nest("/api", api_router)
        .with_state(state)
        .layer(cors);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr)
        .await
        .expect("Failed to bind to address");

    println!("{} v{} listening on {}", APP_NAME, APP_VERSION, addr);

    // ── Serve with graceful shutdown ────────────────────────
    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal())
        .await
        .expect("Server error");

    // This line runs AFTER the server has fully drained
    println!("{} has shut down gracefully", APP_NAME);
}

/// Waits for a shutdown signal (SIGINT or SIGTERM).
///
/// Returns when either signal is received, triggering graceful shutdown.
/// - SIGINT: Ctrl+C in terminal (development)
/// - SIGTERM: `kill <pid>`, Kubernetes pod termination (production)
async fn shutdown_signal() {
    let ctrl_c = async {
        tokio::signal::ctrl_c()
            .await
            .expect("Failed to install Ctrl+C handler");
    };

    #[cfg(unix)]
    let terminate = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("Failed to install SIGTERM handler")
            .recv()
            .await;
    };

    // On non-Unix platforms (Windows), only listen for Ctrl+C
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c => {
            println!("\nReceived SIGINT (Ctrl+C), starting graceful shutdown...");
        }
        _ = terminate => {
            println!("\nReceived SIGTERM, starting graceful shutdown...");
        }
    }
}
```

### Anatomy of the Changes

**The server startup** changes one line:

```rust
// Before (2.20):
axum::serve(listener, app).await.expect("Server error");

// After (2.21):
axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal())
    .await
    .expect("Server error");
```

That's it. One method call. Axum and Hyper handle the rest — stop accepting connections, drain in-flight requests, close cleanly.

**The `shutdown_signal` function** is the only new code:

```rust
async fn shutdown_signal() {
    // ...set up signal listeners...
    tokio::select! {
        _ = ctrl_c => { ... }
        _ = terminate => { ... }
    }
}
```

This function is a `Future` that never completes until a signal arrives. `with_graceful_shutdown` polls it concurrently with the server. When the signal fires, the function returns, and the server begins draining.

### `#[cfg(unix)]` — Platform Conditional Compilation

```rust
#[cfg(unix)]
let terminate = async {
    tokio::signal::unix::signal(SignalKind::terminate())
        .expect("Failed to install SIGTERM handler")
        .recv()
        .await;
};

#[cfg(not(unix))]
let terminate = std::future::pending::<()>();
```

`SIGTERM` is a Unix concept — it doesn't exist on Windows. `#[cfg(unix)]` is Rust's **conditional compilation** attribute: the code is only compiled on Unix-like systems (Linux, macOS, FreeBSD).

On Windows, we replace it with `std::future::pending()` — a future that never completes. Since `tokio::select!` returns on the _first_ future to complete, `ctrl_c` will always win on Windows.

In practice, RustFlow will run on Linux in production (containers) and macOS in development — both Unix. But the Windows fallback makes the code portable and prevents compilation errors for anyone working on Windows.

### `tokio::select!` Deep Dive

```rust
tokio::select! {
    _ = ctrl_c => {
        println!("\nReceived SIGINT (Ctrl+C)...");
    }
    _ = terminate => {
        println!("\nReceived SIGTERM...");
    }
}
```

`select!` concurrently polls multiple futures and returns when the **first one** completes:

- If Ctrl+C arrives first: the `ctrl_c` branch runs, `terminate` is dropped
- If SIGTERM arrives first: the `terminate` branch runs, `ctrl_c` is dropped
- Both cannot fire — `select!` picks one

The `_ =` pattern means we don't care about the future's return value — we only care that it completed (signal received).

### The Post-Shutdown Line

```rust
axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal())
    .await
    .expect("Server error");

// This runs AFTER all connections are drained
println!("{} has shut down gracefully", APP_NAME);
```

This line is crucial. The `.await` on `serve()` blocks until **all connections are fully drained**. Only then does execution continue. This is where you'd put cleanup logic:

- Close database connections
- Flush log buffers
- Send final metrics
- Notify service registry that you're offline

For now we just print a message. In Section 8 (Database), we'll add connection pool cleanup here.

### Compare With Forced Kill

```bash
cargo run -p rustflow-server &
SERVER_PID=$!
sleep 1

# Force kill — no graceful shutdown
kill -9 $SERVER_PID
wait $SERVER_PID
echo "Exit code: $?"
# → Exit code: 137 (128 + 9 = SIGKILL)
```

Exit code 137 signals a forced kill. Kubernetes logs this as `OOMKilled` or `Error`, not `Completed`. In-flight requests are dropped.

## Graceful Shutdown in Production

### Kubernetes Pod Lifecycle

When Kubernetes decides to terminate a pod (rolling update, scale-down, node drain):

```text
1. Pod marked for termination
2. Pod removed from Service endpoints (no new traffic from load balancer)
3. preStop hook runs (if configured)
4. SIGTERM sent to PID 1 (your Rust binary)
5. Grace period starts (default: 30 seconds)
6. Your server drains in-flight requests
7. Server exits with code 0
8. Kubernetes cleans up the pod

--- If server hasn't exited after grace period ---

9. SIGKILL sent — process dies immediately
```

Steps 2 and 4 can happen **concurrently** — traffic might still arrive for a moment after SIGTERM. That's normal. Your server handles whatever requests are already in the pipeline and rejects nothing.

### The `preStop` Hook

Kubernetes sends SIGTERM and removes the pod from endpoints at roughly the same time. There's a small window where the load balancer still sends traffic to the pod. A `preStop` hook adds a delay:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

This gives the load balancer 5 seconds to remove the pod from its rotation _before_ the server starts draining. It's a common production pattern.

### Configuring the Grace Period

```yaml
spec:
  terminationGracePeriodSeconds: 60  # default is 30
```

For services with long-running requests (file uploads, report generation), increase the grace period. For fast APIs like RustFlow, the default 30 seconds is more than sufficient.

### Docker Compose

Docker Compose also sends SIGTERM on `docker-compose down`, with a default 10-second grace period:

```yaml
services:
  rustflow:
    build: .
    stop_grace_period: 30s  # wait 30 seconds before SIGKILL
```

## Key Takeaways

1. **Graceful shutdown is one line in Axum.** `.with_graceful_shutdown(future)` handles all the complexity — stop accepting, drain in-flight, close cleanly. The hard part is writing the signal handler, and even that is straightforward with Tokio.

2. **Handle both SIGINT and SIGTERM.** SIGINT is Ctrl+C (development). SIGTERM is `kill`/Kubernetes (production). Handle both identically — drain and exit.

3. **`tokio::select!` races futures.** It returns when the first future completes. Perfect for "wait for signal A or signal B, whichever comes first."

4. **`#[cfg(unix)]` keeps code portable.** SIGTERM is Unix-only. Conditional compilation ensures the code works on all platforms while handling platform-specific signals where available.

5. **Post-drain cleanup runs after `.await`.** The line after `axum::serve(...).await` runs only after all connections are fully drained. Put cleanup logic (database connections, log flushing, metrics) there.

6. **Exit code matters in production.** Code 0 = clean shutdown. Non-zero = crash. Kubernetes, CI/CD, and monitoring systems use this to distinguish between graceful stops and failures.

7. **Kubernetes cooperation requires understanding the pod lifecycle.** SIGTERM, grace period, preStop hooks, and endpoint removal all interact. Your server's job is simple: catch SIGTERM, drain requests, exit quickly.
